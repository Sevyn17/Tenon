## 十、protocol 2

> 状态：已实现（2026-11-05）。原§一至§九描述的 protocol 1 已随 S8 删除。

### 10.1 为什么现在改、改成什么

现在只有我们自己的 `web/` 用这套协议，没有外部接入方，破坏性变更的成本最低。所以不在 protocol 1 上逐条修补，而是一次设计好 protocol 2，直接切过去，**不同时维护两个版本**。

protocol 1 的 G1–G10（见 10.10） 来自三个根因，protocol 2 针对根因设计：

| 根因 | 表现 | protocol 2 的做法 |
|---|---|---|
| 协议直接序列化内核内部结构 | G6（Go 字段名上线）、G7（`reason` 是拼好的字符串）、G8（两种存储形状不同）、G9 | 协议类型独立定义，`appapi` 做翻译（10.3） |
| 没有"快照 + 游标"的一致性模型 | G3（不能续订）、流式事件和条目之间靠猜 | list-then-watch（10.2），流式事件带关联 id（10.5） |
| 人在回路的等待不是会话状态 | G4、刷新或断线后不知道还有确认在等 | 交互（interaction）作为持久状态（10.6） |

G1、G2、G5 在 10.4、10.7、10.9 一并解决。

设计时按以下顺序取舍：**一致性 > 与内核解耦 > 人在回路 > 流式体验 > 命令易用性**。前三项错了会出数据错误或协议跟着内核坏，后两项错了只是不好用。

### 10.2 一致性模型：快照 + 游标

真相只在内核：会话日志和会话状态都以已提交的数据为准。客户端的做法是"先取快照，再从快照的游标往后订阅"，与 Kubernetes 用 `resourceVersion` 做 list + watch 相同。

```
session.get {session}
  → {info, run_state, mode, log: {base, len}, interactions: [...], live?, cursor: 1234}
session.subscribe {session, after: 1234}
  → 回放 cursor > 1234 的持久事件 → session.synced {cursor} → 实时（持久 + 易失）
断线重连
  → session.subscribe {session, after: 最后收到的 cursor}，不漏不重
游标过期（对应的数据已清理）
  → 错误码 cursor_expired，客户端重新 session.get
```

#### 10.2.1 事件表

protocol 1 的 `Replay` 不读事件日志，而是从 `session_entries`（按 `sync_seq`）和 `session_entries_archive`（按 `rewind_seq`）两张表现拼出 `entry` 与 `rewind`。档位、交互、运行状态都不在这两张表里，所以没法照此扩展。protocol 2 改为：

1. 每个会话一条只追加的事件序列，新表 `session_events(tenant, session_id, cursor, kind, data, at)`，主键 `(tenant, session_id, cursor)`。`cursor` 沿用 `sessions.next_sync_seq` 计数。
2. **每条持久事件与它描述的状态变化在同一个事务里写入**：
   - 检查点产生的事件（条目追加、回退、压缩、档位与设置变化、运行状态变化）随检查点写。
   - 不经过检查点的变化（交互的登记与结束）用单独的小事务，同时写状态行和事件行，同样校验租约纪元。protocol 1 的 `IssueCorr` 在检查点之外单独调用（`host.go:1241`），要改成这样。
3. `entry.appended` 的 `data` 只存 `{idx, entry_id}`，不重复存条目正文；回放时从 `session_entries` 或 `session_entries_archive` 取正文。其他事件的 `data` 存完整载荷。
4. `Replay` 只读这张表。`OnCommit` 推送的实时事件就是刚写进这张表的行。
5. 迁移：已有会话按现有条目和归档生成历史事件，游标沿用原 `sync_seq` / `rewind_seq`，已保存的客户端游标继续有效。

#### 10.2.2 规则

1. **游标按会话计**，单调递增，对外叫 `cursor`。
2. **会话状态的每个变化都是持久事件**（10.5 表一），重连后只靠订阅就能追上，不需要额外查询。
3. **快照包含界面需要的全部当前状态**：日志位置、运行状态、档位、设置、未结束的交互。
4. **快照字段一律来自已提交数据**：`session.get` 在一个读事务里读会话头、未结束交互和当前游标，不读内存。之后的变化一定在 `cursor` 之后。
5. **内存先生效、稍后提交的变化**：回合中改档位时，`SetExt` 只改内存，随下一个检查点落库（`host.go:1225`）。这时 `mode.set` 返回 `{state, committed: false}`：新档位已对后续工具调用生效，`session.mode_changed` 在落库时发出。快照里的 `mode` 是已提交值，可能比刚设的值晚一个检查点，客户端以 `mode_changed` 为准。空闲时 `mode.set` 等落库后返回 `committed: true`。`session.settings` 同理。
6. **易失事件不带游标**，丢了不影响正确性。它们挂在持久事件的坐标上（`turn`、`call_id`、`entry_id`，见 10.5），客户端能确定哪个持久事件会取代它。
7. **中途加入进行中的回合**：易失事件不回放，所以快照带可选的 `live`，内容是当前步已经累积的流式状态（`{turn, streams: [{stream_id, entry_id, part, text}], tools: [{call_id, name, args?}]}`）。`live` 读内存，不承诺持久，也不和 `cursor` 一致；它只用来让晚连上的客户端立刻看到正在输出的内容，之后照常被事件更新和取代。

#### 10.2.3 背压

持久事件和易失事件共用一条连接，但不能因为 `message.delta` 太多把持久事件也挤掉。订阅队列积压时按顺序降级：

1. 合并同一 `stream_id` 的 `message.delta`、同一 `call_id` 的 `tool.args_delta`（拼接文本，只发一条）。
2. 丢弃 `tool.progress` 和 `notice`。
3. 仍然积压：断开订阅，发 `session.lagged {cursor}`，`cursor` 是最后一条确实送达的持久事件。客户端用它重新订阅，只丢易失事件。

#### 10.2.4 进程范围（待拍板，见 10.12 D1）

实时事件靠进程内总线（`DB.OnCommit` → `Bus.Publish`），只覆盖本进程的提交。桌面端、CLI、网页服务连同一个库时，另一个进程写入的事件不会实时推送。推荐：

- **读**：订阅在本进程推送之外，再按游标轮询事件表（间隔 500 ms，只在有订阅时轮询），补上别的进程写的事件。有了 10.2.1 的事件表，这是一次索引范围查询。
- **写**：命令只能由持有会话租约的进程执行。目标会话的租约在别的进程手里时返回 `conflict`（`details.reason = "leased"`）。

### 10.3 协议类型与翻译层

- 协议类型放在新包 `appapi/wire`，**只放线上类型**：命令参数、结果、事件载荷、数据类型。全部带 json 标签，键名统一小写下划线。
- 内核类型（`session.Entry`、`bus.Envelope` 的 `Data any`、`host` 发的 `map[string]any`）不直接上线，由 `appapi` 写显式转换函数翻译成协议类型。内核字段改名、结构调整，只要翻译函数跟着改，协议不变。
- 协议类型是唯一来源：Go 类型 → JSON Schema → TS 类型，不再手写 `web/src/protocol.ts`。
- 一致性测试用**固定的事件流用例**：把真实会话的命令与事件录成 `appapi/testdata/wire/*.jsonl`，Go 测试校验翻译层输出与用例一致，TS 测试用同一批用例测 `client` 的状态合成。

线上数据类型（protocol 2）：

```ts
interface Entry {
  id: string;            // UUIDv7
  idx: number;           // 完整日志下标
  turn: number;
  at: number;            // Unix 毫秒
  source?: "user" | "agent" | "component" | "system" | string;   // 来自 meta.source，不再整体透出 meta
  client_ids?: string[]; // user 条目：吃进的输入的 client_id（多条输入合并成一个回合时有多个）
  item: Item;
}

type Item =
  | { kind: "user";        content: Part[] }
  | { kind: "assistant";   content: Part[]; reasoning?: Reasoning[]; tool_calls?: ToolCall[];
                           model?: string; usage?: Usage; interrupted?: boolean }
  | { kind: "tool_result"; call_id: string; output: Part[]; status: "ok" | "error" | "cancelled";
                           cancel_reason?: "turn_cancelled" | "redirected";
                           truncated?: boolean; output_ref?: string }
  | { kind: "compaction";  upto: number; summary: Part[] }
  | { kind: "context";     source: "snapshot" | "status"; text: string }   // 内核注入，界面可折叠
  | { kind: "unknown";     raw: unknown };

interface Part     { kind: "text" | "media" | "data" | string; text?: string; media?: MediaRef;
                     data?: unknown; schema?: string }   // data 部件带 schema 名，供前端选渲染器
interface MediaRef { ref: string; mime: string; size?: number; sha256?: string }   // 只带引用，不带字节
interface ToolCall { id: string; name: string; args: unknown }   // args 是 JSON 值，不是字符串
interface Usage    { input: number; output: number; cache_read: number; cache_write: number;
                     source: "reported" | "estimated" | "missing" }
```

与 protocol 1 的差别：内层键名小写下划线（G6）；`item` 改成平铺的判别联合，不再是 `{kind, user: {...}}` 的嵌套；`snapshot` / `status` 合并成 `context`；工具参数是 JSON 值；`WireID`、`Opaque` 等只对模型适配器有意义的字段不上线。

**大内容**：单帧上限 4 MiB，所以线上条目有大小约束。`tool_result.output` 的文本超过 64 KiB（阈值见 10.12 Q6）时截断，带 `truncated: true` 和 `output_ref`，全文用 `artifact.get` 取。媒体部件线上只带 `MediaRef`，字节用 `artifact.get` 取。截断只发生在翻译层，内核日志不变。

**`client_ids` 的来源**：protocol 1 的用户条目不记它消费了哪些收件箱项（`envelopeMeta` 只写 `source`、`from`、`trust`）。protocol 2 要求内核把消费的 inbox item id 写进条目 meta，翻译成 `client_ids`。客户端据此把乐观显示的输入替换成正式条目。

### 10.4 命令

约定：

- **幂等靠命令本身的语义，而不是一张通用的结果表**。能用绝对目标表达的命令一律用绝对目标（`rewind {to_turn}`、`compact {upto}`），重发天然无害。只有天然带去重键的命令接受 `client_id`：`send` 和 `steer`（收件箱项 id）、`session.create` 和 `session.fork`（会话 id）、`interaction.respond`（只收第一条回答）。
- 会话不存在一律返回 `not_found`，**任何命令都不隐式新建会话**（G1）。
- **乐观并发**：改日志的命令（`rewind`、`compact`、`fork`）接受可选的 `if_cursor`。会话的当前游标不等于它时返回 `conflict`（`details.reason = "stale"`），防止多端同时操作时一端拿着过期界面改日志。
- 回合号要等回合真正开始才知道（收件箱里的多条输入会合并成一个回合，`BeforeTurn` 也可能拒绝输入），所以 `send` 不返回 `turn`，由 `turn.started.inputs` 关联（10.5）。

`SessionSnapshot`：`{id, parent?, origin, title, pinned?, run_state, mode?, settings, log: {base, len}, interactions: Interaction[], live?, cursor}`。

`run_state` 只有 `idle` / `running`。`running` 合并了 protocol 1 的 `WaitingModel` / `WaitingTools`。"是否在等人"不单独作为状态，由客户端看有没有未结束的交互得出，避免同一件事有两个来源。

### 10.5 事件

信封：

```ts
interface Envelope<T> {
  v: 2;
  session: string;
  kind: string;
  at: number;
  cursor?: number;   // 只有持久事件有
  turn?: number;     // 回合内的事件都带
  data: T;
}
```

命名统一为 `领域.动作`，动作用过去式（G5）。

**表一：持久事件（带 `cursor`，写入事件表）**

| 事件 | 载荷 | 说明 |
|---|---|---|
| `entry.appended` | `{entry: Entry}` | 取代 `entry`。assistant 条目的 `entry.id` 等于流式事件里的 `entry_id` |
| `log.rewound` | `{to, voided_interactions: string[]}` | 取代 `rewind` 与 `session.rewound` |

**流式与条目的关联**：

- 内核在一步开始时预分配这一步 assistant 条目的 `id`，作为 `entry_id`。条目落库时用的就是这个 id。
- `stream_id` 每一段、每一次尝试各分配一个。一步里的 reasoning 和 text 是两段；模型重试时旧段收到 `message.discarded`，新段用新的 `stream_id`、同一个 `entry_id`、`attempt` 加一。
- 客户端收到 `entry.appended` 后，删掉 `entry_id` 等于 `entry.id` 的所有流，以条目为准。工具卡片按 `call_id` 对应 `tool_result` 条目。
- `turn.ended` 时，清掉这个回合所有还没被条目取代的流和工具卡片。失败或取消的回合可能根本不产生 assistant 条目。

**事件过滤**：传输层只推本章列出的事件，且只推连接订阅了的会话（protocol 1 推全部会话的全部事件）。内核的内部事件不再推给客户端；需要调试时由服务端开关打开，事件名前缀 `debug.`。按 `principal.role` 过滤见 10.8。

**会话列表的变化**：`sessions.list` 是分页查询，不提供可靠订阅。连接级事件 `sessions.changed {id, run_state, title, updated_at, pinned, deleted?}`（易失）用于刷新列表里的一行：运行状态变化、`session.update`、`session.delete` 时发出。改标题、置顶时 `updated_at` 为 0（保留原值）；`deleted: true` 时这一行与它的子会话从列表移除。重连后重新查询列表。

### 10.6 交互（人在回路）

工具确认、模块提问，以及以后的表单、多人审批，都统一成"交互"：内核在等人回答。交互是会话状态的一部分，出现在快照里，打开和结束都是持久事件。

```ts
interface Interaction {
  id: string;                  // 交互 id，公开；不是 corr
  session: string;             // 发起的会话（可能是子会话）
  turn: number;
  kind: "approval" | "question" | string;
  title: string;
  approval?: { tool: string; args: unknown; reason?: string;
               session_rules?: string[]; blocked?: string[] };   // "本次会话内都允许"会生成的规则
  question?: { text: string; options?: string[] };
  schema?: unknown;            // 回答须满足的 JSON Schema（表单类交互用）
  responders: string[];        // 谁可以回答（principal id）
  deadline?: number;           // Unix 毫秒
  opened_at: number;
}

// interaction.respond 的 response
type Response =
  | { approve: boolean; scope?: "once" | "session" }   // approval；scope=session 生成会话规则
  | { text: string }                                   // question
  | { value: unknown };                                // 带 schema 的交互

// interaction.resolved 的 outcome
type Outcome = "approved" | "denied" | "answered" | "expired" | "voided";
```

规则：

- **交互 id 与 corr 分开**。corr 是回信凭据（`CorrStore`：不可猜，由内核签发，信封路径只核对 corr 和联系名单），不能推给订阅者，否则凭据会扩散到 `viewer` 等不该拿到的人手里。交互对外只用公开的 `id`；`interaction.respond` 在服务端按 id 查到 corr，以连接身份作发信人投递回信。
- **只收第一条回答**。之后的回答返回 `conflict`（`details.reason = "answered"`），结果里带已有的 `outcome`。同一 `client_id` 的重发返回第一次的结果，不算冲突。
- **回答者由连接身份决定**，不能由客户端在参数里填（protocol 1 `session.reply` 的 `user` 参数取消）。不在 `responders` 里返回 `forbidden`。
- **失效有明确结果**：超过 `deadline` 为 `expired`；回退截掉了它、回合取消、进程重启后等待方已不存在，为 `voided`。每种情况都发 `interaction.resolved`，客户端不用猜。
- 进程重启后不承诺"交互继续等待"，因为等待它的工具调用本身会按工具记录恢复或重做；承诺的是快照和事件如实反映交互已失效。宿主启动恢复会话时，把上次进程留下的未结束交互标为 `voided`。

**子会话的交互必须让顶层看得到**。子智能体的确认发在 `<顶层>/<子>` 会话上，只订阅顶层的客户端看不到，回合就会一直卡住。所以：

- 子会话的 `interaction.opened` / `interaction.resolved` 除了写进自己的事件序列，还在同一事务里写进根会话的事件序列（载荷相同，`session` 字段指向发起的子会话）。订阅根会话即可看到整棵会话树里等人的地方。
- `session.subscribe {children: true}` 额外推子会话的其他事件，用于展开子智能体的过程；缺省不推。
- `interactions.list` 返回当前身份可以回答的全部未结束交互，供跨会话的"待我处理"视图使用；多会话界面以它加各根会话的订阅保持更新。

内核侧的基础已经有：确认走 `human:` 地址加 `corr`，登记在 `session_pending`（`store.CorrStore`），回退时 `VoidCorrAfter` 作废。要补的：

1. `session_pending` 增加列：公开的 `interaction_id`、`kind`、载荷、结束原因（outcome）、结束时间、回答者。
2. 登记与结束按 10.2.1 规则 2 与事件行同一事务写入；能按会话、按回答者列出未结束的条目。
3. `appapi.UI.Ask`（现在是进程内存里的 channel）改走同一条路：签发 corr、登记、经信封回答。

### 10.7 错误码

错误形状不变：`{code, message, retry, details?}`。错误码按**客户端要做的决定**划分，每个码对应一种处理方式：

| 码 | 含义 | 客户端怎么做 |
|---|---|---|
| `bad_request` | 帧或参数解析失败、缺必填参数 | 程序错误，记日志 |
| `invalid` | 参数格式对，但取值不被接受（如 `to_turn` 早于压缩点） | 提示用户，`details` 带说明 |
| `not_found` | 会话、交互、档位、工件不存在 | 从界面移除或提示 |
| `closed` | 会话已关闭（protocol 1 映射成 `not_found`，G2） | 标记为只读 |
| `not_idle` | 需要空闲的命令在回合中调用 | 等 `turn.ended` 后再试，或提示 |
| `busy` | 命令队列满 | 退避重试（`retry: true`） |
| `conflict` | 状态与预期不符，`details.reason` 区分：`exists`（已存在）、`answered`（交互已被回答）、`stale`（`if_cursor` 不符）、`leased`（会话由别的进程持有） | `exists` / `answered`：按 `details` 更新界面；`stale`：重新 `session.get`；`leased`：提示只读 |
| `denied` | 被守卫或权限策略拒绝 | 提示原因 |
| `need_confirm` | 需要用户确认后带 `confirm: true` 重发 | 弹确认 |
| `cursor_expired` | 订阅的游标对应的数据已清理 | 重新 `session.get` 后订阅 |
| `unauthorized` | 没有鉴权或鉴权失败 | 重新登录或取令牌 |
| `forbidden` | 已鉴权但身份无权执行 | 提示 |
| `unsupported` | 协议版本、命令或能力不支持 | 隐藏功能 |
| `internal` | 其他 | 提示并记日志 |

`message` 只给人看，客户端不得解析。

### 10.8 身份与权限

- 每个连接有一个 `principal {id, role}`，由传输层鉴权得出，`hello` 返回给客户端。桌面端和单机网页服务固定为 `{id: "local", role: "operator"}`。
- `role` 先定两级：`viewer`（只能查询和订阅）、`operator`（可以发命令和回答交互）。命令和事件推送都按 `role` 过滤。
- 内核的联系名单、交互的 `responders` 用 `principal.id` 核对。
- 鉴权方式由宿主决定：前端 `client` 接受一个"取令牌"回调，不写死令牌放在哪里。

- S8 已完成：`web/` 改用 `wire.gen.ts` 与新命令表 `web/src/api.ts`：先 `session.get`（会话不存在时显式 `session.create`）取快照、再从快照游标 `session.subscribe`，断线重连从最后的游标续订；`session.lagged` 时按游标重订，`cursor_expired` / `if_cursor` 冲突时重新取快照。确认与提问统一按交互显示，经 `interaction.respond` 回答。`apps/server` 每个 WebSocket 连接一个 `appapi.Conn`，`apps/desktop` 整个进程一个；事件只推订阅了的会话。protocol 1 删除：`appapi` 的旧命令表与方法、`session.go` / `modecmd.go` / `reply.go` / `pending.go`、`web/src/protocol.ts`；`V2` 的命令表成为唯一的 `App.Call`，CLI 的 `/rewind`、`/compact` 改用 protocol 2 方法。`MergeHooks` 原先漏了 `OnStream`（应用自带钩子时分段流式事件会丢），一并修了。S9（HTTP + SSE）不在本轮。

**Go 接口也是契约**：SDK 用户会直接调 `App` 的方法、引用 `appapi/wire` 的类型。"不同时维护两个版本"只适用于线上 JSON；Go 接口按 semver 管理，`appapi/wire` 的破坏性变更同样要升模块主版本。
