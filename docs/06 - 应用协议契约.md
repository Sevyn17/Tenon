> 状态：草案（2026-11-04）。按 `appapi/`、`apps/server`、`apps/desktop`、`runtime/host` 的现有代码整理，描述的是**现在线上的样子**；与目标不一致的地方集中在 §八，修完一条改一条。§十 是 protocol 2 的目标设计（待与后端线对齐），实现前不对外承诺。
> 依据：[归档/12 应用接口层](<90 - 归档/10 - 框架模块/12 - 应用接口层.md>)（原协议设计）、[计划/04 设计质量审查](<计划/04 - 设计质量审查（2026-11-04）.md>)（P1-28、P1-51、P1-57）。

本篇是前端、外部接入方与内核之间的唯一约定。写在这里的命令、事件、字段对外承诺稳定；没写的（包括 §4.4 的内部事件）随时可能变。

## 一、版本与兼容

- 协议版本 `PROTOCOL = 1`（`appapi.Protocol`）。客户端连上后先发 `hello{client, version}`；`version` 不等于服务端版本时返回 `unsupported`，`version = 0` 表示不声明。
- 同一版本内只允许：加命令、加可选参数、加结果字段、加事件类型、加事件字段、加错误码。
- 以下属于破坏性变更，必须升版本：删或改名命令 / 字段 / 事件、改字段类型或含义、可选参数变必填、改错误码含义。
- 客户端必须容忍：未知字段（忽略）、未知事件类型（忽略）、未知条目种类 `item.kind`（降级显示原始 JSON）、未知错误码（按 `internal` 处理）。

## 二、传输

所有传输承载同一套"命令 + 事件"，界面代码只依赖 `call(cmd, args) → Promise<result>` 与 `onEvent(envelope)`。

| 传输 | 命令 | 事件 | 鉴权 |
|---|---|---|---|
| 进程内（Go） | 直接调 `App` 方法，或 `App.Call(ctx, cmd, argsJSON)` | `App.Events(ctx, filter)`（易失）、`App.Follow(ctx, session, after)`（可靠） | 无 |
| Wails（桌面） | 绑定方法 `main.Service.Call(cmd, argsJSON) → resultJSON`；失败时错误文本是 `Error` 的 JSON | Wails 事件 `ybase:event`，数据为 `Envelope` | 同进程，不开端口 |
| WebSocket（网页服务） | 请求帧 `{"id", "cmd", "args"}` → 应答帧 `{"id", "ok": true, "result"}` 或 `{"id", "ok": false, "error": Error}` | 同一连接推 `{"event": Envelope}` | 见下 |

WebSocket 细节（`apps/server/server.go`）：

- 路径 `/ws`，别名 `/api`。
- 令牌三选一：查询串 `?token=`、cookie `ybase_token`、`Authorization: Bearer`。带 `?token=` 打开首页时服务端换成 HttpOnly cookie 并跳到 `/?token=`（空值，前端据此选 WebSocket 传输）。
- 必须带 `Origin`，且与 `Host` 同源；`Host` 必须在白名单里。不发 CORS 头，CSP 只允许同源。
- 单帧上限 4 MiB；单连接同时在途请求上限 16，超过的请求排队等待；写超时 10 s，超时断开连接。
- `id` 原样回传，类型由客户端定（字符串或数字）。应答顺序不保证与请求顺序一致。
- 连接上推送的是**全部会话**的事件（不按会话过滤）。

## 三、命令

约定：会话类命令都带 `session`（会话 id）；子会话 id 形如 `<顶层>/<子>`。结果为 `{}` 的写作 `Empty`。"需打开"指会话必须已在本进程打开，否则返回 `not_found`；"自动打开"指没打开就打开（**不存在时新建**，见 §八 G1）。

### 3.1 握手与会话

| 命令 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `hello` | `{client: string, version: int}` | `{protocol, server, model, workdir, trusted}` | 握手 |
| `sessions.list` | `{cursor?: int64, limit?: int, all?: bool}` | `{items: SessionInfo[], next: int64}` | 按 `updated_at` 倒序；`limit` 缺省 50，上限 500；`next = 0` 表示没有下一页，否则作为下一页的 `cursor`；`all` 含子会话 |
| `session.open` | `{session}` | `{id, run_state, log_len, base, mode?}` | 自动打开。`run_state`：`Idle` / `WaitingModel` / `WaitingTools` |
| `session.entries` | `{session, from?: int, to?: int, tail?: int}` | `{entries: EntryRow[], base, log_len}` | 读已提交日志 `[from, to)`；`from` 缺省为 `base`（最近压缩点），`to` 缺省为 `log_len`；`tail > 0` 时取最后 `tail` 条并忽略 `from` / `to`。回合中也可调 |
| `session.send` | `{session, text, item_id?}` | `Empty` | 自动打开。空闲时开回合，回合中排到下一回合。`item_id` 用于幂等：同一 id 只算一次 |
| `session.steer` | `{session, text}` | `Empty` | 需打开。回合中插话，下一步生效；空闲时返回 `not_idle` |
| `session.cancel` | `{session}` | `Empty` | 需打开。取消进行中的回合；空闲时无操作 |
| `session.rewind` | `{session, turns?: int}` | `{to}` | 自动打开，需空闲。退回最近 `turns` 个回合（缺省 1），日志截到 `to`；压缩点之前的回合不能退回 |
| `session.compact` | `{session}` | `{summary, upto, tokens_before?, tokens_after?}` | 自动打开，需空闲。未装压缩模块返回 `unsupported` |
| `session.fork` | `{session, to, upto?: int, origin?: "fork" \| "side"}` | `{id}` | 来源需空闲；`to` 已存在返回 `conflict`；`upto` 缺省为整段日志 |
| `session.stats` | `{session}` | `Stats` | 只读，回合中可用 |
| `session.max_steps` | `{session, n?: uint32}` | `{n}` | 自动打开。不带 `n` 为查询；`0` 表示不限；回合中到下一步边界生效 |

### 3.2 确认与提问

| 命令 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `session.confirm` | `{session, call_id, decision: "once" \| "session" \| "deny", tool?, args?}` | `{rules?: string[]}` | 需打开。回答 `human_requested`。`session` 是事件里的会话（可能是子会话）。`decision = "session"` 生成"本次会话内都允许"规则并返回，未装权限模块返回 `unsupported`；`tool` / `args` 缺省取服务端记下的事件内容 |
| `session.reply` | `{session, corr, user?, approve: bool, body?}` | `Empty` | 按 `corr` 回答一次人工确认，走信封投递。`user` 缺省 `"local"`，必须是会话创建者；`body` 非空时以它为准（`"approve"` / `"deny"` / JSON）。同一 `corr` 只收第一条 |
| `session.answer` | `{ask_id, text}` | `Empty` | 回答 `ask` 事件；问题已超时或已回答返回 `not_found`；应用没用事件化界面时返回 `unsupported` |

`session.confirm` 与 `session.reply` 回答的是同一件事，任选其一。需要生成会话规则时用 `confirm`。

## 四、事件

### 4.1 信封

```ts
interface Envelope<T> {
  v: number;       // 信封格式版本（bus.Version）
  seq: number;     // > 0：持久事件的同步序号；0：易失事件
  at: number;      // Unix 毫秒
  session: string; // 所属会话；空 = 不属于某个会话（见 §八 G4）
  kind: string;
  data?: T;
}
```

### 4.2 持久事件（`seq > 0`）

由存储在提交成功后发出，可以回放。界面上的已提交内容以它们为准。

| kind | data | 说明 |
|---|---|---|
| `entry` | `{idx: int, entry: Entry}` | 日志追加了一条，`idx` 是完整日志下标 |
| `rewind` | `{to: int}` | 日志截到 `to`，`idx >= to` 的条目作废 |

### 4.3 易失事件（`seq = 0`，公开）

只用于显示进行中的状态，丢了不影响正确性：断线重连后客户端按 §七 用持久数据补齐。

| kind | data | 来源 | 说明 |
|---|---|---|---|
| `turn_start` | — | host | 回合开始 |
| `turn_end` | `{reason: string}` | host | 回合结束。`reason`：`Done` / `Cancelled` / `MaxSteps` / `Denied(<code>)` / `Failed(<code>)` |
| `turn_denied` | `{unconsumed: Content}` | host | 回合被拒，`unconsumed` 是没被处理的输入 |
| `turn.interrupted` | — | host | 回合被中断 |
| `turn.failed` | `{error: string}` | host | 回合失败 |
| `text_delta` | `{text}` | appapi | 正文增量，按 30 ms 合批；保证在同一会话的 `tool_call` / `tool_result` / `turn_end` 之前发出 |
| `text_reset` | — | appapi | 模型重试，丢弃本步已收到的正文 |
| `tool_call` | `{call_id, name, args: string}` | appapi | `args` 是 JSON 文本 |
| `tool_result` | `{call_id, preview: string, error: bool}` | appapi | `preview` 截到 300 字符；全文看随后的 `entry` |
| `human_requested` | `{call_id, tool, reason, args: string, corr, deadline: int64}` | host | 工具调用等待人工确认；`deadline` 为 Unix 毫秒。用 `session.confirm` 或 `session.reply` 回答 |
| `ask` | `{ask_id, question, options: string[]}` | appapi | 模块向用户提问；用 `session.answer` 回答 |
| `notice` | `{text}` | appapi | 提示文本（档位文件更新、规则保存失败、模块告警等） |
| `session.forked` | `{from, upto, origin}` | host | 本会话由 `from` 分出 |
| `session.rewound` | `{to, corr_voided}` | host | 退回完成；`corr_voided` 是随之作废的确认 |
| `session.suspended` | `{reason}` | host | 会话挂起 |
| `session.resumed` | — | host | 会话恢复 |
| `session.closed` | `{reason}` | host | 会话关闭（如 `parent_rewind`：父会话退回导致子会话关闭） |
| `session.escalated` | `{error}` | host | 错误上报给父会话 |
| `resync` | — | 传输层 | 事件订阅因慢消费被断开并已重订，期间的事件可能丢失，客户端须按 §七 补齐 |

### 4.4 内部事件（不承诺）

以下事件也会出现在事件流上，用于调试和 `trace.explain`，字段与是否存在都不保证稳定，客户端不得依赖：`mail.delivered`、`mail.rejected`、`mail.failed`、`mail.dead`、`guard.denied`、`human.answered`、`session_wake`、`session_sleep`、`store.pruned`、`store.prune_failed`，以及任何未列在 §4.2、§4.3 的类型。

## 五、数据类型

字段名以线上 JSON 为准。`Entry` 内层结构体（`UserItem`、`AssistantItem` 等）没有 json 标签，线上键名是 Go 字段名（大驼峰），见 §八 G6。

```ts
interface SessionInfo { id; title; preview; run_state; origin; parent; updated_at }  // 部分字段可能为空串

interface EntryRow { idx: number; entry: Entry }

interface Entry {
  v: number; id: string;  // id 全局唯一、按时间有序（UUIDv7）
  turn: number;           // 回合序号，从 1 开始
  at: number;             // Unix 毫秒
  meta?: { source?; from?; trust?: "trusted" | "untrusted"; steer?: "append" | "redirect"; [k: string]: unknown };
  item: Item;
}

interface Item {
  kind: "user" | "assistant" | "tool_result" | "compaction" | "snapshot" | "status" | "unknown" | string;
  user?:        { Content: Part[] | null };
  assistant?:   { Reasoning?: { Text?; Opaque? }[]; Content: Part[] | null; ToolCalls?: ToolCall[];
                  Model?; Usage?: Usage; Interrupted?: boolean };
  tool_result?: { CallID; Output: Part[] | null; Status: { State: "ok" | "error" | "cancelled";
                  CancelReason?: "TurnCancelled" | "Redirected" } };
  compaction?:  { Upto: number; Summary: Part[] | null };
  injection?:   { Text: string };  // kind 为 snapshot（上下文快照）或 status（状态更新）时的载荷；内部注入，界面可不显示
  unknown?:     { Raw: unknown };
}

interface Part { kind: "text" | "media" | "data" | "unknown" | string; text?; media?; data?; raw? }
interface ToolCall { ID; WireID?; Name; Args: unknown }
interface Usage { Input; Output; CacheRead; CacheWrite; Source: "Reported" | "Estimated" | "Missing" }

interface Stats { attempts; reported; missing; errors; input; output; cache_read; cache_write;
                  hit_rate; tool_calls; compacts; composition?; last_request? }

interface ModeInfo  { id; label; builtin: boolean; project: boolean; widened?: string[] }
interface ModeState { mode; label; sandbox }
interface ModeItem  { item; title; value; source; bounded: boolean }
interface PluginInfo  { name; on: boolean; default: boolean; source; effects: string[]; schema: Field[] }
interface PackageInfo { name; version; description; scope: "user" | "project"; source; contents }
```

## 六、错误

失败结果统一为 `Error{code: string, message: string, retry: bool}`。`message` 给人看，不用于判断；判断只用 `code`。`retry = true` 表示可以原样重试。

| code | 含义 |
|---|---|
| `bad_request` | 参数不合法 |
| `not_found` | 会话 / 档位 / 问题不存在，或会话未打开 |
| `busy` | 命令队列满，`retry = true` |
| `not_idle` | 需空闲的命令在回合中调用，或会话不在等待状态 |
| `conflict` | 会话被另一进程写入或接管，或目标已存在 |
| `unauthorized` | 令牌 / Origin / Host 检查失败（只出现在网页服务） |
| `unsupported` | 协议版本、命令或能力不支持（含未装对应模块） |
| `need_confirm` | 项目档位放宽了权限且未确认过，带 `confirm: true` 重发 |
| `internal` | 其他 |

## 七、客户端约定

打开一个会话并保持同步：

1. `hello` 协商版本。
2. `session.open` 拿 `log_len` 和 `base`。
3. `session.entries`（缺省区间，或 `tail`）取已提交条目，按 `idx` 放好。
4. 处理事件流里该会话的事件：
   - `entry`：按 `idx` 写入，同一 `idx` 重复到达时覆盖，不追加。
   - `rewind`：删掉 `idx >= to` 的条目。
   - 收到某一步的 `entry`（assistant 或 tool_result）后，丢弃这一步的流式缓冲（`text_delta` 累积的正文、`tool_call` / `tool_result` 的临时卡片），以条目为准。
   - `text_reset`：清空当前步的流式正文。
5. 收到 `resync` 或传输重连后：重新 `session.entries` 补齐当前打开的会话，清空所有流式缓冲；进行中的确认和提问可能已丢失，以 `session.open` 的 `run_state` 为准判断会话是否还在等待。

其他：

- 待确认项以 `call_id` 为键，收到对应的 `tool_result` 或 `entry`，或 `turn_end` 时移除。
- `ask` 以 `ask_id` 为键；`session.answer` 返回 `not_found` 说明问题已超时，直接移除。
- 不要从 `message` 文本里解析信息。

| 编号 | 问题 | 影响 | 归属 | 计划 |
|---|---|---|---|---|
| G1 | `session.open` / `send` / `rewind` / `compact` / `mode.set` / `max_steps` 遇到不存在的 id 静默新建 | 打错 id 不报错，会多出空会话 | P1-57 | 拆出 `session.create`；其余命令对不存在的会话返回 `not_found`。属破坏性变更，与 G2 一起升 protocol 2 |

## 十、protocol 2 目标设计

> 状态：提案（2026-11-04），待与后端那条线对齐。§一至§九描述 protocol 1 现状；本章是要切换到的目标。protocol 2 落地、`web/` 切换完成后，本章替换§一至§八，protocol 1 不再保留。

### 10.1 为什么现在改、改成什么

现在只有我们自己的 `web/` 用这套协议，没有外部接入方，破坏性变更的成本最低。所以不在 protocol 1 上逐条修补，而是一次设计好 protocol 2，直接切过去，**不同时维护两个版本**。

§八的 G1–G10 来自三个根因，protocol 2 针对根因设计：

| 根因 | 表现 | protocol 2 的做法 |
|---|---|---|
| 协议直接序列化内核内部结构 | G6（Go 字段名上线）、G7（`reason` 是拼好的字符串）、G8（两种存储形状不同）、G9 | 协议类型独立定义，`appapi` 做翻译（10.3） |
| 没有"快照 + 游标"的一致性模型 | G3（不能续订）、流式事件和条目之间靠猜 | list-then-watch（10.2），流式事件带关联 id（10.5） |
| 人在回路的等待不是会话状态 | G4、刷新或断线后不知道还有确认在等 | 交互（interaction）作为持久状态（10.6） |

G1、G2、G5 在 10.4、10.7、10.9 一并解决。

设计时按以下顺序取舍：**一致性 > 与内核解耦 > 人在回路 > 流式体验 > 命令易用性**。前三项错了会出数据错误或协议跟着内核坏，后两项错了只是不好用。

### 10.2 一致性模型：快照 + 游标

真相只在内核：会话日志和会话状态都以已提交的数据为准。客户端的做法是"先取快照，再从快照的游标往后订阅"，与 Kubernetes 用 `resourceVersion` 做 list + watch 相同。

```
session.get {session}
  → {info, run_state, mode, log: {base, len}, interactions: [...], cursor: 1234}
session.subscribe {session, after: 1234}
  → 回放 cursor > 1234 的持久事件 → session.synced {cursor} → 实时（持久 + 易失）
断线重连
  → session.subscribe {session, after: 最后收到的 cursor}，不漏不重
游标过期（对应的数据已清理）
  → 错误码 cursor_expired，客户端重新 session.get
```

规则：

1. **游标按会话计**，单调递增。沿用存储已有的 `sync_seq`（`sessions.next_sync_seq`），对外叫 `cursor`。
2. **会话状态的每个变化都是带游标的持久事件**，不只是条目追加和回退。protocol 2 的持久事件见 10.5 表一。这样重连后只靠订阅就能追上，不需要再额外查询。
3. **快照包含界面需要的全部当前状态**：日志位置、运行状态、档位、未结束的交互。protocol 1 的 `session.open` 不返回待确认项，这是要补的缺口。
4. **快照和游标原子一致**：`session.get` 返回的 `cursor` 是读快照那一刻的值，之后的变化一定在 `cursor` 之后。
5. **易失事件不带游标**，丢了不影响正确性，只影响"正在发生什么"的显示。它们挂在持久事件的坐标上（`turn`、`call_id`、`stream_id`，见 10.5），客户端能确定哪个持久事件会取代它。
6. **背压明确告知**：慢订阅被断开时，发 `session.lagged {session, cursor}`，告诉客户端从哪个游标之后可能丢了，客户端用它重新订阅。取代 protocol 1 不带信息的 `resync`。

客户端状态因此只有两层：

- **已提交层**：由快照和持久事件维护，是界面显示内容的依据。
- **流式层**：由易失事件维护，收到对应的持久事件后整块替换。

### 10.3 协议类型与翻译层

- 在 `appapi` 下单独建协议类型包（名称待定，见 10.12 Q4），**只放线上类型**：命令参数、结果、事件载荷、数据类型。全部带 json 标签，键名统一小写下划线。
- 内核类型（`session.Entry`、`bus.Envelope` 的 `Data any`、`host` 发的 `map[string]any`）不直接上线，由 `appapi` 写显式转换函数翻译成协议类型。内核字段改名、结构调整，只要翻译函数跟着改，协议不变。
- 协议类型是唯一来源：Go 类型 → JSON Schema → TS 类型，不再手写 `web/src/protocol.ts`。
- 一致性测试用**固定的事件流用例**：把真实会话的命令与事件录成 `appapi/testdata/wire/*.jsonl`，Go 测试校验翻译层输出与用例一致，TS 测试用同一批用例测 `client` 的状态合成。

线上数据类型（protocol 2）：

```ts
interface Entry {
  id: string;            // UUIDv7
  idx: number;           // 完整日志下标
  turn: number;
  at: number;            // Unix 毫秒
  source?: "user" | "agent" | "system" | ...;   // 来自 meta.source，不再整体透出 meta
  item: Item;
}

type Item =
  | { kind: "user";        content: Part[] }
  | { kind: "assistant";   content: Part[]; reasoning?: Reasoning[]; tool_calls?: ToolCall[];
                           model?: string; usage?: Usage; interrupted?: boolean }
  | { kind: "tool_result"; call_id: string; output: Part[]; status: "ok" | "error" | "cancelled";
                           cancel_reason?: "turn_cancelled" | "redirected"; output_ref?: string }
  | { kind: "compaction";  upto: number; summary: Part[] }
  | { kind: "context";     source: "snapshot" | "status"; text: string }   // 内核注入，界面可折叠
  | { kind: "unknown";     raw: unknown };

interface Part     { kind: "text" | "media" | "data" | string; text?: string; media?: MediaRef;
                     data?: unknown; schema?: string }   // data 部件带 schema 名，供前端选渲染器
interface ToolCall { id: string; name: string; args: unknown }   // args 是 JSON 值，不是字符串
interface Usage    { input: number; output: number; cache_read: number; cache_write: number;
                     source: "reported" | "estimated" | "missing" }
```

与 protocol 1 的差别：内层键名小写下划线（G6）；`item` 改成平铺的判别联合，不再是 `{kind, user: {...}}` 的嵌套；`snapshot` / `status` 合并成 `context`；工具参数是 JSON 值；`WireID`、`Opaque` 等只对模型适配器有意义的字段不上线。

### 10.4 命令

约定：

- 会产生副作用的命令都接受 `client_id`（幂等键，客户端生成）。同一会话内同一 `client_id` 只执行一次，重发返回第一次的结果。
- 会话不存在一律返回 `not_found`，**任何命令都不隐式新建会话**（G1）。
- 命令的结果带上能关联后续事件的标识（例如 `send` 返回 `turn`）。

| 命令 | 参数 | 结果 | 变化 |
|---|---|---|---|
| `hello` | `{client, protocol}` | `{protocol, server, principal, capabilities: string[], model, workdir, trusted}` | 新增 `principal`（10.8）与能力清单；界面按能力决定显示哪些功能，不再靠调用失败才知道 |
| `sessions.list` | `{cursor?, limit?, all?}` | `{items, next}` | 不变 |
| `session.create` | `{session?, definition?, client_id?}` | `SessionSnapshot` | 新增。`session` 缺省时由服务端生成；已存在返回 `conflict` |
| `session.get` | `{session}` | `SessionSnapshot` | 取代 `session.open`；不存在返回 `not_found` |
| `session.subscribe` | `{session, after?: cursor}` | `{}` | 新增（G3）。`after` 缺省为当前游标（只收新事件） |
| `session.unsubscribe` | `{session}` | `{}` | 新增 |
| `session.entries` | `{session, from?, to?, tail?}` | `{entries: Entry[], base, len}` | 结构按 10.3 |
| `session.send` | `{session, text, client_id?}` | `{turn, queued: bool}` | `item_id` 改名 `client_id`；返回本次输入所属回合，`queued` 表示排在进行中的回合之后 |
| `session.steer` | `{session, text, client_id?}` | `{}` | 加幂等键 |
| `session.cancel` | `{session}` | `{}` | 不变 |
| `session.rewind` | `{session, turns?, client_id?}` | `{to}` | 不再隐式新建 |
| `session.compact` | `{session, client_id?}` | `{summary, upto, tokens_before?, tokens_after?}` | 同上 |
| `session.fork` | `{session, to?, upto?, origin?}` | `SessionSnapshot` | `to` 可缺省由服务端生成；直接返回新会话快照 |
| `session.stats` | `{session}` | `Stats` | 不变 |
| `session.settings` | `{session, max_steps?}` | `{max_steps}` | 取代 `session.max_steps`；以后的会话级设置都放这里 |
| `interaction.respond` | `{interaction, response, client_id?}` | `{outcome}` | 取代 `session.confirm` / `session.answer` / `session.reply`（10.6） |
| `mode.list` / `mode.get` / `mode.set` / `mode.show` | 同 protocol 1 | 同 protocol 1 | `mode.set` 不再隐式新建会话；档位变化以 `session.mode_changed` 事件通知 |
| `plugins.list` / `plugins.set` / `packages.list` | 同 protocol 1 | 同 protocol 1 | 名称不动（05 命名方案：外部可见名不改） |
| `artifact.get` | `{session, ref}` | `{mime, text?, base64?, size}` | 实现（G10），`ref` 来自 `tool_result.output_ref` / `tool.ended.output_ref` |
| `trace.explain` | `{trace}` | `{text}` | 不变 |

`SessionSnapshot`：`{id, parent?, origin, title, run_state, mode?, settings, log: {base, len}, interactions: Interaction[], cursor}`。

`run_state` 取值：`idle` / `running` / `waiting_human`。`running` 合并了 protocol 1 的 `WaitingModel` / `WaitingTools`（界面不需要区分），`waiting_human` 由未结束的交互推出。

### 10.5 事件

信封：

```ts
interface Envelope<T> {
  v: 2;
  session: string;
  kind: string;
  at: number;
  cursor?: number;   // 只有持久事件有
  turn?: number;     // 回合内的事件都带
  data: T;
}
```

命名统一为 `领域.动作`，动作用过去式（G5）。

**表一：持久事件（带 `cursor`）**

| 事件 | 载荷 | 说明 |
|---|---|---|
| `entry.appended` | `{entry: Entry, stream_id?}` | 取代 `entry`。`stream_id` 见下文"流式与条目的关联" |
| `log.rewound` | `{to, voided_interactions: string[]}` | 取代 `rewind` 与 `session.rewound` |
| `log.compacted` | `{upto, entry_idx}` | 新增：压缩点前移 |
| `session.state_changed` | `{run_state}` | 新增：运行状态变化 |
| `session.mode_changed` | `{mode, label, sandbox}` | 新增：档位变化（任一端改档位，其他端都能看到） |
| `session.settings_changed` | `{settings}` | 新增 |
| `interaction.opened` | `Interaction` | 新增（10.6） |
| `interaction.resolved` | `{id, outcome, by?}` | 新增（10.6） |
| `session.closed` | `{reason}` | 由易失改为持久 |
| `session.forked` | `{from, upto}` | 由易失改为持久，发在新会话上 |

**表二：易失事件（不带 `cursor`）**

| 事件 | 载荷 | 说明 |
|---|---|---|
| `turn.started` | `{turn}` | |
| `turn.ended` | `{turn, kind: "done" \| "cancelled" \| "max_steps" \| "denied" \| "failed", code?, message?}` | 结构化（G7） |
| `turn.rejected` | `{reason}` | 取代 `turn_denied`：输入被守卫拒绝，没有开回合 |
| `message.started` | `{stream_id, part: "text" \| "reasoning"}` | |
| `message.delta` | `{stream_id, text}` | 合批间隔保持 16–50 ms |
| `message.ended` | `{stream_id}` | |
| `message.discarded` | `{stream_id}` | 模型重试，丢弃这一段；取代 `text_reset` |
| `tool.started` | `{call_id, name}` | |
| `tool.args_delta` | `{call_id, text}` | 参数流式（长参数期间界面也有进度） |
| `tool.running` | `{call_id, args}` | 参数完整，开始执行 |
| `tool.progress` | `{call_id, text?, data?}` | 可选，工具自己发 |
| `tool.ended` | `{call_id, status, preview, output_ref?}` | 取代 `tool_result` 事件 |
| `notice` | `{level: "info" \| "warn", source?, text}` | 带 `session`（G4）；不属于任何会话的发在空会话上 |
| `session.synced` | `{cursor}` | 订阅回放完毕 |
| `session.lagged` | `{cursor}` | 背压断开，见 10.2 |

**流式与条目的关联**：同一步的 `message.*` 与随后落库的 assistant 条目必须能对上。推荐做法是内核在开始一步时预分配这一步 assistant 条目的 id，用它作 `stream_id`，`entry.appended` 带同一个值；客户端收到后按 `stream_id` 把流式层整块替换成条目。工具卡片按 `call_id` 对应 `tool_result` 条目。备选做法见 10.12 Q1。

**事件过滤**：传输层只推本章列出的事件，且只推连接订阅了的会话（protocol 1 推全部会话的全部事件）。§4.4 的内部事件不再推给客户端；需要调试时由服务端开关打开，事件名前缀 `debug.`。

**会话列表的变化**：`sessions.list` 是分页查询，不提供可靠订阅。连接级事件 `sessions.changed {id, run_state, title, updated_at}`（易失）用于刷新列表里的一行；重连后重新查询列表。

### 10.6 交互（人在回路）

工具确认、模块提问，以及以后的表单、多人审批，都统一成"交互"：内核在等人回答。交互是会话状态的一部分，出现在快照里，打开和结束都是持久事件。

```ts
interface Interaction {
  id: string;                  // 即内核签发的 corr
  session: string;             // 发起的会话（可能是子会话）
  turn: number;
  kind: "approval" | "question" | string;
  title: string;
  approval?: { tool: string; args: unknown; reason?: string;
               session_rules?: string[]; blocked?: string[] };   // "本次会话内都允许"会生成的规则
  question?: { text: string; options?: string[] };
  schema?: unknown;            // 回答须满足的 JSON Schema（表单类交互用）
  responders: string[];        // 谁可以回答（principal id）
  deadline?: number;           // Unix 毫秒
  opened_at: number;
}

// interaction.respond 的 response
type Response =
  | { approve: boolean; scope?: "once" | "session" }   // approval；scope=session 生成会话规则
  | { text: string }                                   // question
  | { value: unknown };                                // 带 schema 的交互

// interaction.resolved 的 outcome
type Outcome = "approved" | "denied" | "answered" | "expired" | "voided";
```

规则：

- **只收第一条回答**。之后的回答返回 `conflict`，结果里带已有的 `outcome`。
- **回答者由连接身份决定**，不能由客户端在参数里填（protocol 1 `session.reply` 的 `user` 参数取消）。不在 `responders` 里返回 `forbidden`。
- **失效有明确结果**：超过 `deadline` 为 `expired`；回退截掉了它、回合取消、进程重启后等待方已不存在，为 `voided`。每种情况都发 `interaction.resolved`，客户端不用猜。
- 进程重启后不承诺"交互继续等待"，因为等待它的工具调用本身会按工具记录恢复或重做；承诺的是快照和事件如实反映交互已失效。

内核侧的基础已经有：确认走 `human:` 地址加 `corr`，登记在 `session_pending`（`store.CorrStore`），回退时 `VoidCorrAfter` 作废。要补的：

1. `appapi.UI.Ask`（现在是进程内存里的 channel）改走同一条路：签发 `corr`、登记、经信封回答。
2. `session_pending` 的登记与结束写入会话的持久事件序列（分配 `cursor`），并能按会话列出未结束的条目供快照用。
3. 结束原因（approved / denied / answered / expired / voided）落到登记里。

### 10.7 错误码

错误形状不变：`{code, message, retry, details?}`。错误码按**客户端要做的决定**划分，每个码对应一种处理方式：

| 码 | 含义 | 客户端怎么做 |
|---|---|---|
| `bad_request` | 帧或参数解析失败、缺必填参数 | 程序错误，记日志 |
| `invalid` | 参数格式对，但取值不被接受（如 `turns` 超过可退回的回合数） | 提示用户，`details` 带说明 |
| `not_found` | 会话、交互、档位、工件不存在 | 从界面移除或提示 |
| `closed` | 会话已关闭（protocol 1 映射成 `not_found`，G2） | 标记为只读 |
| `not_idle` | 需要空闲的命令在回合中调用 | 等 `turn.ended` 后再试，或提示 |
| `busy` | 命令队列满 | 退避重试（`retry: true`） |
| `conflict` | 已存在、已被回答、被别的进程接管 | 重新 `session.get` |
| `denied` | 被守卫或权限策略拒绝 | 提示原因 |
| `need_confirm` | 需要用户确认后带 `confirm: true` 重发 | 弹确认 |
| `cursor_expired` | 订阅的游标对应的数据已清理 | 重新 `session.get` 后订阅 |
| `unauthorized` | 没有鉴权或鉴权失败 | 重新登录或取令牌 |
| `forbidden` | 已鉴权但身份无权执行 | 提示 |
| `unsupported` | 协议版本、命令或能力不支持 | 隐藏功能 |
| `internal` | 其他 | 提示并记日志 |

`message` 只给人看，客户端不得解析。

### 10.8 身份与权限

- 每个连接有一个 `principal {id, role}`，由传输层鉴权得出，`hello` 返回给客户端。桌面端和单机网页服务固定为 `{id: "local", role: "operator"}`。
- `role` 先定两级：`viewer`（只能查询和订阅）、`operator`（可以发命令和回答交互）。命令和事件推送都按 `role` 过滤。
- 内核的联系名单、交互的 `responders` 用 `principal.id` 核对。
- 鉴权方式由宿主决定：前端 `client` 接受一个"取令牌"回调，不写死令牌放在哪里。

### 10.9 传输

| 传输 | 命令 | 事件 | 状态 |
|---|---|---|---|
| 进程内（Go） | `App` 方法 | `App.Subscribe` | 已有，改用协议类型 |
| Wails | `Service.Call` | Wails 事件 | 已有，改为按订阅推送 |
| WebSocket | 请求 / 应答帧 | 事件帧 | 已有，改为按订阅推送 |
| HTTP + SSE | `POST /api/<cmd>` | `GET /api/events?session=…`，SSE 的 `id` 字段用 `cursor`，重连时浏览器自动带 `Last-Event-ID` | 新增，给外部嵌入用：易过代理和网关，鉴权用普通请求头 |

帧格式、鉴权检查（令牌、Origin、Host 白名单）、帧大小与在途上限沿用 protocol 1。WebSocket 一个连接可以订阅多个会话；SSE 一个连接对应一组会话。

| S5 | 交互模型：`Ask` 走 `corr`、`session_pending` 写入持久事件序列、快照列出未结束交互 | `runtime/host`、`runtime/store`、`appapi` | 后端线 | S3 |
| S6 | 运行状态、档位、设置变化作为持久事件 | `runtime/store`、`runtime/host` | 后端线 | S3 |
| S7 | 前端 `client` 按 protocol 2 实现并切换，删除 protocol 1 | `web/` | 前端线 | S1–S6 |
| S8 | HTTP + SSE 传输 | `apps/server` | 前端线 | S3 |

S1–S3 基本只改 `appapi` 和应用，不碰 `runtime/`，可以和后端线现在手上的 P1 修复并行。S4–S6 要改内核，等后端线排期。S5、S6 改存储，要带 schema 迁移。
