# 沙箱（M6.1 调研一页，安全项）

## 参考

- **DSH** `dsh-sandbox`：模式 read-only / workspace-write / danger-full-access；请求的模式无法强制执行时以 `SANDBOX_UNAVAILABLE` 失败，**绝不降级为不受限**；被拒后模型可为单次调用申请**严格更宽**的模式，由人批准一次。`dsh-sandbox-windows-acl`：WRITE_RESTRICTED 受限令牌（登录 SID、Everyone、按工作区路径派生的能力 SID、私有临时目录 SID）+ 降到 Low 完整性；工作区一次性写入“能力 SID 允许 ACE + Everyone 拒绝 FILE_DELETE_CHILD + Low 强制标签”；只读模式不带写 SID；自述为“部分保证”（硬链接等）。`dsh-fs-sandbox`：进程内文件工具按模式限写。
- **Codex** `windows-sandbox-rs`：受限令牌 + 能力 SID + ACL 授权，工作区内 `.git` / `.codex` 保持只读；`linux-sandbox` 用 landlock + seccomp；默认禁网。`orchestrator.rs`：沙箱拒绝后升级重试，不二次审批。
- **pi-mono / opencode / goose**：无 OS 级沙箱，靠审批。

## 结论

1. **机制**：`kernel/plugins/sandbox` 包，`Apply(cmd, mode)` 在进程启动前把子进程放进沙箱；shell / 后台 job 都走它（单一路径）。进程内文件工具已由 `resolve` 限定在工作区内，不经沙箱。
2. **Windows 实现（M7 改版：写受限令牌 + 能力 SID，不再改完整性级别）**：`CreateRestrictedToken(DISABLE_MAX_PRIVILEGE|LUA_TOKEN|WRITE_RESTRICTED)` 复制当前令牌，受限 SID 依次为 [能力 SID]、登录 SID、Everyone；写访问要通过普通 SID 与受限 SID 两轮检查，读不受影响。
   - 能力 SID 由工作区规范路径（小写、Clean）的 SHA-256 派生 `S-1-5-21-a-b-c-d`，确定性，重启后不变，无需另存。
   - workspace-write：工作区根 DACL 追加一条可继承的“能力 SID 读写执行删除”ACE（每进程每工作区一次）；`.ybase/` 追加能力 SID 拒写 ACE（拒绝 ACE 排在前面）；TEMP / TMP 改到能力 SID 可写的专用目录 `%LOCALAPPDATA%\ybase\sbtmp\<hash>`。
   - read-only：令牌不带能力 SID，工作区内外都写不了（Everyone 可写的目录除外）。
   - 令牌默认 DACL 给登录 SID（Codex 做法），否则子进程建不了自己的对象。
   - 旧方案（Low 完整性 + 给工作区打 Low 标签）的副作用：工作区被降级后，工作区里构建出的 exe 以 Low 运行，连 `.ybase` 都建不了。新方案不改标签，此问题消失。
   - `ybase sandbox-reset [-dir 工作区]` 撤销沙箱对工作区的全部修改：能力 SID ACE（根、受保护目录、临时目录）和旧版留下的 Low / Medium 标签。
3. **不降级**：模式无法强制执行（非 Windows、令牌或标签失败）→ 工具返回 `SANDBOX_UNAVAILABLE`，不执行命令。非 Windows 平台 P0 只支持 danger-full-access（landlock / bwrap 推迟）。
4. **一次性升权**：shell 参数 `sandbox_permissions`（workspace-write / danger-full-access）。比会话模式更宽时，`sandbox` Guard 返回 Confirm（**即使权限模式是 full 也要人批准**），批准只对这一次调用有效；执行器再核对 `cx.Approved`（纵深防御）。更窄的申请直接生效。sandbox Guard 排在 permission Guard 之前，一次确认同时覆盖两者。
5. **默认**：沙箱模式取档位的 `sandbox.level` 项（level 型，权限插件登记）：内置仅可查看 → read-only，每次询问 / 工作区允许 → workspace-write，完全权限 → danger-full-access；`-sandbox` 可固定。档位按会话持久化（见 05 - 权限.md）。其他子进程也走同一 Confiner：MCP stdio 服务按服务的 `sandbox` 字段，缺省取新会话缺省档位的 `sandbox.level`（沙箱插件未启用时不加沙箱并告警）；用户钩子按钩子的 `sandbox` 字段，缺省 workspace-write。shell 被拒（输出含“拒绝访问 / Access is denied”等）时，结果末尾提示模型用 `sandbox_permissions` 申请下一档，需人批准，仅本次有效。
6. **已知缺口（部分保证，如实报告）**：读不受限；网络不受限；Everyone 可写的位置（少数公共目录）仍可写；硬链接到工作区外的文件可被改写；`.git` 未单独保护；写到用户目录的工具缓存在沙箱内会失败：GOCACHE 已改指到该工作区的专用临时目录（`sbtmp\<hash>\go-build`），npm / pip / cargo 等其他缓存尚未处理，需要升权。**node / libuv 用管道 stdio 启动子进程会 `spawn EPERM`**（vite、esbuild、部分 npm 脚本）：libuv 的管道是命名管道，其缺省安全描述符只给创建者用户全权、Everyone 只读，客户端以写方式打开时受限 SID 检查不过；DSH 同样有这个限制（dsh-sandbox-windows-acl README “Piped stdio capture is impossible”）。stdio 为 inherit / ignore 的子进程不受影响。shell 输出含 `spawn EPERM` 时提示模型申请升权。
7. **独立开关，缺省关闭（2026-11-01，工具权限设计方案 §9.9，用户 m12907 定论）**：sandbox 插件 `Meta.Default = false`，在 `~/.ybase/profile.toml` 写 `[[plugin]] name = "sandbox"` / `enabled = true` 开启。关闭时 shell / MCP stdio / 钩子不加沙箱，shell 走普通权限判定（`shell.exec` 权限项，workspace 档缺省 allow，此时命令只按文本匹配，**不构成边界**，`ybase mode show` 会如实标注）；开启时沙箱内自动执行，申请越界仍每次单独确认。缺省关闭的原因是第 6 条的缺口（只限写、仅 Windows、缓存与 node 管道问题）会让常用工具链失败，需用户知情后自选。
