### 1.1 基线与 02 的主要差异

1. 归口不同：02 把分发规则独立成框架 07、事件表放在框架 09 §3.2；基线把分发规则收进 M6 §4.4（F03），对外事件表收进 M4「事件」小节，M6 只列本模块收的事件（search、memory 订阅）。
2. 投递模型的措辞：02 写"独立的有界队列 + 独立投递任务"，基线落实为"独立的有界 channel + 独立投递 goroutine"（M6 §4.4），已是 Go 实现口径。
3. 跨进程订阅：02 §2 单列"值守层订阅"一节；基线 M6 §4.4 把它压成背压条目中的一句括注（共享宿主库只读游标、按谓词对 entries 增量轮询）。
4. 事件表：基线 M4 表比 02 §3.2 少了"会话驻留"类（SessionLoaded / SessionUnloaded / SessionSuspended / OwnershipLost）的单列行（M4 第 141 行之后未读，不确定是否在后文）；但现有代码 `events.go` 仍定义了 `session_suspended`、`session_unloaded`。
5. 订阅粒度：02 §1 列了"房间（v2）"；基线 M6 §4.4 已读部分未出现房间。
6. 运行期注册措辞：02 §1 先说"唯一可在运行期注册 / 注销的甲类点位"，紧接着又说点位表里"启动期注册、运行期可注销"——同一段自相矛盾；基线 M6 §4.4 与 M4 事件表（`plugin.<名>.*` 行）沿用"运行期可注册 / 注销"，没有收口。
7. 版本：02 §3.1 与基线 M4 信封都带 `v`，但都没写事件 `v` 何时升、字段如何增删；02 §5 只给"未知事件类型客户端直接忽略"一条，且是针对客户端协议。现有代码 `Event` 结构里没有 `v` 也没有 `at`。

## 4. 推荐方案

### 4.1 接口（Go）

```go
type Event struct {
	V       uint16
	Kind    string          // turn_start / item_appended / text_delta / ...
	Session string
	Seq     int64           // 会话内单调；durable 类 = 日志下标，ephemeral 类 = 0
	At      int64           // Unix 毫秒
	Data    json.RawMessage
}

type Filter struct {
	Session string   // 空 = 全部
	Kinds   []string // 空 = 全部
}

type EventBus interface {
	// Subscribe：易失通道。sc 结束自动注销；队列满即断开，Closed() 给出断点 seq。
	Subscribe(sc *Scope, f Filter, buf int) Subscription
	// Follow：先从存储回放 (after, 水位]，发 Synced，再无缝转实时。只对 durable 类事件有效。
	Follow(sc *Scope, session string, after int64, f Filter) Subscription
	Publish(ev Event) // 只由宿主在 checkpoint 提交后调用
}

type Subscription interface {
	C() <-chan Event
	Closed() (lastSeq int64, reason error) // 断开原因：overflow / scope_done
}
```

### 4.2 Follow 的无缝衔接

1. 先挂实时订阅，缓存到达的事件；
2. 从存储读 `(after, W]`，W = 读取开始时的日志水位，逐条发出；
3. 发 `Synced{W}`；
4. 放出缓存中 `seq > W` 的事件，之后直通实时。

断开后订阅者用 `Follow(after = lastSeq)` 重连即可补齐。审计、轨迹导出、搜索索引一律用 `Follow`；界面用 `Subscribe` 加断线时 `Follow` 补。

### 4.3 P0 事件表

| 类 | 事件 | durable |
|---|---|---|
| 会话 | `session_created` / `session_opened` / `session_closed` / `session_deleted` / `session_idle` | 是（idle 否） |
| 回合 | `turn_start` / `turn_end`（带结束原因、unconsumed） | 是 |
| 条目 | `item_appended` / `truncated` / `config_changed` / `ext_changed` | 是 |
| 模型 | `step_start` / `text_delta` / `reasoning_delta` / `stream_reset` / `model_call_finished` | 否 |
| 工具 | `tool_start` / `tool_progress` / `tool_end` | 否（结果本身经 item_appended 落库） |
| 人工 | `human_requested` / `human_resolved` | 是 |
| 系统 | `error`（插件失败、订阅断开等） | 否 |

durable 类事件都能从存储重建，所以 `Follow` 可以回放它们；ephemeral 类只给界面。

## 5. 待拍板

| # | 问题 | 建议 | 理由 |
|---|---|---|---|
| D1 | 可靠消费者怎么读 | 总线提供 `Follow`（存储回放 + 无缝转实时 + `Synced` 标记） | opencode 同做法；把"可靠观察走存储"变成一个 API，插件作者不会误用易失通道 |
| D2 | 慢订阅者 | 队列满即断开并给出断点，不静默丢单条 | 静默丢会制造"看似完整"的错觉；断开后 `Follow` 补齐，语义清楚 |
| D3 | 信封 | 补 `v`、`seq`、`at`（**review-1 R4**：`seq` 取会话级单调 `sync_seq`，不等于条目 `idx`，撤销后不复用）；同 `v` 只加字段，改语义升 `v`；订阅者忽略未知类型与字段 | 原设计只有"未知类型忽略"一条，不够演进 |
| D4 | 是否支持同步 await 的监听器（pi 式） | 不支持。总线永不阻塞 actor；需要同步改会话的走钩子 | 守住"钩子与事件分开"的原则；pi 的做法会让一个慢监听器拖住回合 |
| D5 | 订阅生命周期 | 绑在作用域上（插件作用域 / 连接作用域） | 收口 02 §1 的自相矛盾；与 plugin-manager L1 一致 |
