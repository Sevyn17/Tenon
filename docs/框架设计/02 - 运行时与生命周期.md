# 02 运行时与生命周期

> 状态：草案（2026-11-01，按审查结论改为"定义 + 会话"模型）。索引见 [00 - 索引](<00 - 索引.md>)，术语见 [11 术语与内核对象](<11 - 术语与内核对象.md>)。

运行时只有两个运行概念：

- **定义**：智能体是什么。6 个内核字段（`id`、描述、模型、提示词、工具、`resident`）加 `[use.*]` 使用配置（权限在 `[use.permission]`），以及它声明要用哪些组件和资源。只读、带版本，**不运行**（03）。
- **会话**：智能体为一个或多个用户干活的执行现场。带信箱、历史、检查点、租约。**会话是唯一的执行单位**：会话内部串行，会话之间完全并行。

智能体没有"实例"，也没有自己的记忆。跨会话共享的东西（长期记忆、任务板、小组）都是组件的数据资源（05）。组件是全局单例，每次调用通过 `*Ctx` 拿到当前会话、租户和本轮触发者（04 4.4）。

## 2.1 定义

| 状态 | 进入条件 | 说明 |
|---|---|---|
| 已加载 | 定义来源返回一份定义包 | 来源可以是目录、数据库、代码（03） |
| 已校验 | 内核字段合法；每个 `[use.<组件>]` 都有已装组件且通过该组件的配置结构校验 | 不通过则拒绝加载，报出具体字段。T5 之前声明 `resident = true` 的定义报"未支持"（B23） |
| 生效 | 校验通过，记录整包内容哈希作为版本 | 新会话按最新版本构造 |
| 已替换 | 来源返回了新内容 | 新会话用新版本；已有会话继续用创建时的版本，直到会话结束或被显式迁移 |
| 已下线 | 来源删除了这份定义 | 不再创建新会话；已有会话可以跑完当前一轮，之后只读 |

模型不能创建或修改定义（B3）。应用可以随时通过来源接口增删定义。

## 2.2 会话

```
   新建（应用 / 信封发往 agent: / 派生）
               │
               ▼
 ┌────────► 活跃 ──── 空闲超时 ───► 休眠 ──┐
 │          │  │                           │
 └── 收信唤醒 ┼──┼───────────────────────────┘
            │  │
            │  ├── 预算用尽 ──► 预算挂起 ── Resume ──► 活跃
            │  │                   └── 超时 ──► 已中断
            │  └── 中断 ──► 已中断 ── 本轮收尾 ──► 活跃
            │
            │ 归档 / 删除 / 父会话回收 / 下线后只读
            ▼
          已关闭
```

| 状态 | 说明 |
|---|---|
| 活跃 | 进程内有它的对象，持有该会话的写租约。同一时刻只有一个节点持有，即单写者（A2） |
| 休眠 | 空闲超时后释放进程内对象和租约，只剩存储里的几行。空闲会话不占内存（2026-11-02 T2a-2 已实现：`store.SleepStore` + `Host.SleepAfter`） |
| 唤醒 | 信箱有新信封时，任一节点抢到租约即唤醒，从检查点恢复（2026-11-02 T2a-2 已实现：`open` 抢租约后迁移 `sleeping→active`，`Host.ScanOnce` / `ScanLoop` 兜底） |
| 预算挂起 | 守卫发现预算用尽：当前一轮停在检查点，不再调模型；补足预算或应用显式恢复（`Resume`）后从检查点继续，超时则转已中断 |
| 已中断 | 用户、Watchdog 或应用中断当前一轮：未完成的工具按 2.6 处理，信箱保留；会话回到活跃，可继续收信 |
| 已关闭 | 应用归档或删除；子会话随父会话回收。常驻定义的会话不回收（见下文"常驻"）。关闭时：未用的 `corr` 作废，并给请求方回错；子会话按所属树策略处理；信箱里剩下的信封拒收，发送方收到 `ErrSessionClosed` |

另有两个由应用显式发起的操作，都要求持有租约：

- **Fork** 从某个检查点复制出一个新会话（新 id、父链接指向原会话、历史截到该点），原会话不受影响。待回复表和信箱不复制，子会话不跟随新会话。
- **Rewind** 把本会话回退到某个检查点，之后的历史标记作废但保留可查。回退点之后签发的 `corr` 一律作废，这些 `corr` 对应的子会话按所属树取消。已执行的不幂等工具不会被撤销，回退后在上下文里注明。

会话创建时记录：所属定义及版本、租户、创建者、父会话（若是派生的）、`meta`（05 5.4）、算好的使用配置（06）。租约按会话 id 分片到节点，可以横向扩展；百万个会话里同时在推理的只有少数，资源只花在这少数上。

**会话的成员**：内核只记创建者。信箱接收任何通过守卫的发送者发来的信封，单人会话只是"发送者恰好只有一个"的会话，内核不区分两种。成员表、邀请、加入退出、角色由成员组件管理，通过 `Registrar.Guard` 放宽投递规则（联系规则以 08 8.2 为准）。v1 一个会话只支持创建者一个用户（B23），多人会话放在 T4。

**派生**：子智能体就是带父会话链接的子会话。所属树带重启策略（学 OTP 监督树）：子会话的一轮运行失败时，按 `restart`（重跑）、`give_up`（标记失败并告知父会话）或 `escalate`（上报给父会话或 Watchdog）处理，缺省 `give_up`。结果怎么交回父会话看调用方式：同步子智能体的结果是父会话那次工具调用的工具结果；异步工作组成员的结果是带 `corr` 的回信（13 13.1）。

**常驻**（D6，T5）：由定义声明 `resident = true`，会话本身不再有 resident 字段。每个租户只有一个该智能体的会话，固定 id `resident:<租户>/<名字>`，唯一性靠固定 id 保证，不算会话键的特例。创建者记为租户系统主体 `system:<租户>`，用户层使用配置不参与；别人能否联系它只看 `agent:` 的定义守卫。发往 `agent:<名字>` 时内核按这个 id 查找，存在就投进去，不存在就创建。常驻会话可以休眠，只是不回收；进程重启后有待处理信封才唤醒。Router、Watchdog 都是这种。常驻会话天然会收到同一租户里多个用户的消息，和 v1 的单用户限制冲突，所以和定时、外部事件入口一起放到 T5；T5 之前 `resident = true` 的定义报"未支持"（B23）。

### 租约与唤醒

- **租约带纪元（fencing）**：每次抢到租约，会话的 `lease_epoch` 加一。这一轮写入的历史、检查点、工具结果、信箱确认都带上这个纪元，存储只接受等于当前纪元的写入。旧节点因为卡顿丢了租约后醒来，它的写入会被拒绝，不会和新节点交叉写。（2026-11-02 T2a-1 已实现：`store.LeaseStore` 的 `AcquireLease` / `RenewLease` / `ReleaseLease` + `Checkpoint.Epoch`，sqlite 与 memstore 都在事务里校验纪元并返回 `store.ErrLeaseLost`；休眠与唤醒的竞态处理已随 T2a-2 落地。）
- **休眠与唤醒的竞态**：转入休眠分两步，先在持有租约的状态下检查信箱为空并把状态写成休眠，再释放租约；投递方先写信箱、再检查会话状态，看到休眠就发唤醒。两边都按"先写后查"做，所以"刚检查完信箱就来了信"时，要么休眠前的检查看见这封信，要么投递方看见休眠状态。唤醒请求按会话 id 去重。（2026-11-02 T2a-2 已实现：`SetSessionStatus` 条件迁移带纪元，检查信箱为空与写休眠在 actor 内串行；投递/唤醒走 `Host.open` 的租约获取。）
- **兜底扫描**："先写后查"在快照隔离的数据库上不保证两边一定互相看见。所以内核再周期性扫描"信箱有待处理的 `wake` 信封、状态却是休眠"的会话，补发唤醒。（2026-11-02 T2a-2 已实现：`Host.ScanOnce` / `Host.ScanLoop`，boot `StartOptions.SleepAfter` 与 `ybase.WithSleepAfter` 打开时启动；`wake` 信封语义仍随 T3。）
- **只有 `context` 时可以休眠**：休眠前的检查只看 `wake` 和 `control` 信封。`context` 信封留在信箱里，不触发唤醒，下次被别的信封唤醒时一起补上（13 13.3）。

## 2.3 消息发到哪

消息只发给会话，不发给智能体。投递目标如下（完整地址表见 11 11.3）：

| 目标 | 含义 |
|---|---|
| `session:<id>` | 投给已有会话。会话不存在或已关闭就拒绝（`ErrSessionNotFound` / `ErrSessionClosed`），不会自动新建（B18） |
| `agent:<名字>` | 和这个智能体新建一个会话，并把这封信封作为第一条消息，返回新会话 id。可带会话键 `key`：内核按 `(租户, 定义, 创建者, key)` 原子地查找或新建（B19）。`key` 只由应用（SDK）或组件（`Registrar.Mailer()`）设置，模型工具不能传；不带 `key` 每次新建。常驻定义（T5）投进它唯一的会话，靠固定 id 实现，不算会话键的特例（D6）。要求定义已存在、发送方通过联系守卫（08 8.2），否则拒绝 |
| `human:<用户>` | 发给人。缺省只能联系本会话的创建者、本轮触发者和成员组件登记的成员（D4，规则以 08 8.2 为准） |
| 带 `corr` 的回信 | 回复问人、工具确认、子会话结果，直接回到发出请求的会话 |

**`corr` 由内核签发**（D3）：会话发出请求（问人、派生、调别的会话）时，内核生成不可猜的随机 `corr`，写入待回复表 `session_pending`（新建，不复用 `session_requests`，那是模型请求日志）：`corr`、所属会话、预期回复方、`deadline`、是否已用，以及原请求那一轮的权限主体、`caps`、`origin`，回信触发的一轮据此沿用 `caps`。回信到达时依次核对：`corr` 存在、未过期、未用过、发送者 = 预期回复方。只收第一条，之后的同 `corr` 回信拒绝并记 `guard.denied`。调用方自己填的 `corr` 不被信任。

租户不写在地址里，取自调用上下文（07 7.3）；地址解析限定在本租户内（08 8.8）。

两种地址走两条不同的校验流程（会话存在、租户一致、会话状态、联系守卫、`corr` 核对；或定义解析、创建权限与配额、常驻与会话键查找、新建），详见 13 13.3。

内核不按"同一用户 / 同一资源"去猜信封该进哪个会话：猜错了会把消息送进别人的对话。外部事件、定时任务落到哪个会话，由入口规则或路由组件决定（例如订阅匹配后投到某个 `session:`，或投到 `agent:` 新建）。

## 2.4 一轮运行

```
空闲 → 取信（信箱，带租约） → 组装上下文 → 推理 ──┬─→ 回复 → 完成
                                       ▲        │
                                       │        ├─→ 调工具 ─→ 等结果 ─┐
                                       │        │                     │
                                       │        └─→ 等人确认 ──────────┤
                                       └────────────────────────────────┘
任一处可以：中断（用户、应用、Watchdog）→ 已中断；预算用尽 → 预算挂起
```

- **会话内部串行**：同一会话同一时刻只有一个推理在跑。推理期间到达的信封先排队。不打断正在进行的模型调用和工具执行，要打断就发 `control` 信封（B20）。
- **运行中插入**：只有和本轮**同一权限主体**的 `wake` 信封，才在下一次调模型前插入当前回合，不等整个回合结束。其他权限主体的信封、`origin = external` 的信封继续排队，本轮结束后另起一轮，否则它们会借用本轮的 `caps` 和预算。`notice` 进下一次状态更新，`context` 只排队。
- **处理方式**（B20）：每封信封带 `mode`，未填时按 `kind` 推出（11 11.1）：`wake`（空闲时开回合，忙时按上一条插入）、`context`（只是背景，不唤醒，下次开回合时附上）、`notice`（进下一次状态更新，见 12）、`control`（中断、关闭，内核直接处理）。
- **谁能发 `control`**：只有会话创建者、父会话、内核和登记了该会话的组件。其他发送者的 `control` 拒绝并记 `guard.denied`。多人会话（T4）里，本轮触发者也可以中断本轮。
- **合并格式**：到同一个边界时，待处理信封合并成一条用户消息，每条用 `<msg from at>` 标明发送者和时间（13 13.4）。
- **会话之间并行**：不同会话互不等待。并发总量由守卫按定义、租户、用户的并发上限控制，同时受模型供应商限速约束（08 8.4）。
- **按权限主体算**（B21）：每条历史条目带发送者 `from`。一轮只合并同一权限主体（同一触发用户、同一 `budget_ref`）的信封，例如同一用户派出的几个工作组成员的回信可以合并；不同权限主体按到达顺序分轮串行处理。v1 一个会话只支持创建者一个用户（B23）。每轮有一个主触发者，有效权限和记账按它算（08 8.3、8.4）；`*Ctx.Trigger()` 返回主触发者，`Envelopes()` 列出本轮合并的全部信封。回信（`reply`）触发的一轮，`caps` 沿用原请求那一轮，不被回信方压低；`origin` 照常合并，任一封是 `external`，本轮就是 `external`。
- 等工具、等人确认不占推理：长工具可以异步，`start` 立即返回，结果作为新信封投回信箱。
- 预算和权限由守卫在每次调模型、调工具前检查（08）。

## 2.5 会话上下文与跨会话读取

内核只有一种"记忆"：会话上下文，即历史、检查点和压缩后的摘要。它天然隔离，一个会话读不到另一个会话。

跨会话读取只有三条显式的路，都经过组件或守卫：

1. **记忆组件**：从一个会话提取内容存成组件数据，另一个会话再召回。分区（用户、租户、智能体、会话）和召回策略由组件决定；建议缺省在有多个成员的会话里不召回个人分区，除非定义里显式打开。
2. **共享资源**：任务板、小组等数据，多个会话一起订阅（05、04）。
3. **读别的会话历史**：作为工具提供，守卫检查本轮触发者是否有权访问目标会话。

多个智能体加多个人的群聊不放进内核：做成"小组"资源，每个参与的智能体在里面有自己的会话，通过订阅收消息。现有 workgroup 就是这个形状。

## 2.6 检查点与崩溃恢复

学 Temporal：每一步的结果先落库，再推进。

| 步骤 | 落库内容 | 崩溃后 |
|---|---|---|
| 收信 | 信封进信箱表，按 `id` 幂等 | 不丢、不重复 |
| 取信 | 带租约领取，处理完确认；确认带租约纪元。运行中插入的信封，和本次调模型前的检查点在同一事务里确认 | 租约过期后别的节点重新领取；旧节点的确认因纪元不符被拒 |
| 推理 | 模型请求和响应写入会话日志 | 已完成的推理不重跑；未完成的重发 |
| 调工具 | 调用前写 `tool_results`（状态 pending、参数哈希），完成后写结果 | 已完成的直接用结果；未完成的按工具的 `Idempotent` 声明处理（04 4.2）：幂等的重跑，不幂等的标记"结果未知"交给模型判断 |
| 外发 | 一轮内产生的外发信封、待回复登记（`corr`）和检查点在同一事务写入发件箱 | 不会只发了信封没记检查点，也不会记了检查点漏发 |
| 投递 | 投递器把发件箱里的信封搬进对方信箱 | 按 `id` 幂等，重搬不重复 |

现有代码已经有其中大部分：`session_inbox` 先落库再确认、`tool_results` 带 `status` 和 `deadline`、`session_entries` 有序追加（[schema.go](<../../core/store/sqlite/schema.go#L31-L62>)）；插入消息的确认也已经和检查点同事务。目标态要补的是会话级租约（含纪元）、发件箱和投递器、待回复表 `session_pending` 的签发与核对、工具的幂等声明。按 key 查或建、跨会话投递超出单会话分区事务，由 `Store` 的 `FindOrCreateSession` 原语做（05）。

## 2.7 组件在哪里介入

组件不按"级别"挂钩子，只有两种方式（B7，详见 04）：

- **中间件**：同步，包在内核固定点位外面，可以改行为或拦截。点位有 `SessionOpen`、`Deliver`、`Turn`、`Context`、`ModelCall`、`ToolCall`（04 4.3）。
- **事件**：异步，只读。会话和一轮运行的每次状态变化都有对应事件（`session.created`、`session.idle`、`turn.done` 等，完整列表见 07 7.5）。

定义校验由组件的配置结构完成（06 6.2），需要额外检查的实现 `Validator` 接口（04 4.2）。压缩由 compact 组件通过 `Turn` 中间件做。
