# 01 总览与边界

> 状态：草案（2026-11-01）。索引见 [00 - 索引](<00 - 索引.md>)。

## 1.1 框架是什么

框架是一个 Go 写的智能体框架：一个 Go 库（SDK）加一组标准模块（A15）。应用引用框架，用代码装配组件、加载智能体定义，就能得到一个能收消息、调模型、调工具、存状态、出故障后能恢复的智能体运行时。

类比 Web 世界：

| | Web 框架 | 智能体框架 |
|---|---|---|
| 处理对象 | 短请求，处理完就结束 | 长时间运行、有状态的智能体；一轮运行可能持续半小时，中间等工具、等人 |
| 开发体验学谁 | — | FastAPI / Django：类型声明生成校验和文档、组件自带数据和配置、约定优于配置、自带测试工具 |
| 运行时学谁 | — | Erlang/OTP（会话 + 信箱 + 监督树）、Temporal（每步落检查点，崩溃后从断点接着跑） |

## 1.2 核心加模块（B14）

```
应用（桌面版、客服、电商、SaaS……各自独立的项目）
  决定：用哪些模块、加载哪些定义、数据存哪、配置从哪来、界面长什么样
────────────────────────────────────────────
模块（SDK 里的 Go 包，可选用、不用或重写；tenon.Default 是预设组合）
  上下文、会话与消息（单聊渠道、工作组、子智能体、群聊、定时）、
  fs、shell、memory、permission、budget、compact、members、watchdog……
────────────────────────────────────────────
扩展点（04 的点位、Registrar、资源与订阅、*Ctx）＝ 内核对外的全部接口
────────────────────────────────────────────
核心 = 智能体运行时（不可替换）
  定义 · 会话 · 信封 · 资源 · 步进循环 · 守卫 · 上下文组装器 · 模型调度 · 存储原语接口
```

划分规则：涉及并发、持久化、安全的放核心（例如运行中插入消息、`corr` 核对、会话键原子查建）；只是"消息从哪来、投给谁、存在哪"这类策略的放模块。标准模块只能通过公开扩展点实现，用户自己写的模块和官方模块拿到的能力相同。

"模块"是 SDK 包和文档的分组单位，一个模块里可以有几个组件（组件是实现 `Component` 接口、在装配时登记的单元，04）。例如群聊模块含小组资源和 IM 渠道组件。

| 模块 | 包 | 内容 | 进 `tenon.Default` | v1 |
|---|---|---|---|---|
| 上下文 | `tenon/context` | 时间、待办、AGENTS.md、技能目录、权限档位等状态与快照提交（12） | 是 | 是（T2b） |
| 单聊渠道 | `tenon/chat` | 网页 / IM 私聊 / 客服，会话键路由（13） | 是 | 是（T3） |
| 子智能体、工作组 | `tenon/agent` | 派生子会话、成员回信（13） | 是 | 是（T1b 改用定义模板，T3 改走信封） |
| 定时与事件 | `tenon/scheduler` | 后台任务完成等事件（13）；定时、webhook 入口和常驻会话在 T5 | 是 | 事件部分是；定时、webhook 否（T5） |
| 群聊 | `tenon/group` | 小组资源：原始记录、@ 唤醒、背景补齐、转人工开关（13） | 否 | 否（T4） |
| 其他 | `fs`、`shell`、`memory`、`permission`、`budget`、`compact`、`members`、`watchdog` | 各自模块篇落地时补 | 视模块 | 视模块 |

v1 范围（B23）：核心做到 T1a–T3（见 09 的总表），模块含单聊渠道、子智能体与工作组、事件三类。v1 一个会话只支持创建者一个用户；常驻会话、定时与外部事件入口在 T5，群聊、转人工和多人会话在 T4。T5 之前 `resident = true` 的定义加载时报"未支持"。

外部插件（Node / Python 进程，A11）通过扩展进程协议接到组件层，能力比组件小，跑在隔离进程里（04）。存储实现（SQLite、Postgres……）不是组件，由应用通过 `tenon.WithStore` 提供（05 5.5、07 7.2）。

## 1.3 框架做什么、不做什么

| 框架做 | 框架不做（交给应用或模块） |
|---|---|
| 按定义创建会话，驱动"收信 → 推理 → 调工具 → 回复"的循环 | 界面、服务进程、部署形态 |
| 每步落检查点，崩溃恢复 | 业务含义："这是客服"、"按用户隔离记忆"、"IM 群聊" |
| 信封投递、地址解析、休眠与唤醒 | 应用的业务数据：订单、商品、用户资料 |
| 守卫：工具权限交集、联系范围、跳数、预算执行 | 具体的数据库、具体的模型协议、具体的沙箱 |
| 存储原语接口，组件数据集合 | 端侧守护进程、SaaS 节点调度（A15） |
| 组件装配、中间件链、事件 | 读全局配置文件、写固定目录、假设有终端 |

判断标准：所有应用都要、且运行时离不开的，进核心；只有部分应用要的，做成模块；只有一个应用要的，应用自己写组件或用 `meta` / `x.`。

## 1.4 核心概念

| 概念 | 含义 | 详见 |
|---|---|---|
| 智能体 / 定义（`tenon.Agent`） | 智能体就是它的定义：6 个内核字段（`id`、描述、模型、提示词、工具、`resident`；`resident` 到 T5 才支持）加上挂哪些组件和资源（`[use.*]`，权限在 `[use.permission]`）。只读、带版本（整包内容哈希），不运行，没有实例，也没有自己的记忆 | 03 |
| 会话 | 智能体为一个或多个用户干活的执行现场，唯一的执行单位：内部串行，会话之间并行 | 02 |
| 一轮运行 | 一次"收信 → 推理 → 调工具 → 回复" | 02 |
| 地址 | 能收信封的东西都有地址：会话 `session:`、智能体入口 `agent:`（新建会话；带会话键时按（租户, 定义, 创建者, key）查到已有会话就投进去）、人 `human:`、资源、远端 `remote:` | 11 |
| 信封 | 消息的统一格式，字段以 11 的信封表为准；`from`、`origin`、`hop`、`caps`、`budget_ref`、`trace` 由内核写入 | 11 |
| 信箱 | 会话的收件队列，先落库再确认，按信封 id 幂等 | 02 |
| 资源 | 有地址、可被订阅的共享对象，由组件登记类型，如小组、看板、外部线程。记忆不是资源，是 `memory` 组件的数据 | 11 |
| `meta` | 应用挂在会话上的键值对，模型改不了；租户、用户不放这里 | 05 |

协作原则：会话内部串行、会话之间并行（B9，取代 04 草案 A1、A2、A12 的实例模型）；人也是地址（A3）；不做硬性流程编排（A5）；没有组合智能体（A6）；小组是资源（A7）。

## 1.5 开放与封闭

框架的稳定性来自"核心封闭、扩展位开放"：

| 封闭（只有框架能改，走版本） | 开放（应用和模块随意用） |
|---|---|
| 定义的 6 个内核字段 | 定义里的 `[use.<组件>]`、`[x.<应用>]`、定义包里的任意文件 |
| 内核数据表的结构和字段含义 | 会话上的 `meta`；组件的数据集合 |
| 信封字段、生命周期状态机 | 中间件链、事件订阅 |
| 存储原语接口 | 存储实现（SQLite、Postgres、MongoDB……） |

应用遇到扩展位不够用的情况，说明框架缺一个通用能力。这时应提成框架需求、出新版本，不在应用里改框架。
