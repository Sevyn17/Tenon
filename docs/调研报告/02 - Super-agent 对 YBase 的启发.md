# Super-agent 设计探索：对 YBase 的启发

> 依据：[01 - Super-agent 设计探索](<01 - Super-agent 设计探索(DeepSeek Harness 团队).md>)（原文 2026-11-01 抓取）。

> 状态：调研结论草稿，未经用户确认，不改变任何已定稿设计。

## 一、原文要点（一句话版）

Super-agent 是跨会话持续存在的 Agent。五个模块：

1. 双层架构：常驻 Router 只负责对人交互、分派和全局记忆；Worker 在隔离上下文里干活，不直接对人说话。
2. 事件驱动：先用程序规则过滤，再用 LLM 语义过滤；Thread 被 Worker 订阅后，后续事件由程序直通，不再经过 Router。
3. 面向人的交互：异步 ReAct（`start()`/`stop()`，长任务立即返回"已启动"，结果作为事件回灌）；按信道调整输出（IM 简短，GitHub 完整）。
4. 存算分离：云端无状态计算 + 会话入库；执行环境留在原机器，只装轻量 daemon。
5. Watchdog：独立会话，定时检查 Worker 是否真有进展。

实验结论：同样的 ~20 个并发请求，Super-agent p95 为 15.7 分钟，单会话加 Subagent 为 29.5 分钟（中性提示下 5 次都没有用 Subagent）。去掉订阅直通后，Router 决策增加约 30%，读缓存 token 从 2323 万升到 3177 万（约 +37%）。Router 单会话批处理在 40 条/分钟时，每个决定的分摊推理时间从 6.4 秒降到 1.6 秒。

## 二、与 YBase 现状的对照

| 原文机制 | YBase 现状 | 差距 |
|---|---|---|
| Worker 是隔离会话 | subagent、workgroup 成员都是持久的普通会话，`parent_id` 关联 | 已具备 |
| Worker 结果作为事件回灌 | workgroup 的 `team_spawn` 异步，结果作为 input 投递领导 inbox，崩溃后 `Group.Recover` 补投 | 已具备，且有持久化（比原文描述更严谨） |
| 异步 start/stop | shell 有后台任务；`subagent` 工具是同步的；`team_spawn` 是异步的 | 子智能体缺异步形态 |
| 事件总线、回放与补齐 | `bus` 已有，`Follow` 支持回放加实时 | 只面向前端，没有"外部事件源" |
| 外部事件触发 | `scheduler`、`a2a` 仅📋；无 IM / GitHub / 邮件 / CI 入口 | 缺口最大 |
| 订阅直通 | 无 Thread 概念；成员消息走 `team_send` | 无 |
| Router 与 Worker 分层 | 领导会话既分派又可自己执行，工具不受限 | 无专用 Router 形态 |
| 上下文 Inline & Spill | toolhub 有"结果溢出"和 `tool_search` | 已有雏形，未扩展到事件与引用图 |
| 存算分离 | 内核与会话在同一进程，存储可换后端（`store-postgres` 📋） | 暂无远端 daemon |
| Watchdog | 无；工作组只有 30 分钟 `MemberTimeout` | 只有超时，没有"进展判断" |
| 安全（原文 8.4） | permission、sandbox、redact 已有 | 事件驱动会引入不可信输入，需要新增信任模型 |

## 三、对 YBase 的启发（按价值排序）

### 1. 把 Super-agent 做成"一组插件"，而不是改内核（最大的结论）

YBase 的原则是"内核只提供机制，影响会话内容的一律做成插件"（[00 - 总体架构](<../90 - 归档/00 - 总体架构.md>) 第一节）。原文的 Router、事件过滤、Watchdog 都影响会话内容，因此天然属于插件。内核需要补的只是通用机制：

- 外部事件进入 inbox 的入口（目前只有人的 `Send` / `Note`）。
- 定时触发（对应已规划的 `scheduler`）。
- 这些机制已有 inbox item id 幂等、`Source` 字段，大部分基础已在。

这与原文自己的结论一致：它的原型也是 DSH 的一个插件（`dsh-superagent-prototype`），不是内核改动。

### 2. 优先做：事件进 inbox + scheduler（成本低，收益确定）

- `scheduler`（📋）可以最先落地，用 `Source=scheduler` 向指定会话投递定时消息。它同时是 Watchdog 的前置条件。
- 随后做一个"事件源"扩展点：外部进程通过现有的扩展进程协议（[00 - 总体架构](<../90 - 归档/00 - 总体架构.md>) 第四节第 2 档，已规划 `事件订阅`）把 IM / GitHub webhook 转成 inbox 消息。这个设计与原文的 Trigger 一一对应，不需要新协议。

### 3. subagent 增加异步形态

原文 4.1 的核心：长任务不应阻塞前台对话。YBase 的 `subagent` 同步阻塞父回合，只有 `team_spawn` 是异步的。建议评估把 `subagent` 增加 `async` 参数，或让 `team_spawn` 的"无看板轻量模式"覆盖这个场景。`team_spawn` 已有的"结果经 inbox 回灌 + 崩溃补投"可以直接复用，不必重新设计。

同时补一个 `stop` 类动作：目前工作组"无成员间直接中断（interrupt）"，已列为缺口，原文也明确要求 `stop()`。

### 4. 工作组可演化出"Router 形态"的领导

原文的价值判断：让 Router 不执行具体工作，系统层面强制分工，比依赖提示词让模型"自觉委派"稳定得多（中性提示下模型 5 次一次都没委派）。对 YBase 的含义：

- 工作组领导可以提供"仅分派"配置：限制领导只保留 `team_*`、看板、对人沟通工具，去掉 shell、写文件。这个限制在 YBase 里可以用现有的权限与工具作用域实现，不需要新机制。
- 这能避免领导因为"任务很小"而自己动手，导致被后续消息反复打断。

### 5. 订阅直通：先理解成本，再决定是否做

直通的实测收益是省 token（Router 决策 -30%，读缓存 -37%），而不是提升速度或质量。YBase 现在没有 Thread 概念，也没有多个外部事件流，做直通的前提（事件量大）还不存在。建议放在事件入口落地之后，用真实负载再评估，当前只在设计里预留"事件带 thread 标识"的字段即可。

### 6. 上下文：Inline & Spill 与 Chain of Recall

- toolhub 的"结果溢出"已经是 Spill。可以把同一原则写进事件注入规范：注入"ID + 摘要 + 邻近内容前 N 字"，全文通过工具取回。
- 给会话、成员、任务看板条目等对象都赋唯一 ID，并在工具返回中内联下一跳的 ID 与摘要。YBase 的会话 id 已是 `<父>/m-<名>`、`<父>/sub-<末8位>` 这种可追溯形式，`task_list` 也有 id，具备做引用图的条件。几乎没有新增成本，值得在工具返回格式上统一。

### 7. Watchdog 作为可选插件

依赖 `scheduler`。内容是一个独立会话，定时读取工作组看板和成员会话状态，判断是否停滞或偏离目标。YBase 的看板有 `rev` 和 `status`，可读信息足够。优先级低于前几项，因为它的前提（长时间无人值守运行）还没有场景。

### 8. 暂不跟进的部分

- **存算分离 / 远端 daemon**：YBase 现阶段是本地编程助手，桌面端和网页接入已有计划（Wails v3、api-server）。原文自己也承认云端 Agent Loop 加端侧 daemon 的信任模型是开放问题（8.4）。除非 YBase 明确要做云端常驻，否则不做。
- **Router 水平切分、长程记忆、A2A 边界**：原文也未解决，保留 `a2a`（📋）即可。
- **多信道输出风格（IM ≤100 字）**：属于具体适配器的 prompt 约定，等有 IM 入口时再定。

### 9. 必须先想清楚的风险

事件驱动让 Agent 接触不可信输入（群聊内容、PR 评论、邮件）。进入前需要明确：

- 事件来源白名单与"只响应显式请求 / 候选 / 忽略"分级（原文 3.1 的 Fast Path）应做成程序规则，不要只靠提示词。
- 来自外部事件的内容默认低信任，不得直接触发高风险工具（Write / 执行），应走现有 permission 确认。
- 凭据不进入模型上下文（`redact` 插件已有写入守卫，可扩展）。
