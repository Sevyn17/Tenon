## 3. 竞品对比

读过的文件：

- DSH：`refer/deepseek-harness/packages/dsh-session/README.zh.md`（只读 README，未读编译后 JS）。
- Codex：`refer/codex/codex-rs/core/src/thread_rollout_truncation.rs`（开头约 60 行）、`refer/codex/codex-rs/core/src/compact.rs`（§54–§90 附近的 `SUMMARY_PREFIX`、`CompactedHistoryMetadata`）。

| 维度 | 本方案（M4 / 03） | DSH | Codex | Claude Code / OpenCode |
|---|---|---|---|---|
| 存储形态 | 日志（条目）+ 头部覆盖写 + 幂等记录 | 仅追加的类型化事件日志，模型历史、transcript、持久化都"从这条流派生" | rollout：`RolloutItem` 序列（`ResponseItem` / `Compacted` / `EventMsg` 等） | JSONL 追加日志（未核实） |
| 请求快照 | 无；恢复时重建请求（本轮新增请求记录） | `request/header` "存储非历史请求封装的完整规范快照"；`developer/message` 用 `headerSeq` 引用更早请求头 | 未在读到的范围内看到 | 未核实 |
| 压缩 | Compaction 条目追加在末尾，取代 `[0, upto)` | 压缩"在活跃对话中隐藏被取代的条目，但不会删除它们" | `RolloutItem::Compacted` 带 `replacement_history`；元数据含 `compaction_model_hash`，注释称保证 "live and persisted histories remain identical" | 摘要替换上下文（未核实） |
| 撤销 | `rewind(to)` 物理截断 `[to, end)` | README 未见截断，替换用 `{ op: 'replace', startSeq, endSeq }` | 追加 `ThreadRolledBack { num_turns }` 标记，读取时按回合回退，不改原始流 | 未核实 |
| fork | 02 内部不一致（压缩点起 vs 完整前缀） | 复制"包含切点的精确事件前缀"，开放步骤补错误结果并以 `forked` 关闭；`inheritedEventCount` 区分继承与自有 | 未读 | 未核实 |

可借鉴点：

- DSH 的 `request/header` 与本轮"请求记录"思路一致：把实际发出的请求封装落盘，而不是恢复时重算。
- Codex 记 `compaction_model_hash`，与 E41"Assistant meta 记配置哈希"同一用途：事后能追溯当时用的配置。
- Codex 与 DSH 都不物理删除历史（标记回退 / 替换投影）；本方案 rewind 物理截断，更简单但不可追溯。本地 CLI 先保持截断，作为待拍板 D5。

## 4. 推荐方案

范围：本地单用户、单进程。以现有 `kernel/session` 为底，只列差异，不重写接口。

### 4.1 不动的部分

- 返回形态 `([]Change, *Need, error)`、`Need` / `Change` 结构、`WithClock` / `WithIDs` 注入。
- `restore.go` 的状态一致性检查（WaitingModel 须有回合与请求 id、Idle 不残留请求 id 等）。
- `newModelNeed` 内部生成 `PendingModelRequestID` 并随 `ModelNeed.RequestID` 返回：保持现状，只改文档（E31）。

### 4.3 关键规则（本地版）

- 持久化三分 + 一：日志（追加 / 截断）、头部（每次停顿覆盖写）、幂等记录（工具管理器写，按调用 id）、请求记录（宿主写，按 `request_id`，请求体在 BlobStore）。
- 请求记录不新增插槽：SessionStore 扩 `PutRequest` / `GetRequest` 两个方法（08 §1）。
- 写入顺序沿用 03 §8.2，并补宿主侧时机：**每次模型调用前**，请求记录与含 `pending_model_request_id` 的头部同事务写入，之后才发出调用。
- rewind 保持物理截断；存储层把被截区间移入归档段，轨迹导出从归档段读（D5 修订，不依赖事件）。
- 恢复：WaitingModel 先查请求记录，按外壳 + 前缀区间 + 后缀重组、校验 `final_hash`，命中则原样重发，不符则换新 attempt key（review-1 R1 / R3）；WaitingTools 沿用原调用 id，从幂等记录取回已完成结果。
- R23 工具冻结、ext 命名空间、来源计算全部由宿主执行，内核不内置白名单。

### 4.4 review-1 补充（2026-10-28）

- **R3**：内核的 need id（`PendingModelRequestID`）恢复后沿用，回交内核只认它；发给厂商的是 attempt key = need id + 计划项序号，由模型管理器生成，换计划项即换。内核不改。
- **G1**：`SystemBlock` 加 `Source` 字段（产出该段的插件 / 来源，如 `agents-md`、`skill-catalog`），内核原样透传、不解释，供上下文组成统计。
- 会话形态：`origin` 取 `new / fork / side / subagent / member`；fork 记 `fork_upto`。分支树由 `parent_id + fork_upto` 还原。

## 5. 已定（2026-10-28）

判断依据：内核纯净（无 IO、无点位、只解释自己的结构）；一个事实只存一处；冻结接口越少越好（扩已有插槽不新增）；历史可追溯但由观测层负责；内存视图与存储分层表述。

|---|---|---|---|
