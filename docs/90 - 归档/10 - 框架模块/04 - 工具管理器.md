## 4. 推荐方案

### 4.1 接口（Go）

```go
type Tool interface {
	Meta() *ToolMeta
	Call(ctx context.Context, cx *Cx, args json.RawMessage) (ToolOutput, error)
	Cancel(ctx context.Context, cx *Cx, callID string) // 默认空实现（嵌入 NopCancel）
}

type ToolMeta struct {
	Spec     session.ToolSpec
	Risk     Risk          // Read / Write / Dangerous
	Parallel *bool         // nil = risk == Read
	Timeout  time.Duration // 0 = 默认 120s
	Deferred bool          // 可用但默认不显露（§4.2）；动态来源可整包标记
	Attrs    map[string]any
}

// ToolHub 由框架装配；插件经 SetupCx.Tools() 注册。
type ToolHub interface {
	RegisterSource(src ToolSource) error
	SpecsFor(agent *AgentDef) (Toolset, error)               // 会话创建：展开、冻结可用集
	Execute(rc *Scope, cx *Cx, calls []session.ToolCall) Run // 读写锁并行（D6）：单一分发者按调用顺序取锁；结果按调用顺序产出
	Submit(sessionID, callID string, token string, out Content) error // 挂起回传
	Confirm(sessionID, callID string, approve bool) error
}

type Run interface {
	Next() (Result, bool) // 按调用顺序；内部可乱序完成
	Stop()                // 级联 Tool.Cancel，遵守 finish_grace
}
```

- `Execute` 产出的顺序就是内核要求的提交顺序，宿主拿到一个交一个，不在宿主里重排。
- 工具不自己截断、分页：入口环节统一存工件（M5 实现自由第 1 条）。

### 4.2 工具列表：冻结可用集，按需显露（D1）

| 概念 | 内容 | 何时确定 | 能否变 |
|---|---|---|---|
| 可用集（allowlist） | 智能体定义 ∩ 已装配插件，展开后的全部工具 | 会话创建 | 不能（R7 的安全语义保留：权限、explain、审计都以它为准） |
| 显露集（`config.tools`） | 发给模型的工具定义 | 创建时 = 可用集中 `Deferred = false` 的部分 | 只增不减，只在步边界经内核 `SetConfig` 追加 |

规则：
1. **默认不延迟**。只有当可用集里工具定义的估算 token 超过预算（默认：最小上下文窗口的 10%）时，才把动态来源（MCP 等）标为延迟；内置核心工具永不延迟。小配置下行为与原 R7 完全相同。
2. 延迟工具只以"名称 + 一句描述"出现在系统提示的目录段里（有长度上限）。模型调用内置 `tool_search(query | names)` 拿到完整定义，tool-hub 在本步结束时经 `SetConfig` 把它们追加进显露集。
3. 追加只在步边界生效，内核 `validateCalls` 仍以显露集校验——未显露的工具被调用时按"工具不存在，请先用 tool_search 加载"回错误，不绕过校验。
4. 缓存：追加会让缓存在 `tools` 处断一次。适配器若支持厂商原生的延迟加载（例如 Anthropic 的 tool search），由适配器映射为原生能力，避免断缓存；不支持的就接受一次性的缓存失效。
5. 动态来源的变化依旧只影响新会话；会话内的可用集不变。

机制复用内核已有的 `SetConfig` 暂存到步边界的路径，但**内核要小改一处**（lead 核实 `kernel/session/core.go` `applyConfigPatch`：`ConfigPatch` 现在只有 `Model` / `Params`）：`ConfigPatch` 增加 `AddTools []ToolSpec`，步边界追加且按名去重、只增不减；宿主白名单只为 tool-hub 开放这一项，外部命令仍不能改。内核仍不感知"可用集"，可用集归 tool-hub。

## 5. 定稿结论（2026-10-28，用户确认；lead 复审后修订 D5 / D6 / D7）

复审修订：
- **D5 补两条约束**：① 子调用 id 由父调用 id + 序号确定性派生（`<parent>#<n>`），崩溃恢复后同一子调用命中同一幂等记录，不重复执行；② 子调用结果写 ToolResultStore（不进会话日志，只有 `run_code` 的最终结果进日志），轨迹导出从这里读，满足"可靠观察走存储"。`run_code` 本身 risk = Dangerous（代码可执行任意子调用组合），每个子调用另按自身 risk 过 Guard。
- **D6 补顺序规则，并修正 session-host H15**：锁由单一分发者**按调用顺序**获取（不是各 goroutine 抢锁），否则顺序语义不成立。挂起中的调用（等确认 / 等回传）**保留它的顺序位**：排在它后面的调用一律等待。原 H15 写"挂起只阻塞其后的串行项、不阻塞已就绪的并行组"——复审发现这会让"先写后读"的读提前执行、读到旧状态，是错的；以本条为准，回改 session-host H15。代价：一个等确认的写会挡住同一步其后的只读调用；模型通常把依赖调用放在不同步，影响小，且正确性优先。
- **D7 增 `head_tail`**：`Attrs.preview` 取 `head`（默认）/ `tail` / `head_tail`（头尾各一段，中间注明省略量）；shell 默认 `tail`。
