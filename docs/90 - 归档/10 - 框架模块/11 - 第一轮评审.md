## 2. 逐条

### R1 请求记录平方增长

- 现状：每次模型调用存 Transform 之后的完整请求，sha256 内容寻址。每步请求都包含全部历史且互不相同，去重无效。50 步会话约存 1+2+…+50 ≈ 1275 条消息副本。
- 修正：按结构存，记录 = `{request_id, shell_hash, base_from, base_to, compaction?, suffix_ref, final_hash}`。
  - `shell`（system、tools、params、model）：内容寻址，几乎不变，自然去重。
  - 前缀：只记日志区间与压缩视图（`upto` + 摘要来自哪个条目或哪个 side_call 结果）。
  - 后缀：Transform 追加的消息，单独存（通常很小）。
  - 恢复时按三部分重组，重组结果的哈希与 `final_hash` 不符即换新 request_id（S7 不变）。
- 依据：DSH `request/header` 只存外壳，消息从日志派生。
- 代价：重组逻辑约百行；"模型可见 ⟺ 可重建"仍成立，且由 R2 的校验保证。

### R2 Transform 约束不落代码

- 现状：01 §3.2 规定"注入只追加末尾、tools 只能收窄、压缩是唯一替换前缀的例外"，代码层无校验。
- 修正：调度器在全部 Transform 之后、Guard 之前做一次结构校验：
  1. `Messages` 的前缀与基础请求逐字节一致（压缩层声明了 `compaction` 视图时，与 `BuildWithCompaction` 的结果一致）；
  2. `Tools` 是基础请求的子集；
  3. 违反即按 Guard 失败（FailClosed）处理，`explain` 与 OTel 记下是哪一层。
- 这一条同时是 R1 的前提：后缀能单独存，是因为前缀被强制不变。

### R3 两种 request_id 混用

- 现状：内核 `ModelDone(requestID, needID, …)` 要求 requestID 等于头部的 `PendingModelRequestID`；model-hub §4.2 又写"换计划项时请求体变了，换新 id 并更新请求记录"。照此实现，换计划项后回交给内核会被当成过期结果拒收。
- 修正：分两个 id。
  - `need request id`（内核生成，标识"这一步的模型需求"），恢复沿用，回交内核用它；
  - `attempt key`（调度器生成，= need id + 计划项序号，发给厂商做幂等 / 缓存键），换计划项就换。
  - 请求记录按 need id 存，记录里附各次 attempt 的计划项与 final_hash。
- 内核不改；只改 model-hub 文档与调度器实现。

### R4 事件 seq 撤销后重复

- 现状：event-bus D3 定 `seq` 会话内单调；data-contract §4.4 写"seq 就是条目 idx，截断后从新 log_len 继续"——撤销后同一 seq 会指向两条不同条目，`Follow` 断点续读会错。
- 修正：会话级单调 `sync_seq`（sessions 表一列，每次 checkpoint 递增分配），事件与 `Follow` 用它；`idx` 只作日志下标。08 原设计本来就有 `sync_seq`，恢复它即可。

### R5 配置两处内容寻址

- `session_configs(hash, body)` 存会话 config；R1 的 shell 也是 config 的一个视图。合并为一张 `session_shells(hash, body)`：头部的 config 与请求外壳都引用它。
