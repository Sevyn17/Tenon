## 3. 竞品对比

| 维度 | 本方案（04 / M4） | DSH（`dsh-agent-loop` README） | Codex（`codex-rs/core`，只看了结构） | Claude Code / OpenCode |
|---|---|---|---|---|
| 运行体 | 每会话一个 actor，命令队列 | agent 由 loop 驱动，`ctx.agents` 创建 / 恢复 | 提交队列 + 事件队列的 actor（未逐行核实） | 单进程会话循环（未核实） |
| 并行工具 | 连续 parallel 成组 | `maxParallelToolCalls` 限并发；独占调用保序 | 支持并行调用（未核实细节） | 支持只读工具并行（未核实） |
| 取消 | 保留半截正文，工具级联取消 | 保留已流式交付文本 | 未核实 | 未核实 |
| 崩溃恢复 | 头部 + 请求记录 + 幂等记录，按原 id 续跑 | 事件日志重放 | rollout 重放（未核实是否续跑在途调用） | 会话 JSONL 可续聊，在途调用不续跑（未核实） |
| 钩子 | create / restore / before_turn / after_turn | 插件订阅事件 + 服务替换 | 用户 hooks（未核实） | 用户 hooks：PreToolUse / PostToolUse / Stop 等（公开文档，未逐条核实） |

可借鉴点：

- Claude Code 的用户钩子是"工具前 / 工具后 / 回合结束"粒度，我们只有回合级钩子。工具前后由工具调用层（Transform / Guard）覆盖，能力等价；但给**用户**写脚本钩子的入口（类似 hooks 配置）可作为一个插件挂在工具 Guard 层，列入 P1，不改宿主。
- DSH 的独占调用保序与我们的"串行项"同义；并发上限可配置，采纳为 `CallPolicy.max_parallel_tools`（默认 8）。
- 我们在"在途调用按原 id 续跑"上比各家更严格，这是优势，保留。

## 4. 推荐方案

### 4.1 结构

```go
// SessionHost：进程内会话表 + 每会话 actor。
type SessionHost struct { /* sessions map[string]*actor; deps HostDeps */ }

type HostDeps struct {
	Store    SessionStore    // 插槽：日志 / 头部 / inbox / 请求记录（PutRequest/GetRequest）
	Results  ToolResultStore // 插槽：幂等记录
	Blobs    BlobStore       // 插槽：请求体、超大结果
	Models   *ModelHub
	Tools    *ToolHub
	Bus      EventBus
	Hooks    TurnHooks       // before_turn / after_turn，由插件管理器组装
	Agents   AgentStore
}

func (h *SessionHost) Create(ctx context.Context, agentID string, opts CreateOpts) (SessionHandle, error)
func (h *SessionHost) Open(ctx context.Context, id string) (SessionHandle, error) // 含恢复
func (h *SessionHost) Fork(ctx context.Context, id string, upto int) (SessionHandle, error)

// SessionHandle：只投递命令（外部有界、插件无界），不等回复；查询走 View。
type SessionHandle interface {
	Send(cmd Command) error // 外部队列满 → ErrBusy
	View() SessionView
}
```

### 4.2 关键规则（本地版）

- 回合：`before_turn`（Transform → Guard：Allow / Deny / Record）→ `core.Input` → checkpoint（running）→ `drive`。
- `drive` 每个 `Need::Model`：构造请求 → 走模型调用栈得到最终请求 → **checkpoint（头部 + 请求记录同事务）** → 发出。恢复时有请求记录即原样重发。
- `Need::Tools`：checkpoint → `ToolHub.Execute`（读写锁并行，单一分发者按调用顺序取锁，结果按序提交；tool-hub D6）→ 步边界。
- 回合结束：after_turn → checkpoint（idle）→ `TurnEnd`。
- 打开会话时 run_state = running 即恢复；`rt.recover` 超 3 次以 Failed 结束回合。
- 事件一律在 checkpoint 提交之后发布。

## 5. 定稿结论（2026-10-28）

用户决定把原 P1 并入 P0（见《01 - 路线图》）。D1–D5 按"宿主只保留最少机制、扩展走点位、一条路径不留特例"重新评估后定稿；§2 中标"P1"的条目（H3 挂起命令、H13 续写、H14 挂起、H18 suspended）一并进入 P0。

| # | 问题 | 结论 | 理由 |
|---|---|---|---|
| D1 | 命令集 | 全集：Send / Steer / Resume / Cancel / ToolResult / Confirm / Note / SetConfig / Compact / SetExt / Rewind / Close / Delete / Drain。只推迟 op_id 去重（H4） | 并入后权限确认、后台任务、子智能体都在 P0，挂起命令是它们的共同依赖；Drain 对应 CLI 正常退出（写 `rt.drained`，区分退出与崩溃） |
| D2 | inbox | 做，存本地 SQLite 的 `session_inbox`（data-contract D1 修订落盘位置）；Send 先落 inbox 再确认 | 回合中输入、补报 note、子智能体结果回交都走这里，一个机制覆盖三种来源 |
| D3 | 人工确认 | **改**：不做同步询问特例。Guard 返回 `Confirm` → 入口环节写挂起记录 → 发 `HumanRequested` → CLI 渲染提示、用户作答后投递 `Confirm` 命令 → 以原调用 id 重发 | 只有一条路径；等待确认时崩溃，恢复后仍在等确认；子智能体的确认可上交父会话，CLI / 桌面 / 远程同一机制。原倾向的"同步问"在 P1 并入后成了要拆的临时代码 |
| D4 | 两个进程打开同一会话 | 头部条件写（期望 `log_len`），失败即转只读 | 不引入租约；单进程 no-op Coordinator 的语义保持不变 |
| D5 | 用户脚本钩子（类 Claude Code hooks） | 不进宿主；做成插件，挂工具 Guard 层（工具前）、工具 Transform 返回侧（工具后）、after_turn（回合结束），P0 内交付 | 宿主仍只有回合级钩子；用户钩子是"把点位暴露给脚本"的一个插件，不是新机制 |
