# 工具权限设计方案（2026-10-31，用户已确认：m10253 / m10256 / m10257；第九节 m11015）

> 2026-10-31 23:30 重建：本文件被一次失败的脚本清空（未入 git），按会话记录与已实现代码重写。第一至八节内容与实现一致；措辞可能与原稿不同。

## 一、思路

- 工具只声明自己的**效果**（读、写、执行……），不各自决定要不要问。
- **档位就是一份配置文件**：按效果给出 allow / ask / deny，再加按工具覆盖、规则和沙箱级别。内置档位与用户自定义档位格式相同。
- 判定由权限插件完成；会起子进程的工具（shell、MCP stdio 服务、用户钩子）一律在档位指定的沙箱里运行。
- 新会话缺省档位为 `workspace`（工作区允许）。

## 二、工具效果

| 效果 | 含义 | 工具 |
| --- | --- | --- |
| read | 只读工作区或会话数据 | read_file、grep、glob、list_dir、job_output、task_list |
| write | 改工作区文件 | edit、write_file |
| exec | 起子进程 / 结束进程 | shell、job_kill |
| network | 访问网络 | web_fetch、web_search |
| interact | 只和用户交互 | todo、ask_user |
| spawn | 创建子智能体 | subagent、team_spawn |
| collab | 改协作状态 | team_send、task_create / claim / complete |
| orchestrate | 编排其他工具（子调用各自再判定） | run_code |
| external | 外部服务，效果未知 | MCP 工具（按 trust 调整，见第五节） |

效果写在工具 `Attrs[toolhub.AttrEffect]`（`core/toolhub/attrs.go`，`EffectOf` / `WithEffect`）。

## 三、档位就是配置文件

### 3.1 档位文件格式

```toml
name = "工作区允许"          # 显示名
base = "workspace"           # 可选：继承的档位
description = "…"

[effects]                    # 效果 → allow / ask / deny
read  = "allow"
write = "allow"
exec  = "allow"
network = "ask"

[sandbox]
default = "workspace-write"  # read-only / workspace-write / danger-full-access
# shell = "workspace-write"  # 按工具覆盖；"mcp__fs__*" 这样的通配名也可以

[tools]                      # 工具名（可通配）→ 动作，优先于 [effects]
job_kill = "allow"

[rules]                      # 与 permissions.toml 同格式的 工具(模式) 规则
allow = ["shell(npm run test:*)", "edit(src/**)"]
ask   = []
deny  = []
```

### 3.2 判定顺序

1. deny 规则（公共 + 档位 + 会话）命中 → 拒绝。
2. ask 规则命中 → 询问。
3. allow 规则命中 → 放行；若调用申请了比档位更宽的沙箱，规则须带 `@sandbox` 后缀才放行，否则询问。
4. `[tools]` 命中 → 按其动作。
5. `[effects]` 按工具效果 → 按其动作。
6. 都没有 → 询问。

收紧项（在上面结果之后）：
- 申请更宽 `sandbox_permissions` 时 allow 降为询问（档位沙箱本身是 full 时不问）。
- 不可信输入触发的调用 allow 降为询问。
- MCP 工具声明 `destructiveHint` 时 allow 降为询问，且不提供“本会话内都允许”。

### 3.3 内置档位

内置档位嵌入 `plugins/security/permission/modes/*.toml`：

| 档位 | read | write | exec | network | interact / spawn / orchestrate | collab | external | 沙箱 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| read-only 仅可查看 | allow | deny | allow | ask | allow | deny | ask | read-only（`job_kill` allow） |
| ask 每次询问 | allow | ask | ask | ask | allow | ask | ask | workspace-write |
| workspace 工作区允许（缺省） | allow | allow | allow | ask | allow | allow | ask | workspace-write |
| full 完全权限 | allow | allow | allow | allow | allow | allow | allow | danger-full-access |

### 3.4 自定义档位

- 位置：`~/.ybase/modes/<名字>.toml`（`$YBASE_HOME/modes`），以及受信任项目的 `<项目>/.ybase/modes/`。同名时项目覆盖用户；不能覆盖内置档位名。
- `base` 继承：键级覆盖，`[rules]` 追加；链长 ≤ 8，成环报错。
- 命令：`ybase mode list`、`ybase mode copy <源> <新名> [-project]`，会话内 `/mode copy …`、`/mode <名字>`，启动参数 `-mode <名字>`。

### 3.5 公共规则

`~/.ybase/permissions.toml` 与受信任项目 `.ybase/permissions.toml` 里的 `allow / ask / deny` 对所有档位生效；其中 `mode` 是新会话的缺省档位。

### 3.6 会话与生效时机

- 会话 Ext `permission.mode` 存档位名；“本会话内都允许”生成的规则存 Ext `permission.allow`。子智能体、成员跟随顶层会话。
- 档位文件按 mtime 每回合检查，变化时提示“[权限] 档位 <名字> 的配置已更新，本回合起生效”。档位文件被删时按“每次询问”处理并提示。
- 迁移：旧值 `auto` → `workspace`，`custom` → `ask`。

## 四、各工具的具体处理

- **文件工具**：`edit`、`write_file` 效果 write，标 `AttrWorkspace`；路径越出工作区由工具本身拒绝。规则 `edit(src/**)` 按相对工作区的路径匹配。
- **shell**：效果 exec，在档位 `[sandbox]` 指定的级别执行；被沙箱拒绝时输出提示，模型可加 `sandbox_permissions` 重试，需用户批准、仅本次有效。“本会话内都允许”按非安全命令段生成前缀规则（如 `shell(git push:*)`）。
- **job_output** read；**job_kill** exec（read-only 档位单独放行）。
- **web** network；**todo / ask_user** interact；**subagent / team_spawn** spawn；**team_send / task_*** collab；**run_code** orchestrate，子调用逐个再走判定。

## 五、MCP

`mcp.toml` 用 `[[server]]` 数组：

```toml
[[server]]
name    = "fs"
command = "npx"
args    = ["-y", "@modelcontextprotocol/server-filesystem", "."]
trust   = "ask"              # ask（缺省）| readonly | trusted
sandbox = "workspace-write"  # 可选，stdio 服务进程的沙箱
```

- `trust`：ask → 效果 external；readonly → read；trusted → write。
- 工具注解 `destructiveHint` → 询问，不提供“本会话内都允许”。
- stdio 服务进程经 `Confiner` 启动：用服务的 `sandbox`，否则用缺省档位 `[sandbox]` 中 `mcp__<服务>__*` 或 default；没有沙箱插件时按 full 运行并警告。

## 六、用户钩子接入沙箱

钩子配置加 `sandbox` 字段，缺省 workspace-write，经 `Confiner` 执行（`plugins/extend/hooks/hooks.go` Runner.Confine）。

## 七、沙箱的定位

沙箱是唯一由操作系统强制的限制，只管子进程。Windows 实现为 WRITE_RESTRICTED 受限令牌 + 工作区能力 SID（`plugins/security/sandbox`）；非 Windows 暂无沙箱，按 full 运行。MCP 服务和钩子的沙箱级别在启动时按缺省档位确定，会话中切换档位不影响已启动的进程。

## 九、权限项注册表与档位表（2026-11-01 用户确认，m13123）

本节取代上一版的「授权机制（Plan + 台账）」。上一版被否掉的原因有三条：`Plan` 仍然是工具自报，解决不了「凭什么相信它说自己只读」；台账是第二套规则系统，和档位并存会让同一个问题有两处答案；策略接口要重做层链，改动面远大于收益。

### 9.1 结构：三层词汇

| 层 | 谁定义 | 用途 | 用户能改吗 |
| --- | --- | --- | --- |
| **类别** | 宿主写死九个（就是第二节的效果） | 只用于给内置档位封顶 | 不能 |
| **权限项** | 插件注册工具时声明，宿主汇总成**注册表** | 判定与配置的单位 | 不能 |
| **取值** | **档位表**给每个权限项赋值 | 实际生效的策略 | 自定义档位可改 |

关键区别：类别是粗粒度的九个桶，权限项是细粒度的可配置条目（`shell.exec`、`web.fetch`、`fs.write`、`sandbox.level`……）。一个权限项可以被多个工具共用；一个工具可以引用多个权限项。

### 9.2 封顶表

权限插件源码里的常量，4 个内置档位 × 9 个类别，进 git，规模稳定：

| 类别 | read-only | ask | workspace | full |
| --- | --- | --- | --- | --- |
| read | allow | allow | allow | allow |
| write | deny | ask | allow | allow |
| exec | ask | ask | allow | allow |
| network | ask | ask | ask | allow |
| interact | allow | allow | allow | allow |
| spawn | allow | ask | allow | allow |
| collab | deny | ask | allow | allow |
| orchestrate | allow | ask | allow | allow |
| external | ask | ask | ask | allow |

封顶表只约束**生成的内置档位**：插件给某权限项的建议值必须等于或严于其类别在该档位的封顶值（严格程度 deny > ask > allow），越顶则装配期拒绝启动。理由是插件自报只能加严不能放宽。

封顶表不约束自定义档位——自定义档位是用户自己写的策略，用户就是权威（见 9.6）。

### 9.3 注册表

插件注册工具时声明权限项，宿主汇总。用户不可编辑注册表。

```go
type ItemType string // 宿主固定三种，插件只能选不能扩展

const (
    ItemSwitch ItemType = "switch" // 开关：allow / ask / deny
    ItemMatch  ItemType = "match"  // 匹配列表：allow / ask / deny 三个模式列表 + 未命中缺省
    ItemLevel  ItemType = "level"  // 级别：从 Levels 里取一个值，如沙箱级别
)

type Item struct {
    ID      string   // "shell.exec"、"web.fetch"、"sandbox.level"
    Title   string   // 面板显示名
    Type    ItemType
    Class   string   // 所属类别，用于查封顶表
    Levels  []string // 仅 level 型
    Bounded bool     // 仅 match 型：匹配是否构成边界（见第十节）
    Subject func(args json.RawMessage) ([]string, error) // 仅 match 型：从参数取匹配对象
    Suggest map[string]Action // 各内置档位的建议值，键是内置档位 id
}
```

工具侧只引用项 id：

```go
Items: []string{"shell.exec", "sandbox.level"}
```

两条硬规则：

- **未注册权限项的工具一律询问**，不是放行。漏声明的代价是啰嗦，不是失守。
- **不需授权的工具必须显式声明「无需授权」**（`todo`、`ask_user`），而不是靠「没声明就不管」。

`match` 型项的匹配对象由声明它的插件提供 `Subject`：shell 插件知道怎么把 PowerShell 命令拆成段，权限插件不需要知道。这解决了上一版 9.2 悬着的归属问题——**判定表归权限插件，命令切段归 shell 插件**，两层在 `Subject` 处汇合。

`match` 型项的清单必须有限且由注册表汇总，不能让用户凭空造新项（参考 Zed：它的 pattern 工具是宿主固定的十个）。

### 9.4 档位表

档位表 = 每个权限项的取值。

**内置档位由生成得到**，不再是文件：取全部插件对该档位的建议值汇总，用封顶表校验。改成生成的理由是，继续用 `modes/*.toml` 给每项取值意味着权限插件必须知道所有工具的项名，这是插件间的反向依赖（薄内核规则：插件之间不得互相 import）；而且插件可开关，关掉 web 插件后文件里的 `web.*` 就是悬空配置。顺带解决现存的丑陋处——`read-only.toml` 里孤零零的 `job_kill = "allow"` 变成 job_kill 这一项自己的建议值，由 shell 插件声明，例外和需要例外的工具待在一起。

**自定义档位是文件**，复制基础档位后只写覆盖项：

```toml
name = "我的本机档位"
base = "workspace"
description = "放宽测试命令和文档站点"

[items]
"shell.exec"   = { allow = ["npm run test:*", "go test ./..."], default = "ask" }
"web.fetch"    = { allow = ["docs.rs", "pkg.go.dev"], default = "ask" }
"sandbox.level" = "workspace-write"
"team_spawn"   = "deny"
```

- 位置：`~/.ybase/modes/<名字>.toml`（`$YBASE_HOME/modes`），以及受信任项目的 `<项目>/.ybase/modes/`。
- `base` 继承：键级覆盖，`match` 型的列表追加；链长 ≤ 8，成环报错。
- **取不到值的新权限项沿继承链回落到内置档位的建议值，不回落 allow**。新装一个插件不能因为老档位文件没写它就自动放开。
- 文件改动按 mtime 每回合检查，变化时提示「[权限] 档位 <名字> 的配置已更新，本回合起生效」；文件被删时按「每次询问」处理并提示。

### 9.5 判定

取本次调用涉及的**所有**权限项，逐项求值：

1. 公共 deny 规则命中 → 拒绝（跨档位硬兜底，见 9.7）。
2. 会话临时层（「本会话内都允许」）命中 → 放行（只含 allow，见 9.8）。
3. 档位表里该项的取值：`switch` 直接取；`match` 型按 `Subject` 取出的每个对象查 deny → ask → allow 列表，都没命中按 `default`；`level` 型取级别值。
4. 该项未在档位表里出现 → 回落内置档位建议值 → 仍没有 → 询问。

汇总：**任何一项 deny → 拒绝；任何一项 ask → 询问；全部 allow → 放行。**

匹配顺序保持 deny → ask → allow，不采用 OpenCode 的「最后匹配者胜」（他们自己也在 `evaluateInput` 里补了前置 deny 救场）。

收紧项（在上面结果之后）：

- 不可信输入触发的调用，allow 降为询问。
- MCP 工具声明 `destructiveHint` 时 allow 降为询问，且不提供「本会话内都允许」。
- 申请比档位更宽的沙箱级别时，**每次单独确认**，不被任何 allow 取值免除（Codex 原话：`a command allow rule does not authorize removing filesystem restrictions`）。

**取值为 deny 的权限项，其工具不进模型的工具列表**——模型看不到它，而不是看到之后被拒绝。副作用：会话中途切档位会改变工具列表，必然丢一次提示缓存（实测命中率 82.6–87.2%），这是已知代价，不是 bug。

### 9.6 自定义档位可以更宽

允许自定义档位比基础档位更宽。禁止放宽会让这个功能作废：用户的真实需求几乎总是放宽型（「工作区档位，再加我的测试命令」），禁止之后他只能从 `full` 往下裁，而从完全权限裁剪比从工作区加项危险得多——漏裁一项就是全开。Codex 的 `extends` 也没有 tighten-only 约束。

配套三条：

1. **硬兜底不受影响**：公共 deny 和写死的不可关清单在 `full` 和任何自定义档位生效；沙箱越界申请仍每次确认。「放宽」的天花板不是基础档位，是硬兜底。
2. **名字不许单独出现**：`ybase mode list`、`/mode` 回显、切档位横幅，凡显示自定义档位名的地方都要带放宽清单，例如 `local（基于 workspace，放宽 2 项：shell.exec、web.fetch）`。名字会骗人，名字加放宽清单不会。
3. **继承只继承取值，不继承封顶**：封顶表只管生成的内置档位。这一条要写进文档，否则会被当 bug 报。

**项目级档位再严一档**：受信任项目 `<项目>/.ybase/modes` 里的档位，收紧随便放；放宽则在首次选用时列出放宽项、要求确认一次，结果记进 `~/.ybase/trust.toml`。否则一个仓库可以靠提交一个档位文件放宽本机权限，这是授权放大。

### 9.7 公共规则只能加严

`~/.ybase/permissions.toml` 与受信任项目的 `.ybase/permissions.toml` 最终只剩三样：`mode`（新会话缺省档位）、`deny`、`ask`。

- **公共 deny / ask 保留**：「永远不碰 `~/.ssh`」「这一类我永远要亲眼看一遍」与档位无关，切到完全权限也不该失效。
- **公共 allow 砍掉**：一条全局 allow 会悄悄放宽「仅可查看」档，于是档位名不再代表上限——而档位这个概念的全部价值就是名字能预测上限。留着它也等于留两套规则系统。

不做迁移（2026-11-01 用户要求不留兼容，m14468）：`permissions.toml` 里出现 `allow` 直接启动报错，提示改写进自定义档位文件。

### 9.8 会话临时层

「本会话内都允许」叠一层会话临时授权，**不改档位表**：

- 只能含 allow，且带有效期（参考 OpenCode 的 `savedRules()` 只映射 `effect: "allow"`，Goose 的 `ToolPermissionRecord{expiry}`）。
- 工具层按「工具 + 参数哈希」（已有 `ArgsHash`）；终端层按命令前缀段（已有，按非安全段生成前缀规则）。
- 存会话 Ext `permission.allow`；子智能体与成员跟随顶层会话。
- 批准后同会话里挂起的相同请求一并放行。

### 9.9 沙箱：独立开关，缺省关闭

沙箱是一个独立开关，**缺省关闭**：

- 关闭时，shell 走普通权限判定（`shell.exec` 这一项）。
- 开启时，沙箱内自动执行，申请越界时问一次。
- 开关说明里如实写明取舍与现状缺口：只限写、不限读、不限网；仅 Windows（WRITE_RESTRICTED 受限令牌 + 工作区能力 SID）；`GOCACHE` 要改到沙箱临时目录；node 起子进程会 `spawn EPERM`，无法修。

沙箱级别本身是一个 `level` 型权限项（`sandbox.level`），所以它和其他权限项一样出现在档位表里。

### 9.10 可视化与出口

- `ybase mode list`：列出全部档位，自定义档位带基础档位与放宽清单。
- `ybase mode show <名字>`：打印解析后的**完整取值表**，每行标注来源（哪个插件的建议值 / 哪个档位文件 / 继承自谁）。
- `ybase mode copy <源> <新名> [-project]`：把解析结果落成文件，供编辑。
- 会话内 `/mode <名字>`、`/mode copy …`；启动参数 `-mode <名字>`。

### 9.11 装配约束取代缺省闸门

此前加的缺省闸门（`Layer.Authorizes`、`Options.RequireAuthorization`、`core/toolhub/exec.go` 的 `defaultGate`、`core/toolhub/gate_test.go`）按工具自报的 read 效果放行，属于工具层越权判断，撤掉。改为装配约束：**权限策略必须恰好有一个**，没有或多于一个时启动报错。

`EffectOf` 不再按 `Risk` 推断效果：类别只用于查封顶表，不再是判定依据。

### 9.12 保留字与迁移

- 保留档位名，自定义档位不得占用：`read-only`、`ask`、`workspace`、`full`、`custom`、`auto`。后两个是保留字而非可用档位（DSH 在 preset 里遇到这两个名字直接报错）。
- 不做迁移（m14468）：会话 Ext 里不存在的档位名按「每次询问」处理并提示；档位文件出现 `[effects]` / `[tools]` / `[sandbox]` / `[rules]` 等旧段直接报错；沙箱级别改由 level 型项 `sandbox.level` 提供。
- MCP 规则的 server 段不许带通配：`mcp__*` 可以，`mcp__gi*__*` 不行，否则会命中以后新装的 server（Claude Code 的做法）。

### 9.13 信任前提与已知缺口

- 权限项与 `Subject` 都是插件声明，宿主采信但不验证；同进程内拦不住工具直接调 `os`。前提是装上的插件是可信代码。用依赖测试禁止工具插件直接导入 `os/exec`（子进程必须经 `Confiner`）。
- 真正的隔离留给外置插件（进程协议 / WASM），届时插件只拿到句柄，本机制原样适用。
- 子进程内部行为只靠沙箱限制；非 Windows 暂无沙箱。
- 不采纳让模型自报风险（Cline 的 `requires_approval` 把判定权交给被判定方）。
- 不加 `delegate` 取值（Amp 把判定外包给外部程序）；用户钩子已覆盖这个场景，但要确认**钩子的 deny 在 `full` 档也生效**。
- 审查者层（Goose SmartApprove / Codex auto_review / DSH 实验插件）留接口不实现、缺省不装；装了的话界面必须标明是谁批的。

### 9.14 分步实施

1. `core/toolhub`：`Item` / `ItemType` / 注册表、工具引用项、工具列表过滤钩子（deny 项的工具不下发）、装配约束（恰好一个权限策略）；撤掉 `defaultGate`。
2. 各插件声明权限项与各内置档位建议值；shell 的拆段 / 安全段 / 前缀生成从 `plugins/security/permission/command.go` 搬到 `plugins/tools/shell` 并作为 `Subject`。
3. 权限插件：封顶表常量、内置档位生成、装配期校验、`[items]` 解析与继承回落、按项判定、`permissions.toml` 砍公共 allow 与自动迁移、`mode show`。
4. 沙箱改独立开关（缺省关闭）与 `sandbox.level` 权限项；项目级档位放宽的首次确认记入 `trust.toml`。
5. 文档（`20 - 插件/05`、`06`、`03 - 约束清单`）与决策记录（`02 - 任务总清单`）；vet + race；真机验收。

## 十、两层控制：闭集与开集

工具层和终端指令层不是粒度粗细的差别，是性质差别。

| | 工具层 | 终端层 |
| --- | --- | --- |
| 参数是什么 | 结构化数据（路径、URL） | 另一门语言的程序 |
| 判定依据 | 注册表项 + JSON schema 约束的参数 | 命令文本（启发式） |
| 谁是权威 | 判定表 | 沙箱（操作系统层） |
| 文本匹配的作用 | 构成边界 | 只减少询问次数 |

工具层是**闭集**：注册表能枚举，判定是可判定的——规范化路径、比对 glob，结果确定。

终端层是**开集**：`npm run test` 跑的是 `package.json` 里的任意脚本；`sh -c "…"`、变量展开、base64 解码、别名、脚本文件，都能让「看起来匹配 `npm run test:*`」的命令干任何事。VS Code 把这句写进了自己的文档：`Terminal auto-approval is a best-effort convenience, not a security boundary.`

### 10.1 这解释了沙箱的适用范围

开集没法在参数层判定，只能在系统层限制实际行为。所以沙箱恰好只用在会起子进程的三处：`shell`、MCP stdio 服务、用户钩子。`edit` 不需要沙箱，因为它的路径是数据，工具自己规范化后就能拒绝越界。

### 10.2 按「参数是数据还是程序」给工具分类

- **数据类**：`edit` / `write_file`（路径）、`web_fetch`（域名）、MCP 工具（名字可枚举，参数由 server 的 schema 约束）。匹配构成边界。
- **程序类**：`shell`、`run_code`。匹配只是便利。

注册表 `match` 型项因此带 `Bounded` 标记。档位面板必须如实显示：沙箱关闭且 `shell.exec = allow` 时，提示「命令内容只按文本匹配，不构成边界」。否则用户以为自己配了一道墙，实际只配了一个提示过滤器。

### 10.3 停止线：启动器类命令永不被前缀规则放行

`plugins/security/permission/command.go` 的 `SplitCommand` / `Safe` / `Prefix` 要加一份清单：`sh`、`bash`、`cmd`、`powershell`、`node`、`python`、`npm run`、`pnpm`、`make`、`xargs`、`env`、`eval`、`sudo` 等启动器类命令，**永远不能被前缀规则自动放行**，因为它们的参数是另一个程序。

没有这条，一条 `shell(npm run test:*)` 的 allow 规则实际授权范围是「`package.json` 作者能写的任何东西」。Codex 为此有专门的 execpolicy。

### 10.4 处理开集的优先顺序

1. **能变回闭集的就变**：`run_code` 的子调用回到 hub 重新走判定（调用 id `<parent>#<n>` 就是为此），所以不需要对代码文本做任何匹配；`subagent` 同理，子会话的工具调用各自判定。
2. **变不回的靠沙箱**：`shell`、MCP stdio、用户钩子。
3. **两者都做不到的，如实告诉用户这里没有边界**，而不是给一个看起来像规则的东西。
