# 工具权限调研

> 第一至六节为用户整理的四家（Qoder / Claude Code / Codex / DSH）调研。第七至十节是 2026-11-01 补的三批调研：按工具 / 按方法的授权界面（Zed、Continue、Cline、Roo、Amp）、四个本地仓库的源码级数据结构（OpenCode、Goose、Codex、DSH）、插件声明 + 宿主存储的跨领域做法（VS Code、MCP、浏览器扩展、Android），以及第十节对我们「注册表 + 档位表」方案的最终修正。

---

## 一、先建立一个统一模型

把智能体想成一位来你电脑上干活的外包工程师：

| 层                   | 类比               | 作用                             | 谁来执行                    | 典型实现                                                     |
| -------------------- | ------------------ | -------------------------------- | --------------------------- | ------------------------------------------------------------ |
| **边界（Sandbox）**  | 工位和门禁         | 物理上能碰哪些文件、能不能上网   | 操作系统，不靠模型自觉      | Seatbelt(macOS)、Landlock+seccomp(Linux)、Windows Sandbox、容器 |
| **审批（Approval）** | 门口保安           | 每次越界前问不问、问谁           | 人 / 分类器 / 同模型 / 没人 | `ask`、`on-request`、自动审批                                |
| **规则（Policy）**   | 员工手册+封条      | 哪些命令和路径永远放行或永远禁止 | 静态配置，可进仓库共享      | `allow` / `ask` / `deny`                                     |
| **工作状态**         | 今天做勘查还是施工 | 只读规划 vs 动手执行             | 会话状态机                  | Plan / Goal，与权限模式**正交**                              |

这四个维度两两组合，就能解释所有产品：

|            | 有审批                           | 无审批                             |
| ---------- | -------------------------------- | ---------------------------------- |
| **有沙箱** | 默认安全区（Codex 默认档）       | 无人值守安全区（`dontAsk` + 沙箱） |
| **无沙箱** | 靠人兜底（你截图里的“每次询问”） | **事故象限**（完全访问 / YOLO）    |

你截图三档的本质：边界始终是“工作区文件夹”这一条软边界，变的是保安——**每次问你 → 风险分类器替你判断 → 撤掉保安**。真正危险的从来不是“开了完全访问”，而是“墙本来就只是文件夹约定 + 保安也撤了”。

## 二、四家具体怎么做的

### Qoder
- **IDE/桌面**三档：每次询问（默认）/ 自动审批 / 完全访问，配一张**按操作类型**的矩阵表：工作区内读写、工作区外写入、终端命令、网络，四类操作分别定义。
- **CLI** 是五档：`default` / `accept_edits` / `auto` / `bypass_permissions`(YOLO) / `dont_ask`。其中 `auto` 是零弹窗+AI 分类器，`dont_ask` 是“该问的一律拒绝”——**真正的无人值守安全档**，因为它是失败关闭。
- 规则体系是 8 层优先级：用户 settings → 项目 settings → 本地 settings → `--settings` → 命令行参数 → `/allow` 会话命令 → 会话临时规则。
- **Hook 优先级高于权限模式**：`PreToolUse` 返回 deny，在 YOLO 下也能拦。这是团队做硬策略的正道。
- 防绕过做得很细：UNC 网络路径、NTFS 备用数据流（`file.txt:stream`）、8.3 短名、设备路径、保留名 `CON/NUL` 都要显式批准；`.git`、`.vscode`、`.bashrc`、`.mcp.json` 属受保护路径。
- 一个容易忽略的点：**Plan / Goal 是工作状态，不是权限档**。Goal 会自动切到 `auto` 并锁住模式切换。

### Claude Code（生态里的“事实标准”）
- 六档：Manual(`default`) / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions`。
- `auto` 引入**第二个模型当分类器**，2026 年 10 月的版本里已是交互式终端和 VS Code 的默认档；`bypassPermissions` 官方只建议在隔离容器/VM 里用，云端会话干脆不给这个选项（因为云端本来就沙箱化）。
- 两条不对称规则很值得学：**deny 规则在任何模式下都生效，包括 bypass；而 allow 规则在 bypass 下反而失效**——防的是“你以为白名单在兜底，其实早就裸奔”。
- “任何模式都不会自动批准”的清单（`.git` 写入等）硬编码，配置关不掉。
- 企业管理员可以限制可用模式、强制只用托管规则。

### Codex（把权限拆成两个正交旋钮）
- 旋钮一 `sandbox_mode`：`read-only` / `workspace-write` / `danger-full-access`。`workspace-write` 可写工作区和 `writable_roots`，**默认断网**，要联网得显式打开 `network_access`。
- 旋钮二 `approval_policy`：`on-request`（默认）/ `never` / 细粒度 `granular`。旧的 `untrusted` 在 v0.149.0 已退役，`on-failure` 也废弃了。
- 桌面端那个“Approve for me”= `workspace-write` + `on-request` + `approvals_reviewer = "auto_review"`，即**换一个审查者 Agent 当保安**。
- 硬兜底：带“破坏性注解”的 MCP/App 工具调用，即使全开也必须人工确认。
- 两个坑：权限配置档（beta）和老的 `sandbox_mode`/`approval_policy` **不能混写**，混了会静默忽略一部分；Windows 上还分 `elevated` / `unelevated` 两种沙箱实现。

### DeepSeek Harness（DSH）
- 三个预设 × 审批：`read-only`+ask / `workspace-write`+ask（默认）/ `danger-full-access`+never。预设本身是个**可插拔插件**（`permission-presets`），部署层还能再覆盖。
- 审批服务设计得很克制：只有“允许一次/拒绝/取消/不可用”四种结果；**没有审批处理器时失败关闭，而不是默认放行**。
- “自动授权审查”是社区/实验插件：每次工具调用前用**同一个模型**预审，被拒的再交给人。它不依赖沙箱，开启前会弹风险确认。
- 官方对边界的描述很诚实：`web_fetch` 默认禁用（SSRF 防护未完善，不拦私有/回环地址）；Web UI 只监听本机，CLI 拒绝 `--host 0.0.0.0`——不把有 shell 的 Agent 暴露成网络可达的 RCE。
- 越界升级路径值得注意：`workspace-write` 被拒 → 用户批准 → 以 `danger-full-access` 重试，此时**直接 spawn，完全绕开沙箱**。

## 三、横向对照

| 维度           | Qoder                                | Claude Code                       | Codex                                  | DSH                       |
| -------------- | ------------------------------------ | --------------------------------- | -------------------------------------- | ------------------------- |
| 默认档         | 每次询问                             | Manual（新版为 Auto）             | `workspace-write` + `on-request`       | `workspace-write` + `ask` |
| 边界靠什么强制 | 工作区 + 受保护路径 + 路径形状检查   | 工作区 + 受保护路径 + 云/容器沙箱 | OS 级沙箱（Seatbelt/Landlock/Windows） | 沙箱插件（三档）          |
| 无人值守方案   | `auto`（分类器）/ `dont_ask`（全拒） | `auto` / `dontAsk`                | `never`（+ 沙箱兜底）                  | `never`（+ 沙箱兜底）     |
| 硬编码兜底     | 受保护路径、UNC/ADS 路径             | deny 永远生效、受保护路径         | 破坏性工具注解                         | 危险命令审批、fail-closed |
| 规则粒度       | 工具/路径/命令/MCP/子代理            | 同左                              | `granular` 分类开关                    | 预设级（沙箱×审批）       |
| 团队治理       | 托管规则 + Hook                      | 托管设置 + 限制模式               | 组织级 `allowed_approval_policies`     | 部署级覆盖预设            |

一个明显趋势：**Qoder CLI 的抽象几乎和 Claude Code 同构**（模式名、8 层优先级、Hook 名、`settings.json` 结构都对齐）。这说明权限模型正在收敛成一门“事实上的标准”，差异主要在默认值和边界强度。

## 四、从这四家能提炼的 7 条设计规律

1. **默认最严，并且失败关闭**。headless/无 UI 时，“该问的”一律拒绝（Qoder `dont_ask`、Claude `dontAsk`、DSH fail-closed）。这是最容易被做错、也最致命的一条。
2. **deny 和 allow 不对称**。禁止清单永远赢，白名单在最高档失效。因为白名单的遗漏是沉默的，而禁止清单的误伤是可见的。
3. **审批请求必须有“有效期”**：一次 / 本会话（进程退出即失效）/ 永久（进配置文件，要过代码评审）。永久授权不该藏在弹窗的第三个按钮里。
4. **审批人可替换，但要区分“自动批准”和“自动审查”**。人 → 独立分类器 → 同模型自审 → 无人，可靠性依次下降。同模型自审存在利益冲突（它判断自己该不该做），UI 必须让用户一眼看出这是谁批的。
5. **硬兜底不能跟着配置走**。`.git`、根目录 `rm -rf`、破坏性工具注解——这些在任何档位都拦。
6. **越界即升级重试，要防授权放大**。`workspace-write` 被拒后以 `danger-full-access` 重跑，意味着一次点击可能把后续整段任务都放进无墙环境；沙箱策略和审批结果要绑定到具体调用，而不是会话。
7. **文件、审批、网络是三个独立控制项**，必须分别评估（DSH 官方原话）。很多“自动审批”只审了命令文本，网络出口完全没管。

## 五、针对你截图那三档的实用建议

- **日常编码**：留在“自动审批”，但补一条 deny 清单。自动审批的漏判代价，取决于背后分类器的质量，而这在 IDE 里是不透明的——所以别把它当沙箱用。
- **真无人值守**：优先 CLI 的 `auto` 或 `dont_ask`，而不是 YOLO。`dont_ask` 的语义是“拒绝而不是放行”，比“全都放行”安全一个数量级。
- **完全访问**：只放容器/VM/低权限账户里。它同时撤掉了墙和保安，没有任何一层兜底。
- **规则最小集**（Qoder CLI 写法，Claude Code 同构）：

```json
{
  "permissions": {
    "deny":  ["Read(~/.ssh/**)", "Read(**/.env)", "Bash(rm -rf:*)", "Bash(git push --force:*)"],
    "ask":   ["Bash(npm publish:*)", "WebFetch", "mcp__*"],
    "allow": ["Read(/src/**)", "Edit(/src/**)", "Bash(npm run test:*)"]
  }
}
```

- **团队场景**：把硬策略写进 `PreToolUse` Hook 或托管配置，别指望每个人每次选对模式——模式是给人用的，Hook 是给机器执行的。
- **你的子代理 fan-out 场景**：四家文档对“子代理权限继承”都写得很含糊。稳妥做法是把边界下沉到沙箱/工作区层面，而不是依赖父会话的权限模式；否则一次“本会话允许”可能在几十个子代理间被继承放大。

## 七、第二批：按工具 / 按方法的授权界面怎么做

前六节看的是“档位”这一侧。这一节补的是另一侧：**授权的最小单位是什么**。四家给出四种粒度，差别直接决定了用户面板长什么样。

### Zed：可用性与是否放行分成两张表

Zed 把两件事拆开，这一点和我们要做的“注册表 + 档位表”最接近：

- `agent.profiles` 决定**工具存不存在**，按工具名给布尔值。官方明确写了 "Profiles do not decide whether a tool call is allowed automatically"。
- `agent.tool_permissions` 决定**调用要不要确认**，取值 `confirm`（缺省）/ `allow` / `deny`，并支持按参数正则细化。

```json
{
  "agent": {
    "profiles": {
      "ask": {
        "name": "Ask",
        "tools": { "read_file": true, "grep": true, "terminal": false, "edit_file": false },
        "enable_all_context_servers": false,
        "context_servers": {}
      }
    },
    "tool_permissions": {
      "default": "allow",
      "tools": {
        "terminal": {
          "default": "confirm",
          "always_allow": [{ "pattern": "^cargo\\s+(build|test|check)" }],
          "always_confirm": [{ "pattern": "sudo\\s+/" }]
        }
      }
    }
  }
}
```

能带参数正则的工具是**固定清单**：`terminal`（匹配命令串）、`edit_file`、`write_file`、`delete_path`、`move_path`、`copy_path`、`create_directory`、`fetch`（URL）、`search_web`（query）、`skill`（SKILL.md 绝对路径）。MCP 工具按 `mcp:<server>:<tool>` 命名，例 `mcp:github:create_issue`。

判定优先级：内置安全规则（如 `rm -rf /`，不可覆盖）> `always_deny` > `always_confirm` > `always_allow` > 工具级 `default` > 全局 `default`。

自定义 profile 走面板 `Configure` 或命令面板 `agent: manage profiles`，支持 **fork 一个已有 profile**——但 fork 是一次性复制，不是运行时继承。profile 绑定在 thread 上，可随时切换。新装的 MCP 工具在 `enable_all_context_servers: false` 且未列入 `context_servers` 时**不暴露给模型**。

配置键在 v0.224.0 改过名：旧版是 `agent.always_allow_tool_actions`。

### Continue.dev：三级里有一级是“对模型隐藏”

CLI 侧三级：`allow` 直接跑 / `ask` 提示 / **`exclude` 对模型完全隐藏**。缺省只读工具（`Read, List, Search, Fetch, Diff, AskQuestion, Checklist, Status, CheckBackgroundJob, ReportFailure, UploadArtifact`）allow，写工具（`Edit, MultiEdit, Write`）与 `Bash` ask；headless 下所有 ask 一律降为 exclude——这是第四节第 1 条“失败关闭”的具体做法。

规则不在主配置里，而在单独的 `~/.continue/permissions.yaml`，主要由 TUI 的 “Continue + don't ask again” 写入，改动下次会话生效：

```yaml
allow:
  - Read(*)
  - Write(**/*.ts)
ask:
  - Bash
exclude: []
```

`Write` 等价于 `Write(*)`；括号里按主参数做 glob。优先级：模式开关（`--auto` / `--readonly`，绝对覆盖）> 命令行 flag > permissions.yaml > 内置缺省。模式可在 TUI 里用 Shift+Tab 中途切换。

IDE 扩展是三档 UI 标签 Ask First（缺省）/ Automatic / Excluded，按组开关，策略按用户本地存储。MCP 工具与内置工具走同一套策略。

### Cline / Roo Code：按类别，不按工具

Cline 的 Auto Approve 是类别开关：读项目文件 / **读所有文件** / 改项目文件 / **改所有文件** / 执行安全命令 / **执行所有命令** / 浏览器 / MCP 服务 / 通知，另有连续自动操作次数上限（缺省 200）。它**没有命令白名单**，而是让模型给每条命令打 `requires_approval` 标记（安全例 `git status`、`npm test`；需批准例 `npm install <pkg>`、`rm -rf`、`sed -i`）——即第四节第 4 条里可靠性最低的那一档：同模型自审。

Roo Code 的类别磁贴类似，但补了命令前缀白名单与黑名单，存 VS Code 设置 `"roo-cline.allowedCommands": ["git", "npm run", "echo"]`，并可用 `"*"` 全拒再放行安全前缀。

两家共同的风险：**MCP 只有一个总开关，不能按单个 MCP 工具授权**。新装一个 server，它的全部工具直接继承已开状态被自动批准。

### Amp：有序规则表 + 可外接裁决程序

`amp.permissions` 是一个**有序列表**，按工具名 + 参数匹配首条命中，动作 `allow` / `reject` / `ask` / **`delegate`**（把决定交给 `$PATH` 上的外部程序）：

```json
"amp.permissions": [
  { "tool": "Bash", "matches": { "cmd": "*git commit*" }, "action": "ask" },
  { "tool": "Bash", "matches": { "cmd": ["*python *", "*python3 *"] }, "action": "reject" },
  { "tool": "mcp__*", "action": "ask" },
  { "tool": "*", "action": "delegate", "to": "my-permission-helper" }
]
```

工具名支持通配，`matches` 按参数名给 glob 或 glob 数组。四家里只有 Amp 能对“未知的新工具”声明统一策略（`{"tool": "*"}` 兜底）。

### 这一批的横向结论

粒度从细到粗：Amp（工具 + 参数 + 通配兜底）≈ Zed `tool_permissions` > Continue CLI（工具 + glob）> Zed `profiles`（工具布尔）> Continue IDE（工具三档）> Cline / Roo（类别）。

对新工具最安全的是 Zed（`enable_all_context_servers: false` 时不暴露）和 Amp（`*` 兜底）；最危险的是 Cline / Roo，MCP 一个总开关让新 server 的工具自动获批。

### 对“注册表 + 档位表”的几点印证和修正

1. **拆成两层是对的，但不该是两份配置**。Zed 的 profiles / tool_permissions 拆分证明“能不能用”和“要不要问”确实是两个问题；但它用了两套文件两套语法，用户得在两处对齐同一个工具名。我们把两者合进档位表的一个 `[items]` 段、用取值区分（deny 不暴露、ask 问、allow 放行），比 Zed 少一层对齐成本。
2. **“对模型隐藏”要作为明确的一档写进语义**。Continue 的 `exclude` 和 Zed profile 的 `false` 都是这个意思。我们已定“取值 deny 时工具不出现在模型工具列表里”，与两家一致。
3. **带参数匹配的工具必须是有限清单**。Zed 的做法不是让每个工具自由定义匹配字段，而是宿主维护一张“哪些工具支持 pattern、匹配哪个参数”的固定表。这正好对应我们的注册表：**匹配对象的提取函数由插件声明，但注册表是汇总后的唯一事实**，用户只在这张表列出的项上写模式。
4. **必须有未知工具的兜底项**。Amp 的 `{"tool": "*"}` 是四家里唯一的正解。我们已定“未声明权限项的工具一律询问”，等价且更强（不需要用户写）。但要补一条：**新装插件带来的新权限项，在自定义档位里取不到值时，走继承链回落到内置档位的建议值**，而不是回落到“允许”。
5. **不要学 Cline 的“让模型自己标 requires_approval”**。这是把判定权交给被判定方。我们的注册表由插件代码声明（静态、可审查、随版本走），不是模型每次调用时自报。
6. **MCP 不能只有一个总开关**。按 `mcp__<server>__<tool>` 作为注册表里的独立权限项，配合 server 级 `trust` 做缺省值——这比 Zed 的 `mcp:<server>:<tool>` 手写清单省事，比 Cline 的单开关安全。
7. **`delegate` 这个动作值得留口子**。Amp 把裁决外包给一个外部程序，本质和我们的用户钩子 `PreToolUse` 同构（第四节已记“Hook 优先级高于权限模式”）。我们不需要在档位表里新增 `delegate` 取值，钩子已经覆盖；但要确认钩子的 deny 在 full 档也生效。

## 八、第三批：四个本地仓库的数据结构（源码级）

前两批看文档，这一批直接读 `refer/` 下的源码，拿到的是真实的数据结构。结论先说：**四家都没有「每个插件声明自己的类型化权限条目」的注册表**，权限词汇一律由宿主写死，工具最多在调用时传几个字符串。

### OpenCode：(action, resource) 规则序列，调用点声明

规则结构 `refer/opencode/packages/schema/src/permission.ts:56-67`：

```ts
export const Effect = Schema.Literals(["allow", "deny", "ask"])
export const Rule = Schema.Struct({ action: Schema.String, resource: Schema.String, effect: Effect })
export const Ruleset = Schema.Array(Rule)
```

工具不注册任何权限条目，而是在调用点自己传。`refer/opencode/packages/core/src/tool/plugin/write.ts:78-86`：

```ts
permission.assert({ action: "edit", resources: [target.resource], save: ["*"],
  metadata: { files: [preview] }, sessionID, agent, source })
```

shell 的 resource 由 AST 生成（`refer/opencode/packages/core/src/shell/parse.ts:197-284`）：`resource` 是命令原文，`save` 是 `` `${prefix(tokens).join(" ")} *` ``，即 `git status *`。

判定是**最后匹配者胜，不是 deny 优先**（`refer/opencode/packages/core/src/permission.ts:74-84`）：

```ts
evaluate(action, resource, ...rulesets) =
  rulesets.flat().findLast((rule) => Wildcard.match(action, rule.action) && Wildcard.match(resource, rule.resource))
  ?? { action, resource: "*", effect: "ask" }
```

但 `evaluateInput`（:162-178）在此之前先跑一遍 `denied(configured rules)`，所以用户保存的 always 规则**不能**覆盖 agent / session 级的 deny——等于把第四节第 2 条「deny 和 allow 不对称」做在了两段式判定里。agent 没写 permissions 字段时落到 `missingAgentPermissions = [{ action: "*", resource: "*", effect: "deny" }]`（:19）。

「本次之后都允许」存 **SQL 表**而非配置文件（`refer/opencode/packages/core/src/permission/saved.ts:69-84`，表定义 `permission/sql.ts:10`），行结构 `refer/opencode/packages/schema/src/permission-saved.ts:15-25` 的 `Info = { id（前缀 "psv_"）, projectID, action, resource, time }`——**按项目作用域**，且 `savedRules()`（permission.ts:137-145）只会把它映射成 `effect: "allow"`。

通配匹配器 `refer/opencode/packages/core/src/util/wildcard.ts`：`*` → `.*`，`?` → `.`，分隔符统一成 `/`，Windows 下加 `si` 标志，且 pattern 以 `" .*"` 结尾时改写成 `"( .*)?"`，所以 `git status *` 也能匹配裸 `git status`。

### Goose：唯一有 profile × 工具名矩阵的一家

`refer/goose/crates/goose/src/config/permission.rs:21-33`：

```rust
pub enum PermissionLevel { AlwaysAllow, AskBefore, NeverAllow }
pub struct PermissionConfig { pub always_allow: Vec<String>, pub ask_before: Vec<String>, pub never_allow: Vec<String> }
```

profile 只有两个（:43-44）：`USER_PERMISSION = "user"`、`SMART_APPROVE_PERMISSION = "smart_approve"`，存 `permission.yaml`（:13）。查找顺序 :134-157 是 `never_allow → always_allow → ask_before`，都不在返回 `None`。

四种模式 `refer/goose/crates/goose-provider-types/src/goose_mode.rs:22-32`：`Auto`（缺省，自动批准）/ `Approve` / `SmartApprove` / `Chat`。

运行期缓存的键比配置层细一级，是**工具名 + 参数哈希**（`refer/goose/crates/goose/src/permission/permission_store.rs:11-20`）：

```rust
pub struct ToolPermissionRecord { tool_name: String, allowed: bool, context_hash: String,
  readable_context: Option<String>, timestamp: i64, expiry: Option<i64> }
```

键 `format!("{}:{}", tool_call.name, context_hash)`（:79-90），取最后一条未过期记录，过期项在 load 时清理；落盘 `Paths::config_dir().join("permissions")` 下的 `tool_permissions.json`，用 `.tmp` + 原子 rename。这正是第四节第 3 条「审批要有有效期」的一个完整实现。

`SmartApprove` 会把判断交给 LLM：`refer/goose/crates/goose/src/permission/permission_judge.rs:144-185` 的 `detect_read_only_requests(...) -> Vec<String>`，从模型返回的 `read_only_request_ids` 取 id。这就是第四节第 4 条说的「同模型自审」，可靠性最低的那一档。

### Codex：两个正交旋钮 + 代码里的 per-tool trait，配置里没有工具表

`refer/codex/codex-rs/protocol/src/protocol.rs:1145-1185`：

```rust
pub enum AskForApproval { UnlessTrusted, OnRequest, Granular(GranularApprovalConfig), Never }
pub struct GranularApprovalConfig { sandbox_approval: bool, rules: bool, skill_approval: bool,
  request_permissions: bool, mcp_elicitations: bool }
```

注释原文：`When a field is true, commands in that category are allowed. When it is false, those requests are automatically rejected instead of shown to the user.`——**五个字段是审批流类别，不是工具名**。

per-tool 覆盖是 Rust trait 而非配置（`refer/codex/codex-rs/core/src/tools/sandboxing.rs:325-357`）：`trait Approvable<Req>` 的 `sandbox_permissions(&self, _req) -> SandboxPermissions::UseDefault`、`exec_approval_requirement(&self, _req) -> Option<…>`（`None` 即回落策略缺省）、`wants_no_sandbox_approval(&self, policy)`。全仓库只有两处 impl：`runtimes/apply_patch.rs:151` 与 `runtimes/unified_exec.rs:172`。

`refer/codex/codex-rs/docs/` 全部 15 个 md 里 grep `[tools]` / `granular` 零命中——**config.toml 里确实没有 per-tool 权限表**。

### DSH：preset 只有 sandbox + approval 两个轴

`refer/deepseek-harness/packages/dsh-permission-presets/lib/index.js`（408 行，源码可读）的 preset schema 只有 `{ sandbox, approval, name, description }`，取值来自 `dsh-sandbox-policy` 的 `["read-only","workspace-write","danger-full-access"]` 与 `dsh-user-approval/lib/index.js:37` 的 `["ask","never"]`。在这个包里 grep `tool` **零命中**。

状态是事件溯源的：`permissionStateSchema = { preset, sandbox, approval, seeded }`，`applyPermissionEvent` 折叠 `permission/preset`、`sandbox/mode`、`approval/policy` 三类事件。保留名 `custom`（旋钮值不匹配任何 preset 时的派生态）与 `auto`（`{ sandbox: "danger-full-access", approval: "ask" }`），preset 里出现这两个名字直接抛错——这一点我们要抄：**内置档位名必须是保留字**。

## 九、第四批：插件声明 + 宿主存储，跨领域怎么做

这一批换个方向看：VS Code 插件、MCP、浏览器扩展、Android 都是「第三方声明、宿主裁决」的成熟形态，正好对应我们的「插件声明权限项、宿主统一管档位」。

### VS Code `contributes.languageModelTools`：声明里没有风险字段

插件清单可声明 `name`、`displayName`、`modelDescription`、`userDescription`、`canBeReferencedInPrompt`、`toolReferenceName`、`icon`、`inputSchema`、`when`、`tags`。**没有任何 risk / destructive / confirmation 字段**。确认是运行时产生的：`vscode.lm.registerTool` 的 `prepareInvocation` 返回 `PreparedToolInvocation.confirmationMessages`，即风险由插件代码每次调用时自行决定，不是静态元数据。

可用性与批准明确分离，官方原文：`Tool availability is separate from tool approval. Enabling a tool makes it available to the agent, but doesn't bypass the configured approval and permission controls.` 启用状态存**用户 profile**：`Your selection persists in the active user profile, rather than applying to only one request.`

批准侧有 `Chat: Manage Tool Approval`（按来源分组，可整源信任）和 `Chat: Reset Tool Confirmations`；确认框给 single use / session / workspace / all future 四种期限——与第四节第 3 条完全一致。关键设置键：`chat.permissions.default`（Manual / Assisted / Allow all，缺省 Manual）、`chat.tools.eligibleForAutoApproval`（置 false 则永远手批，确认框不再给自动批准选项）、`chat.tools.terminal.autoApprove`、`chat.tools.terminal.blockDetectedFileWrites`（缺省 `outsideWorkspace`）。

终端规则的冲突解决值得照抄，原文：`A compound command is auto-approved only when all its subcommands match a true rule and none match a false rule. A false rule always takes precedence.` 以及 `A false rule requires approval. It does not block the command.`——**false 不等于 deny，只是强制询问**，这个区分我们目前没有（我们的 ask / deny 是两个值，正好对上）。官方还有一句自我限定：`Terminal auto-approval is a best-effort convenience, not a security boundary.`

企业侧有 `chat.mcp.allowedServers` / `chat.mcp.deniedServers`（`deny rules always take precedence`）、`chat.mcp.allowManagedServersOnly`。工作区信任：不受信任的工作区进入 restricted mode，`which also disables agents`。

### MCP annotations：规范自己写明「不可信」

```ts
interface ToolAnnotations { title?: string; readOnlyHint?: boolean; destructiveHint?: boolean;
  idempotentHint?: boolean; openWorldHint?: boolean; }
```

缺省值不对称且偏保守：`readOnlyHint` 缺省 false；`destructiveHint` 缺省 **true**，且仅在 `readOnlyHint == false` 时有意义；`idempotentHint` 缺省 false；`openWorldHint` 缺省 true。

规范原文（2025-11-25 schema）：`NOTE: all properties in ToolAnnotations are hints. They are not guaranteed to provide a faithful description of tool behavior (including descriptive properties like title). Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers.` 并且 `there SHOULD always be a human in the loop with the ability to deny tool invocations`。

这正好印证我们第五节已定的做法：MCP 的 `destructiveHint` 只能用来**加严**（allow 降为 ask），不能用来放宽；放宽要靠用户配的 server 级 `trust`。

### 浏览器扩展：声明是上限，授予由用户收窄

`permissions`（安装期必需）/ `optional_permissions` / `host_permissions` / `optional_host_permissions` 四类。运行期用 `permissions.request()`，必须在用户手势的处理器里调用，且 `either all are granted, or none are`；授予后 `The extension retains any permissions granted, even over upgrade and disable and enable cycling`。状态存浏览器 profile，manifest 不变，用户可在扩展页撤销。MDN 明确：host 权限「大多数浏览器视为可选」，用户可随时增删。

站点访问是三态（on click / on this site / on all sites），即**同一条声明可以被用户收窄成不同强度**，而不是布尔。这给我们一个启示：匹配列表型权限项的缺省值不必只有 allow/ask/deny 三选一，可以是「仅本次目标」这种更窄的形态——不过这会让档位表复杂一档，暂不采纳。

### Android 运行时权限：两次拒绝即永久拒绝 + 长期不用自动回收

清单声明 `<uses-permission>` 只是请求上限，危险权限 API 23+ 必须运行时请求。状态存系统 PackageManager，`dumpsys package` 里可见 `USER_SET`（拒过一次）、`USER_FIXED`（两次拒绝 = 永久拒绝，不再弹窗）。Android 11+ 有「仅限这一次」，应用退后台一段时间后失效，撤销时进程被终止；targetSdk 11+ 且数月未用的敏感权限会被**自动重置为拒绝**。官方还明确：`不要对系统行为做任何假设…应用不应依赖于特定权限组之内或之外的权限`——权限组只为减少弹窗，不是语义分类。

`USER_FIXED` 这个设计值得记一笔：**反复询问同一项而用户反复拒绝，应该升级为持久拒绝**，否则询问本身变成骚扰（也是一种诱导点击的攻击面）。

### 模型 API 层：根本没有权限字段

OpenAI 的函数声明只有 `function.{name, description, parameters}` 加 `strict`；Anthropic Messages 的工具只有 `name`（`^[a-zA-Z0-9_-]{1,128}$`）、`description`、`input_schema`，beta 另有 `allowed_callers`（`direct` / `code_execution_*`）——那是限制「谁能调用」，不是风险等级。

这一条划清了边界：**模型 API 只管「可调用性」，权限语义整体是宿主层的事**。我们把效果 / 权限项放在 `Attrs` 而不是塞进工具 schema，方向是对的；schema 里多写的任何风险字段都会被模型看见并可能被诱导利用。

### 两条值得单独记的旁证

**Claude Code 的 `_meta` 只能往更严推。** MCP server 可以用 `_meta["anthropic/requiresUserInteraction"]` 强制某个工具总是落到确认回调，**即使它已命中 allow 规则**；但没有反向的「跳过确认」字段。这是「自报只能加严、不能放宽」的一个完整实现。它的规则命名是 `mcp__<server>__<tool>`，`mcp__*` 匹配全部 MCP 工具，但 **server 段不许带通配**——避免用户写出 `mcp__gi*__*` 这种看起来精确、实际会命中新装 server 的规则。

**Android 的 `protectionLevel` 是平台定义的小枚举，声明方只能选、不能扩展。** `normal` 安装即授予，`dangerous` 必须运行时请求且可撤销。这正是我们第十节第 1 条想要的形态：风险词汇由宿主固定，插件在里面挑。

反面例子是 K8s RBAC：Role / ClusterRole 定义 `apiGroups/resources/verbs`，RoleBinding 把规则集绑给主体，**纯并集、没有 deny**。规则只能加不能减，所以一旦授权范围写宽就没有收回的表达方式——这解释了为什么我们必须保留 deny 优先。

### 这一批的共性

四者都把「插件声明的内容」当作**请求上限或提示**，真正的决定由宿主在自己的存储里按 profile 保存（VS Code user profile、浏览器 profile、Android 包状态）。MCP 把不可信写进了规范正文。未见过的新项，四者缺省都是 ask 或 deny，**没有一个默认 allow**——VS Code 的「默认可用」只是可见性，不是批准。

还有一条反复出现的模式：**自报内容只进 UI 文案和「更严」方向**。VS Code 的扩展能自报 `confirmationMessages`（确认框文案），但放行与否由设置键和沙箱决定；它的 Assisted 档位用一个 LLM judge 逐调用评估，文档自带免责声明 `model-based risk assessment can make mistakes`。Chrome 和 Android 干脆不采信自报风险。

## 十、调研结论：对「注册表 + 档位表」的最终修正

照我们 m11137 定的结构（统一工具权限注册表 + 各档位表 + 会话绑定），调研给出的是七条修正和两条确认。

**确认的两条**

1. **可用性与是否放行要分开表达，但不必分成两份配置**。Zed、VS Code 都把两者拆开，代价是用户得在两处对齐同一个工具名。我们用一个 `[items]` 段的取值区分（deny 不暴露、ask 问、allow 放行）更省；VS Code 终端规则里 `false 只是强制询问、不是拦截` 的区分，我们天然有。
2. **「对模型隐藏」必须是明确的一档**。Continue 的 `exclude`、Zed profile 的 `false`、VS Code 的 enable 开关都是这个意思。

**修正的七条**

1. **带参数匹配的权限项必须是有限清单，由注册表汇总**。Zed 的 pattern 工具是宿主固定的十个，不是每个工具自由定义字段。对应到我们：匹配对象的提取函数由插件声明，但**注册表是汇总后的唯一事实**，用户只能在注册表列出的项上写模式。
2. **新权限项的回落值要走继承链到内置档位的建议值，不能回落到 allow**。四家里只有 Amp 能对未知工具声明统一策略（`{"tool": "*"}`）。我们的「未声明权限项一律询问」更强，但自定义档位里**取不到值的新项**必须回落到内置档位建议值，这一条要写进档位解析逻辑。
3. **判定顺序用 deny 优先，不用 OpenCode 的「最后匹配者胜」**。OpenCode 自己也在 `evaluateInput` 里补了一段前置 deny 检查来救场，说明单纯的 last-match-wins 不够。我们现有的 deny → ask → allow 顺序保持不变。
4. **会话级授权要带有效期和作用域，并且只能是 allow**。Goose 的 `ToolPermissionRecord{expiry}` 和 OpenCode 的 `savedRules()` 只映射 allow 是两个正例；VS Code 的 single use / session / workspace / all future 是期限的完整形态。我们的「本会话内都允许」已经是这个语义，但要显式记：**它只叠加 allow，永不叠加放宽 deny 的能力**。
5. **内置档位名必须是保留字**。DSH 在构造时发现 preset 里出现 `custom` / `auto` 直接抛错。我们已禁止自定义档位覆盖内置名，但还要把 `custom`、`auto` 这两个历史值也列为保留（当前迁移逻辑是 `auto → workspace`、`custom → ask`）。
6. **权限项的类型取值必须是宿主固定的小枚举，插件只能选不能扩展**。Android 的 `protectionLevel` 是这个形态；反面是 K8s RBAC 的纯并集规则（只能加不能减，授权写宽了没有收回的表达方式）。这条支持我们把「开关 / 匹配列表 / 级别」三种类型写死在注册表定义里。
7. **MCP 规则里 server 段不许带通配**。Claude Code 允许 `mcp__*` 匹配全部 MCP 工具，但不允许 `mcp__gi*__*` 这种 server 段通配——否则用户写出看起来精确的规则，实际会命中以后新装的 server。我们按 `mcp__<server>__<tool>` 做权限项时要照这个限制。

**两个明确不采纳**

- **不让模型自报风险**。Cline 的 `requires_approval` 由模型每次调用时打标，是把判定权交给被判定方。我们的注册表由插件代码静态声明、随版本走、可审查。
- **不在档位表里加 `delegate` 取值**。Amp 把裁决外包给外部程序，这个能力我们的用户钩子 `PreToolUse` 已经覆盖；但要确认一条：**钩子的 deny 在最高档位也生效**（Qoder 的「Hook 优先级高于权限模式」、VS Code 的 `deny rules always take precedence` 都是这么做的）。

**一个待定项**：Goose 的「同模型自审」和 Codex 的 `auto_review`、DSH 的实验插件都指向同一个方向——用一个审查者替代人。调研结论是这条路可靠性最低（利益冲突），但它是唯一能让长任务无人值守又不全放开的办法。建议**留接口不做实现**：判定链上允许装一个「审查者」层，但缺省不装，装了要在界面上标明这次是谁批的。
