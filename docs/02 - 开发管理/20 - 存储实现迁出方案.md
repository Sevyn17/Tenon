# 20 存储实现迁出方案（2026-11-13）

> 状态：**已完成（2026-11-13，v0.3.0）**。本篇是框架侧的执行方案；产品侧的背景与落点见
> `Mortise/docs/07 - 存储实现迁出框架方案.md`。本篇只写框架要做什么、怎么验证。

## 一、为什么现在搬

产品（Mortise）要自己换存储实现，框架里留着 SQLite 会让两件事做不成：

1. 框架 `go.mod` 带着 `modernc.org/sqlite`，产品侧无论用不用都要编进这个驱动。
2. `runtime/assemble/deps_test.go` 为 SQLite 开了两个例外（`store-sqlite` 引用自己的实现、
   测试文件引用它）。例外在，规则就不是规则。

投递账改走集合（v0.2.2）之后，标准组件已经不依赖 `service:sql`，搬走不再有功能障碍。

## 二、搬什么、留什么

| 位置 | 处置 | 理由 |
|---|---|---|
| `modules/storage/sqlite`（40 个文件） | **删除** | 已原样复制到 `Mortise/client/store-sqlite/sqlitedb`（逐文件比对，只差包名） |
| `modules/storage/store-sqlite` | **删除** | 组件外壳已在 `Mortise/client/store-sqlite`，三个入口都已空导入 |
| `apphost/assemble.go` 的空导入 | **删除** | 存储插件由调用方登记 |
| `apphost/legacy.go` | **改成接口** | 见第三节 |
| `tenontest.Stores()` 的 sqlite 后端 | **删除** | 框架不再有 SQLite 实现 |
| `examples/web-server` | **改用 memstore** | 示例不需要持久化 |
| `runtime/store/memstore` | 留 | 纯内存，不碰 `os` / `database/sql` / 驱动 |
| `runtime/store/storetest` | 留 | 只依赖接口，是实现方的验收套件 |
| `store.SQL` / `ext.ServiceSQL` | 留 | 可选逃生口，本轮不动；见 19 篇 4.1 |

## 三、`legacy.go` 不搬走，改成接口

旧版会话库并入（`<项目>/.tenon/state.db` → 用户级库）的**编排**在框架里：找旧库、
判断是不是当前库、并入、复制附件、改名、出提示。这段逻辑不依赖 SQLite，依赖的只有
两个能力：

```go
type LegacyImporter interface {
    Import(ctx context.Context, path, workspace string) (LegacyImportResult, error)
    Path() string
}
```

产品侧 `client/store-sqlite/legacy.go` 已经按这个形状实现了 `Import` 和 `Path`，
只是 `apphost.LegacyImportResult` 这个类型还没定义。所以：

- `apphost` 定义 `LegacyImportResult` 和上面的接口，`importLegacy` 改用它。
- 类型断言失败就跳过（别的存储插件不认识旧库格式）。
- 断言打在登记为 `service:db` 的**句柄**上（`assemble.DBHandle` 那个值），
  不打在 `DB()` 的返回值上：并入同时要用库和附件存储，两者都挂在句柄上。
  v0.3.0 打在返回值上，产品的 `Import` 写在句柄上，断言静默失败、并入从不发生，
  v0.3.1 改回句柄。`apphost/legacy_test.go` 用一个假句柄钉住这个位置。
- 产品侧不用改代码，只是把注释里「接口是 apphost 内部的」改成「接口已导出」。

这样旧库并入这个能力留在框架，实现留在产品，两边都不丢功能。

## 三点五、跟着实现走的测试

`apphost/legacy_test.go` 的 `TestImportLegacyProjectStore` 走真实装配：它靠框架空导入
`store-sqlite` 才能打开工作区、建会话、关了再开验证并入。删掉空导入后，框架里没有
任何存储插件，这个测试在框架里跑不起来，也**不该**在框架里跑——它验证的是产品的
存储实现能不能把旧库并进来。

处置：这个测试文件搬到 `Mortise/client/store-sqlite/`，改成产品侧的包测试。
`apphost/profiles_test.go` 里断言 `store-sqlite` 缺省开着的三条，改成断言「存储插件
由调用方登记」，不再点名具体插件。

## 四、测试覆盖怎么处理

框架里 24 个测试文件直接 `sqlite.Open`。逐个看，分两类：

**只是想要一个 `store.Store`**（打开、用、关，不验证「关掉再打开仍在」）：
改成 `memstore.New()`。这类占大多数，覆盖不丢。

**真的在测持久化**（关库、重开、断言数据还在）：

| 测试 | 测的是什么 | 处置 |
|---|---|---|
| `runtime/host/trace_inherit_test.go` `TestInboxTracePersistsAndApplies` | trace 随 inbox 落库，重启后还在 | **改写**：不关库重开，改成直接读 `Inbox()` 断言 trace 列写进去了。落库是 `store.Store` 的契约，由 `storetest` 保证；重启后能读回来是实现的事，由产品侧的 sqlite 测试保证 |
| `runtime/host/guard_test.go`（重开库） | 守卫状态跨重启 | 同样改成读接口断言，不重开 |
| `tenontest/tenontest_test.go` 里跑两种后端的用例 | 两种存储行为一致 | 只留 memstore |

判断标准：框架测的是「调用了存储接口、传了正确的值」；「值写进文件、重启读得回来」
是实现的性质，由实现方跑 `storetest` 验证。产品侧 `sqlitedb/conformance_test.go`
已经在跑这套。

## 五、执行步骤

每步都能编译。

1. **`apphost` 接口化**：定义 `LegacyImportResult`，`legacy.go` 去掉 sqlite 导入，
   `assemble.go` 去掉空导入。
2. **测试改 memstore**：24 个测试文件逐个改，`tenontest.Stores()` 只留 memstore。
3. **删实现**：删除 `modules/storage/sqlite` 与 `modules/storage/store-sqlite`，
   `go.mod` 去掉 `modernc.org/sqlite`，`deps_test.go` 删掉两个例外。
4. **示例**：`examples/web-server` 改用 memstore。
5. **文档**：本篇标完成；04 模块清单、05 数据与存储、07 SDK、09 演进与验收里
   指向 `modules/storage/sqlite` 的改为「实现已迁出，见产品仓库」；`CHANGELOG.md`
   记破坏性变更；`scripts/doclinks.py` 0 坏链。

## 七、版本

破坏性变更，发 **v0.3.0**。破坏点：

- 删除 `modules/storage/sqlite`、`modules/storage/store-sqlite` 两个包。
- `apphost.Open()` 不再自带存储插件，调用方必须自己空导入一个提供 `service:db` 的组件。
- `tenontest.Stores()` 不再返回 sqlite 后端。

公开接口快照（`testdata/api.txt`）会有删除项，发版前按 07 篇 7.4.1 逐条核对。
