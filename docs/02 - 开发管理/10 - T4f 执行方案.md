## 二、交付物

1. **有效权限补两层上限**：被调用方处理一条信封时，有效工具 = 定义 `tools` ∩ `[use.permission]` ∩ `caps` ∩ 租户上限 ∩ 用户上限（本轮触发者）。只降不升。
2. **control 放行范围扩到本轮触发者**：多人会话里，本轮触发者（`from` 的 human）可中断本轮；非触发者、非创建者不行；`external` 仍一律拒绝。
3. **预算记账与挂起**：`budget_ref` 关联的每轮模型/工具用量累计；`[use.budget]` 三层取最小；用尽发 `budget.exceeded` 并转预算挂起，`Resume` 续跑。
4. **跳数上限租户可调**：`MaxHop` 改为可配，缺省 8；超限拒绝并记 `guard.denied`。
5. **13 13.5 定案落地**：按人分轮——一轮只合并同一权限主体（同一触发者、同一 `budget_ref`）的信封；不同主体分轮。

## 三、文件与类型（预估）

- `runtime/toolhub`（caps 求交处）：有效权限多并「租户上限」「用户上限」两层。看 `Agent.InstallCapsGuard` / caps 层最外层做法（09 9.6 T3 TestCapsRestrictToolCall）。
- `runtime/host`（信封投递 / control / hop）：
  - control 放行：`deliverSession` 里 control 的允许主体加「本轮触发者」（从会话当前回合的 from 取）。
  - hop：`MaxHop` 改从内核参数取（`assemble.Kernel`）。
- `runtime/agent`（预算记账）：模型/工具调用后累计到 `budget_ref`；`[use.budget]` 三层求最小；用尽 `Suspend(reason=budget)`。
- `runtime/agentdef` / `useconf`（预算与上限配置）：`[use.budget]`、租户/用户上限的读取与求交；`limit:"intersect"` 每轮按触发者重算（06 D8）。

## 四、验收（09 9.7）

多人会话里：
1. 低权限成员的消息触发不了高权限工具（本轮触发者的用户上限收窄有效工具）。
2. 两个权限主体的消息同时到达时分两轮处理（按人分轮）。
3. 本轮触发者可中断本轮（control 放行）；非触发者不能。
4. 预算：一轮用尽后转挂起，`Resume` 后继续；用量记在 `budget_ref` 主触发者账上。
5. 跳数：租户把上限调小后，超限投递被拒。

测试放 `runtime/host`（投递/control/hop）、`runtime/agent`（预算）、`permission`（有效权限求交），用真实 host + 两种存储。

## 五、13 13.5 定案：按人分轮

**定案 = 按人分轮。** 理由：08 8.3 已规定「一轮只合并同一权限主体的信封」；按群身份合并会与这条冲突，也让「低权限成员触发不了高权限工具」无法强制。敏感操作的个人确认由现有 `corr` 绑定触发者覆盖，不另做机制。`Envelope.Subject()`（from + budget_ref）即主体键；信箱批次收集已按 subject 分。

## 六、不显然的取舍

1. **租户/用户上限的读取层**：沿用现有 `[use.*]` 配置链（不做 `tenon.toml`/env 覆盖，06 现状差距留 v1 后）。
2. **预算记账粒度**：按 `budget_ref`（触发者账），不按会话；一轮只记主触发者账（D5）。
3. **hop 租户可调**：走 `[kernel]` 参数，profile 与 SDK `WithKernel` 都能设；缺省 8 不变。
4. **control 放行**：只放开「本轮触发者中断本轮」，不放开会话关闭等更大范围。

## 七、不做

- `tenon.toml` / 环境变量覆盖配置链（06 现状差距，v1 后）。
- 跨租户投递（任何地址都不行，8.8）。
- 群会话里按群身份合并权限（14 待定项已定案按人分轮，见五）。
