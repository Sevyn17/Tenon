## 二、交付物

1. 一条独立于会话的事件日志：组件发布的事件按全局序号只追加写入，SQLite 与内存两个实现，同一套一致性测试。
2. 组件经 `Registrar.On` 订阅；框架记住每个订阅者的读位点，进程重启后从记下的位置接着读，不漏不重。
3. 订阅方处理失败不影响主流程：记日志、重试有限次、用尽后跳过继续。
4. 发布在存储事务提交之后，事务回滚不产生事件。

## 三、文件与类型

### 3.1 存储（`runtime/store/eventlog.go`，新文件）

```go
// EventLog 组件事件日志（04 4.6）。可选接口，与 CollectionStore 同一规则：
// 没实现的存储照样能用，只是登记了订阅的组件启动时报"存储不支持事件日志"。
type EventLog interface {
    // Append 追加一条。Seq 由存储分配，全局单调；同一事务里追加的按调用顺序相邻。
    Append(ctx context.Context, e ComponentEvent) (seq int64, err error)
    // Read 返回 seq > after 的事件，按 seq 升序，最多 limit 条。limit 缺省 100、最大 1000。
    Read(ctx context.Context, after int64, limit int) ([]ComponentEvent, error)
    // Cursor 记住订阅者读到哪。name 是 "<组件>.<事件名>"。
    Cursor(ctx context.Context, name string) (int64, error)
    SetCursor(ctx context.Context, name string, seq int64) error
}

// ComponentEvent 一条组件事件（store.Event 已是会话事件）。
type ComponentEvent struct {
    Seq    int64           // 存储分配，从 1 起
    At     int64           // 毫秒；0 由存储补当前时间
    Source string          // 发布它的组件名
    Name   string          // <来源>.<动作>
    Data   json.RawMessage // 载荷；空写 {}
}
```

- 序号是全局一条序列，不按事件名分。订阅者按名字过滤，读位点记在全局序号上，这样新增订阅不用为每种事件各维护一条序列。
- `Append` 在 `Store.Tx` 里调用时，事件随事务提交才可见，回滚不留。sqlite 的 `Tx` 把事件暂存在事务视图上，外层提交成功后统一派发（与现有 `Commit` 的持久事件同一做法，`runtime/store/sqlite/db.go`）。
- 读位点只前进不后退：`SetCursor` 的 seq 小于已记下的值时拒绝。订阅方自己的去重靠这个保证：框架不会把同一条再交给它。

表（SQLite，新迁移，不复用 `session_events`）：

```sql
CREATE TABLE component_events(
    tenant TEXT NOT NULL, seq INTEGER PRIMARY KEY,
    at INTEGER NOT NULL, source TEXT NOT NULL, name TEXT NOT NULL, data TEXT NOT NULL);
CREATE TABLE component_cursors(
    tenant TEXT NOT NULL, name TEXT NOT NULL, seq INTEGER NOT NULL,
    PRIMARY KEY(tenant, name));
```

`seq` 用表内 `MAX(seq)+1`。两张表放进核心迁移 v14（`schema.go` 现到 v13），不另开版本表。内存实现用切片加互斥锁，语义相同。

### 3.2 登记（`runtime/component/plugin.go`）

```go
// On 订阅组件事件（04 4.6）。name 支持末尾 * 表示前缀（"session.*" 收 session. 开头的全部）。
// 同一组件对同一 name 只能登记一次。处理函数返回错误时框架重试，不进发布方的调用栈。
func (cx *Registrar) On(name string, fn func(ctx context.Context, e store.ComponentEvent) error) error
```

- 订阅在 `Assembly.Start` 里启动：存储打开之后、组件 `Start` 之前。每个订阅一个协程，从记下的读位点按 `Read` 逐段取，处理成功才 `SetCursor`。
- 发布不另开点位。组件要发事件就 `Need` 一个 `store.EventLog`，在自己的逻辑里 `Append`。内核自己发的（会话、投递）本步不改接这条日志：界面订阅已经走 `session_events`，改接会动协议层，超出 4.6 的缺口。

### 3.3 失败隔离

- 处理函数 panic 或返回错误：记宿主日志（组件名、事件名、序号、错误），按 1s、2s、4s 重试三次。
- 三次仍失败：记一条"跳过"，`SetCursor` 越过这条，继续下一条。不重试到永久，否则一个坏订阅会把后面的事件全部堵住，重启后仍然堵住。
- 发布方看不到这些错误。`Append` 的错误只表示"没写进日志"，由发布方自己决定是否放弃。

## 四、顺序

1. **接口与两个实现**。`EventLog`、SQLite 迁移与实现、内存实现、`storetest` 一致性用例：追加后按序读回、事务回滚不留事件、读位点只前进、`limit` 截断。`go vet`、`go test` 全绿后提交。
2. **登记与投递**。`Registrar.On`、`Assembly.Start` 里按读位点投递、失败重试与跳过。用例：订阅者读到 N 后停掉、重新 `Start` 后从 N 继续且不重复；处理函数返回错误时发布方的调用正常返回。提交。
3. **一个真实使用方**。选一个现成的"发生了什么"通知改走这条日志，证明不是只有测试在用。候选是 `guard.denied`（`runtime/host/envelope.go` 的 `guardDenied`）：现在只发总线事件，重启后看不到。改成同时 `Append` 一条 `guard.denied`，测试断言重启后订阅者能读到。不改界面协议。提交。

第 1 步没过不开始第 2 步。每步一个提交，决策日志各记一行。

## 五、验收

- 订阅者读到序号 N 后停进程，重新打开同一存储，从 N 继续，不漏不重（第 2 步的用例）。
- 订阅者返回错误时，发布方的调用不受影响，后面的事件仍会送达（第 2 步的用例）。
- 回归快照无差异：本步不改模型请求的内容。
- `go vet ./...` 与 `go test ./...` 全绿。
