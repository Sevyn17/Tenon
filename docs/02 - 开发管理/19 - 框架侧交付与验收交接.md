**2026-11-14 订正**：初稿写「16981 行」，这个数**复现不出来**。按迁出前最后一个提交
`eada285` 重算 `web/src` 下全部文件（含 `*.module.css`）是 **17198 行 / 92 个文件**，

### 1.2 `[[ui]]` 扩展点补上形状契约

把 `DeclNode`（15 种节点）与 `DeclAction`（4 种动作）的形状写进框架。

**为什么**：`UISlot.View` 是 `json.RawMessage`，原先只校验大小不校验形状。
前端迁出后，形状只在产品仓库的渲染器里，框架的扩展点变成「有定义、无约束」。

**2026-11-14 订正（初稿此处写「已一致」，不成立）**：契约初版是渲染器迁出**之后**
凭描述转写的，有四处 JSON 字段名与渲染器实际读的不一致：

| 节点 | 契约初版写 | 渲染器实际读 | 照初版写会怎样 |
|---|---|---|---|
| `code` | `text` | **`code`** | 代码块渲染成空 |
| `keyValue` | `keyValue` | **`rows`** | 键值对渲染成空 |
| `button` / `link` | `text` | **`label`** | 按钮没有文字 |
| `badge` 的 `tone` | 按 text 那套（default/muted/…） | badge 那套（neutral/accent/…） | 色调静默失效 |

已在 `v0.3.2` 按渲染器实现逐字段对齐。`button.variant` 一并补上 `ghost` / `outline`。

**2026-11-14 二次订正：契约搬了位置，并补上了校验与类型生成。**

初版把契约放在 `runtime/pkgs/declarative.go`，那是错的落点，也是上面那四处错误的根因：
框架里**所有**线上类型（`Entry`、`UISlot`……）都由 `appapi/wire` 定义、经 `tsgen` 生成到
`web/src/wire.gen.ts`。视图是 `UISlot.View` 的载荷，属于线上类型，之前是唯一的例外。
`pkgs` 属 `runtime/`，依赖规则禁止它 import `appapi`，所以它只能**复制**一份形状——
复制品没有任何手段与权威定义校验，于是安静地漂移了。

现在（`v0.3.2`）：

| 关注点 | 落在哪 |
|---|---|
| 形状定义 | `appapi/wire/declarative.go`，一张 `declKinds` 表 |
| 校验 | `wire.ValidateView`，在 `adapters/plugins` 加载包时调用（协议边界） |
| TS 类型 | 同一张表生成到 `web/src/wire.gen.ts`（`DeclNode` / `DeclAction` 可辨识联合） |
| 清单层校验 | `runtime/pkgs/ui.go`：大小、顶层 `type`、id/slot、`data.cmd` 只读 |

一张表驱动三件事，改一处不会漏掉另一处。校验规则：必填字段缺失报错、`action.kind`
非法报错、递归子节点；**未知 `type` 放行**（渲染器显示占位，前向兼容优先）。

**护栏**（都做过变异验证，故意改坏会红）：

| 测试 | 钉住什么 |
|---|---|
| `appapi/wire/declarative_test.go` | 表引用的字段真的在 `DeclNode` 上；校验器按表工作（含历史错误写法必须被拒）；生成的 TS 与表一致 |
| `runtime/pkgs/contract_ownership_test.go` | `pkgs` 不得再定义 `DeclNode` / `DeclAction` / `declKinds`——防止有人重新复制一份 |
| `adapters/plugins/plugins_test.go` 的 `TestLoadValidatesUIView` | 端到端：坏视图在加载时被拦下 |

**产品侧要做的**：渲染器不需要改代码（它本来就对）。因为 L2 层不得 import 协议客户端，
产品保留一份结构等价的 `DeclNode` 声明，并用**编译期双向可赋值断言**
（`src/shell/declarative-conformance.ts`）与生成的类型绑定——任一边漂移，`tsc` 立刻失败。
升级到 `v0.3.2` 后跑一遍 `pnpm typecheck && pnpm test` 确认。

**公开面变化**：`appapi/wire` 在承诺面内，本次**新增** 5 个导出符号
（`DeclNode` / `DeclAction` / `DeclNodeTypes()` / `DeclActionKinds()` / `ValidateView`），
无删除、无既有签名变更，`testdata/api.txt` 已更新。

## 五、框架与入口的关系（2026-11-13 补充）

产品侧问过「加了新模块，CLI 要不要跟着改」。查完代码的结论是**绝大多数不用改**：

| 新模块的形态 | CLI 要改吗 |
|---|---|
| 加工具（`modules/tools/xxx/`） | ❌ 不用，CLI 通用渲染 `⚙ 工具名 {参数}` |
| 加插件（`apphost/assemble.go` 加空导入） | ❌ 不用，三入口同时装 |
| 加协议命令（`appapi/v2.go`） | ❌ 不用（只是没有终端快捷方式） |
| 需要终端专属入口 | ✅ 要改（加子命令或斜杠命令） |

**框架侧要守住的**：`appapi` 不能出现「按入口分支」的代码（`if client == "cli"` 这类）。
**2026-11-14 已加约束测试**：`appapi/entry_boundary_test.go`，三条规则——

1. `appapi` 与 `appapi/wire` 不得 import 外壳与装配层（`apphost` / `adapters` / `transport` / `tenontest` / `examples`）；
2. 非测试源码不得出现 `cli` / `desktop` / `webhost` / `tui` / `gui` 字面量；
3. 不得读 `os.Args`（命令行参数属于入口）。

写测试时验证过它有效：往 `appapi/v2.go` 的 `Call` 里注入 `if os.Getenv(...) == "cli" { _ = os.Args }`，
两条用例立刻变红；恢复后变绿。详见产品侧 `05 - 入口架构与能力协商方案` 第 5.3 节。

## 七、存储实现迁出：先拆 SQL 依赖（2026-11-13 补充）

产品侧 `Mortise/docs/07 - 存储实现迁出框架方案.md` 提出把 SQLite 实现搬到产品仓库。
审查后**停掉搬家，先做前置的一步**，理由写在那一篇的「审查修订」节。这一步已经在框架里做完：

| 项 | 变化 |
|---|---|
| 投递账 | `p_workgroup_runs` 改为集合 `workgroup.runs`（固定分区 `runs`、索引 `state`、成员 id 作 key） |
| SQL 依赖 | `workgroup` 不再声明 `Requires{SQL: true}`；`service:sql` 改为可选（`?service:sql`），只用于把 v0.2.x 旧表搬进集合 |
| 装配 | 删掉 `tenon.go` 里「外部存储没有 SQL 出口时悄悄去掉 workgroup」的分支 |
| 标准组件 | 不再有组件把 `service:sql` 当必需依赖 |

**效果**：`memstore` 能装起全部标准插件，框架测试不必再为 workgroup 准备 `*sql.DB`。
旧库升级不受影响：有 SQL 出口时 `importRuns` 搬完删表（`TestImportRuns`），没有就跳过。

**已做完**（2026-11-13，v0.3.0）：SQLite 实现已迁出框架，`modules/storage/sqlite` 与
`modules/storage/store-sqlite` 两个包删除，`go.mod` 不再依赖 `modernc.org/sqlite`，
`runtime/assemble/deps_test.go` 的两个例外也已删除。详见 20 篇。

**v0.3.0 之后补的一处（`6708e0c`，CHANGELOG 记为 v0.3.1，随 v0.3.2 发布）**：
