# 18 内核与 I/O 分离方案

> 状态：**第 0、1、2 步已落地（2026-11-12）**。第 3–5 步未开始。
>
> 目标：框架内核（`runtime/`）不接触具体文件和数据库；「存哪、从哪读」由应用决定。
> 两种产品形态共用同一个内核：轻量嵌入（智能体只是别的软件的一块）和以智能体为中心的完整产品。
>
> 相关：配置源细节见第四节；落地步骤见第六节；进度见 `16 - 待办与遗留事项`。

## 一、原则与判断

1. **内核不接触数据层与文件层**。内核只定义接口与机制，不替应用决定数据存哪、配置从哪来。
2. **接口归内核，实现由框架提供，但放在内核之外、按需选装**。会话存储接口有 15 个方法，还要求条件写、写租约、旧节点写入拒绝等语义；让每个应用自己实现一遍容易出错。框架自带现成实现，并把一致性测试套件（`storetest`）公开，第三方实现可自检。
3. **配置不只有文件一种形式**。嵌入场景的配置直接是 Go 值；文件只是其中一种来源，且这种来源属于宿主层。
4. **工具读写工作区不算违规**。`fs`、`shell` 这类工具的功能本身就是读写工作区，它们是可选组件，嵌入方不开即可。

## 二、现状问题（2026-11-12 实测）

1. **根包 `tenon` 直接引用 SQLite 实现**（`agents.go` 的 `SQLiteStore` / `MemoryStore`）。
   任何人 `import tenon`，就算只用内存存储，也会把整个 SQLite 驱动编进程序。
2. **`runtime/` 里 10 个非测试文件直接调用 `os`**（profile、插件包扫描、智能体定义目录、appid 用户目录等），
   2 个文件引用 `net/http`（`modelhub`）。
3. **四套配置机制并存**：profile（只能从文件）、组件 `[plugin.*]`（跟着 profile）、`[use.*]`（已可注入）、
   组件私有文件（组件自己 `os.ReadFile` 并自己做分层合并）。
   `hooks.Setup` 约 60 行自己拼路径、判断受信、合并三层——这些是框架该做的事。

## 三、目标分层

```
runtime/          内核：只有接口和机制，不做任何读写
                  不引用 os / database/sql / net/http / modernc.org/sqlite

adapters/         框架自带的实现，各自独立成包，按需引入
  storage/sqlite    SQLite 存储（从 runtime/store/sqlite 搬来）
  storage/memory    内存存储（测试和嵌入用）
  config/file       从 TOML 文件读配置（按层：用户 / 项目 / 插件包）
  defs/dir          从目录读智能体定义

apphost/          独立运行的宿主：把 adapters 组装好，读用户目录和环境变量
```

两种用法：

```go
// 轻量嵌入：零文件、存储用宿主自己的
app, _ := tenon.New(
    tenon.Minimal(),
    tenon.WithStore(myPostgresStore),          // 宿主自己实现，跑 storetest 自检
    tenon.WithConfig("shell", shell.Config{Timeout: 60}),
)

// 以智能体为中心：用 apphost，文件和 SQLite 都已接好
rt, _ := apphost.Open(apphost.Options{Workdir: dir})
```

## 四、配置源设计（修正版，2026-11-12 拍板）

内核只定义层，不负责合并，也不规定格式。

**命名**：不能叫 `ConfigSource`。`tenon.WithConfigSource(useconf.Source)` 已经存在，
那是会话级 `[use.*]` 的租户 / 用户层（06 6.3），与这里的部署期配置是两回事。
新接口叫 `component.LayeredConfig`，SDK 选项叫 `tenon.WithLayeredConfig`。

```go
// runtime/component/layers.go

// LayeredConfig 部署期配置的来源（内核不关心是文件、数据库还是远程）。
// 应用经 tenon.WithLayeredConfig 注入，组件经 component.KeyLayers 取；
// 没注入时组件只用代码里给的值，不从外部取配置。
type LayeredConfig interface {
    // Layers 配置层，按「低优先级 → 高优先级」返回。
    Layers(ctx context.Context) ([]ConfigLayer, error)
}

// ConfigLayer 一层配置。
type ConfigLayer struct {
    Name    string         // 层名（explain / 报错用），如 "user"、"project"
    Origin  string         // 来源："user" / "project"。脱敏跟来源走，不跟层号走
    Trusted bool           // 由提供方判定；组件只认这个标记，不自己判断受信
    Where   string         // 出错时指给用户看的位置（文件路径、"数据库 xxx"），可空
    // Values 与格式无关的配置值，key 是文件标识（"hooks"、"permissions"、"mcp"）。
    // 值是解码后的通用结构（map / 切片 / 标量），组件按自己的结构体再解码。
    Values map[string]any
}
```

**组件怎么取**：经服务键 `component.KeyLayers`（`service:layers`）注入，
组件在 `Requires` 里写 `component.KeyLayers.Maybe()`，用 `component.GetOptional` 取。
没注入（嵌入场景的缺省）就当没有外部配置。这样内核不用认识「文件」，组件也不用认识「目录」。

**与初稿的修正**：

1. 默认实现（读文件）不放在 `runtime/`，放在 `adapters/configfile`。
2. 接口不返回 TOML 原始字节——那等于要求嵌入方先把配置写成 TOML 文本。
   返回与格式无关的值，组件按自己的结构体解码并决定合并方式。
3. 多一个 `Origin` 字段。脱敏（`scrub`：不把宿主密钥交给第三方命令）跟**来源**走，
   不跟层的位置走：用户来源不脱敏，项目来源和插件包来源脱敏。层顺序变了，这条不能变。
4. 插件包不进这个接口。插件包的钩子、MCP 服务是结构化的段（`[[hook]]`、`[[server]]`），
   还要做 `${TENON_PLUGIN_DIR}` 展开，和「一份配置文件」不是同一件事，继续走 `pkgs.Service`。
   插件包目录扫描已在第 4 步搬到 `adapters/plugins`，见第十节。

**合并仍由组件做**。hooks 是追加，permission 是按规则合并，没有统一的合并函数能两边都对。
所以不设 `Meta.Files`，框架不替组件解码合并——那会把各组件的合并规则搬进内核。

`[use.*]` 是会话级配置（每轮按触发者重算），与部署期配置不同概念，`useconf.Source` 保持独立不动。

## 五、例外（允许留在内核，写进允许名单并注明理由）

| 项 | 理由 |
|---|---|
| `toolhub/attrs.go` 引用 `os/exec` | 沙箱接口签名用到 `exec.Cmd` 类型，只有类型引用、没有实际读写；以后再看要不要换成抽象类型 |

## 七、已拍板（2026-11-12）

1. **插件包统一放第 ② 层：采纳，但 hooks 的执行顺序不变。**
   先说一处更正：之前说「插件包钩子排最后，所以能盖掉用户自己的钩子」，这个判断是错的。
   钩子不是覆盖关系，是按顺序执行、第一个阻止的即停（`hooks.go` 的 `Fire`）。
   排在前面的钩子一旦阻止，后面的就看不到这次调用。所以「谁排前面」才是能挡住谁。
   按这个事实，插件包钩子继续排在用户钩子**之后**执行：用户自己的钩子先看到调用，
   第三方的钩子阻止不了用户自己的审计钩子。profile 那边插件包本来就在用户层之前，
   两边一致的是「插件包盖不掉用户的设置」，不是层号本身。
   权限和 MCP 的插件包贡献保持各自现有的合并规则，不因为统一层号而改行为。
2. **保留 `project_hooks` 闸门。** 它不是多出来的一层，是执行闸门：项目级 `hooks.toml`
   会执行仓库里写的命令，而项目级 `permissions.toml` 只能加严（写 `allow` 直接报错），两者本质不同。
   「信这个仓库的代码」和「允许它在我机器上跑钩子命令」不绑成同一个决定。
   实现上：配置源照常给出项目层并标好 `Trusted`，hooks 自己决定要不要用——
   `project_hooks` 开了就用（即使项目不受信），否则只在 `Trusted` 时用。
3. **`mcp` 不加用户级。** `mcp.toml` 配的是连哪个服务、什么信任级别，跟具体项目绑定；
   `trust = "trusted"` 的服务按「写工作区」信任处理，做成用户级会悄悄作用于所有项目。
   跨项目复用 MCP 服务走插件包（`[[server]]` 段），不另开用户级文件。

**一个要守住的点**：脱敏（`scrub`）跟来源走，不跟层号走。用户来源不脱敏，
项目来源和插件包来源脱敏。层顺序怎么排都不改变这条。

**一个行为变化（如实记录）**：嵌入场景（`tenon.New` 不经 `apphost`）缺省不再读
`~/.tenon/hooks.toml` 和 `~/.tenon/permissions.toml`。原先组件自己拼路径去读，
等于一个嵌进别的软件的智能体悄悄吃掉开发者个人目录里的配置——那份 `permissions.toml`
里的放行规则不该自动套到宿主软件上。要文件配置的嵌入方显式传 `tenon.WithLayeredConfig`。
`apphost` 自己接上文件实现，独立运行的行为不变。

**models 不迁进配置层。** 它读的 `models.toml` 是调用方用 `tenon.WithModelCatalog(path)`
点名的文件，组件不自己拼 `~/.tenon` 路径，也不存在「嵌入场景悄悄读个人目录」的问题。
硬塞进配置层只会让「一份目录文件」变成层里的一个键，没有解决任何真实问题。
读文件仍在 `modules/`（不受内核禁令约束）。第 4 步核实后不抽成注入：
models 读的是调用方点名的文件，组件不自己拼用户目录，抽成注入只是换个写法。

**自定义档位目录（`modes/`）不搬。** 第 2 步曾把它留到第 4 步，核实后确认不该搬：
不是一份配置文件，塞进 `ConfigLayer.Values` 会把目录扫描重新搬进配置层。
permission 现在只把 `permissions.toml` 改成从配置层取，档位目录仍由 `ModeDirs` 读。

## 九、第 3 步的修正（2026-11-12，动手前核实）

第六节第 3 步原话是「`sqlite` 与 `memstore` 都搬到 `adapters/storage/`」。照字面做会让依赖规则测试直接失败，所以改成下面三条。改的是落点，不是目标：内核不再带着具体的数据库实现。

1. **SQLite 实现搬到 `modules/storage/sqlite`，不搬到 `adapters/`。**
   已有的标准模块 `modules/storage/store-sqlite` 直接调用 `sqlite.Open`（`plugin.go` 的 `Start`）。
   `adapters/` 是装配层，依赖规则（`runtime/assemble/deps_test.go`）禁止标准模块引用它。
   搬到 `modules/storage/sqlite` 后，引用它的只有这个存储模块、`apphost`、示例和测试套件，都是本来就允许的方向。
2. **`memstore` 留在 `runtime/store/memstore`。** 它是纯内存实现，不引用 `os`、`database/sql`、SQLite 驱动，
   不在内核禁令的范围内，也没有「编进驱动」的问题。`runtime/` 里约 25 个测试文件用它，
   而这些测试同样不许引用 `adapters/`。把它搬走会逼着要么放开这条规则，要么把测试换成桩。两条都不值得。
3. **`storetest` 留在 `runtime/store/storetest`。** 它只依赖 `store` 接口和 `testing`，没有任何实现，
   第三方实现现在就能 `import` 它自检，本来就是公开的。搬位置不增加任何能力。

**`store.SQL` 留在内核。** 它的方法签名用到 `*sql.DB`，所以 `runtime/store/sql.go` 引用 `database/sql`。
这是类型引用，不是读写：去掉它就要给「组件自有表迁移」另造一套不带 `*sql.DB` 的接口，
而现在只有 SQLite 一个实现，没有第二个方言来证明新接口是对的。允许名单里保留这一条，注明理由。

**测试引用单独放行一个包。** `runtime/` 有 12 个、`appapi/` 有 2 个测试文件用 SQLite 实现，
其中几处直接查表（`trace_spans`、会话的 `origin` / `parent_id`），`store.Store` 没有对应的读方法，
内存实现也做不到「关掉再打开仍在」。依赖规则拆成生产引用和测试引用：生产代码照旧不许引用标准模块，
测试只放行 `modules/storage/sqlite` 这一个包，不论测试在 `runtime/`、`appapi/` 还是标准模块里。
另外 `modules/storage/store-sqlite` 是这个实现的组件外壳，它引用自己的实现是职责，单独放行（`runtime/assemble/deps_test.go`）。生产代码里除此之外不许引用标准模块。

## 十、第 4 步的修正（2026-11-12，动手前核实，落地后订正）

第六节第 4 步原话是把 profile、插件包扫描、`agentdef.DirSource`、`appid` 的文件部分整包搬到 `apphost` 或 `adapters/`。照字面做会让依赖规则测试直接失败，所以只搬「决定路径、读写文件」的部分，解析留在原地。改的是落点，不是目标：内核不再自己决定路径、不再自己扫目录。

1. **`agentdef.DirSource` 留在内核，改成吃 `fs.FS`。** `tenon.Dir`、`runtime/pkgs` 都引用它，`runtime/` 不许引用 `adapters/`。目录布局、跳过符号链接、包大小上限这些规则是解析的一部分，留在内核；真正读盘的 `ReadDir` 换成 `ReadFS`，目录列举走调用方给的 `fs.FS`（读磁盘用 `os.DirFS`）。`FS(fsys, root)` 的 `root` 只写进错误信息，让坏定义仍能定位到包目录。
2. **插件包只把 `Load`、`Discover`、`HasAny`、`Scaffold` 搬到 `adapters/plugins`。** `Parse` 留在内核：hooks、mcp、skills、prompt 四个标准模块都调它，而标准模块不许引用 `adapters/`。`Parse` 里的 `os.Stat` 是校验清单里写的路径确实存在，和读文件是一件事，随 `Parse` 留在内核，记进允许名单并注明理由。`Load` 顺手引用的 `appid`（拼项目目录、生成信任提示）也一起搬走。包名校验留在内核（`pkgs.ValidName`），脚手架要用。
3. **`appid` 留在内核。** 它被十来个标准模块引用（skills、permission、store-sqlite、hooks、mcp、sandbox、fs、web、models、instructions），搬到 `adapters/` 这些模块就引用不上。它做的事是「按应用身份拼目录名、读一个环境变量」，不是读写文件。同样留在内核的还有 `assemble.EnvSecrets`：它是 `env:` 凭证引用的缺省实现，只读一个环境变量。两条都记进允许名单，注明理由。
4. **profile 的读和写拆开。** `LoadProfile` 与 `EditProfile` 的调用方只有 `apphost`，搬到 `adapters/profile`（导出名改为 `Load`、`Edit`、`Revision`）。`ParseProfile`（文本进、结构出）留在内核。include 展开需要再读文件，所以 `ParseProfile` 多一个读文件回调，由 `adapters/profile` 注入；`apphost` 的内置 profile 不写 include，回调传 nil。`ErrRevision` 与 `PluginEdit` 留在内核：`appapi` 引用它们，而 `appapi` 不能引用 `adapters/`。
5. **`modes/` 自定义档位目录不搬。** 它在 `modules/security/permission`，本来就不受内核禁令约束，也不属于「内核接触文件」。第 2 步把它留到第 4 步，是因为想塞进配置层；核实后确认不该塞：它是一整个目录、按 mtime 刷新、带继承链，和「一份配置文件」不是同一件事。维持现状。

**落地后与上面三条预期不符，订正如下：**

- 内核并不是「只剩 `appid` 和 `EnvSecrets` 引用 `os`」。`Parse` 留在内核，连带 `pkgs/pkgs.go`（校验清单路径、读提示词片段）、`pkgs/ui.go`（`view_file` 在解析时读）也留着。`pkgs/agents.go` 把清单点名的目录交给 `agentdef.FS`，用的是 `os.DirFS`，目录由调用方给，不是内核自己扫。这三条都记进允许名单，注明理由。
- `runtime/assemble` 并不引用 `agentdef.DirSource` 的目录实现，它只拿 `agentdef.Source` 接口。原计划里写它引用，是核实前的误判。
- 改写文件用的 TOML 结构在 `adapters/profile` 复制了一份。内核的对应类型不导出；导出它会把文件格式细节变成公开面。字段必须与内核保持一致，测试覆盖「改写后再读回来」这条。

**models 的「按路径读文本」不抽成注入。** 第 2 步留的这句话，核实后没有真实需求：models 读的是调用方点名的文件，组件不自己拼用户目录。抽成注入只是换个写法，不解决任何问题。

**Mortise 直接引用了搬走的 `pkgs.Scaffold`**（`client/mortise/plugin_cmd.go`）。它的 `go.mod` 固定在已发布的 `v0.1.2`，不引用本仓库的工作区，所以这次改动不会让它当下编译失败。下次它升级 tenon 时，这一处要改成 `adapters/plugins`。

## 十一、第 5 步的修正（2026-11-12，动手前核实）

第六节第 5 步原话是把 `modelhub` 的 HTTP 辅助移出内核，并让模型适配器允许注入 `http.Client`。后半句动手前就已是现状：三个适配器的结构体都有 `HTTP *http.Client` 字段，`PostSSE` 在它为 nil 时用 `http.DefaultClient`。注册时传的是零值，所以实际走默认客户端。这条不需要新加东西。

前半句照字面搬到 `adapters/` 会让依赖规则测试直接失败：`PostSSE`、`RunStream`、`HTTPFailure` 的唯一调用方是三个模型适配器（anthropic、openai-chat、openai-responses），它们都是标准模块，不许引用 `adapters/`。

**落点是 `modules/internal/httpx`。** `modules/internal/*` 是已有的「标准模块共用辅助包」机制（05 3.2，依赖规则已放行），不用新增例外。搬过去的是 `PostSSE`、`RunStream`、`SSERequest`、`HTTPFailure` 和对应测试。`ContentString` 不碰网络，留在 `runtime/modelhub/helpers.go`。内核禁令名单去掉 `modelhub/helpers.go` 与 `modelhub/sse.go` 两条，`runtime/` 不再引用 `net/http`。

## 八、验收
