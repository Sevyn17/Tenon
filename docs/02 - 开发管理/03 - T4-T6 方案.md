# 03 T4–T6 方案

> 状态：生效（2026-11-10）。本篇是 T4–T6 的排期与拆分；每步的设计内容与验收标准仍以 [框架设计/09](<../01 - 设计文档/框架设计/09 - 演进与验收.md>) 的 9.7–9.9 为准，行为边界以对应篇（04、05、08、13）为准。进度回填 [01 - 开发计划](<./01 - 开发计划.md>)。
>
> 原则沿用 v1：每步可独立交付，用现有测试做回归；迁移只加表、加列、加索引；公开接口变化按 07 7.6 弃用规则处理。

## 二、依赖与顺序

```
T4a Collection → T4c 资源与订阅 → T4e 小组模块 → T4f 多人会话与权限
T4b 持久事件（独立，只依赖现有 bus 与存储）
T4d 插件包带定义 + explain 视图（独立）
T5a 常驻（依赖 T3 信封，不依赖 T4）
T5b 定时与外部事件入口（依赖 T5a：验收要投常驻会话）
T5c 模型判断类匹配器（依赖 T4c 的订阅与匹配器点位）
T6a 远端地址与 Agent Card（依赖 T3 守卫，不依赖 T4/T5）
T6b 扩展进程协议（依赖 T4c 的资源类型 / 匹配器点位与 T5c 的匹配器登记）
```

建议执行顺序：T4a → T4b → T4c → T4d → T4e → T4f → T5a → T5b → T5c → T6a → T6b。

能并行的只有 T4b、T4d、T5a、T6a 四步（彼此不改同一批文件）。T4e 与 T4f 必须串行：都改小组模块与投递守卫。T6b 放最后：它把前面开的点位暴露给外部进程，点位没定型之前做协议是返工。

## 三、T4 资源、集合、事件、插件、小组

### T4a `Collection`（05 5.6）

- `store.Store` 增加 `Collection(owner, name string, spec CollectionSpec) (Collection, error)`，SQLite 与内存两个实现，进 `storetest` 同一套一致性测试。
- 四种操作：`Get`、`Put`（`ifVersion` 条件写，0 表示必须不存在）、`Delete`、`Query`（按声明的索引等值查，带分页）。明确不做查询语言、关联查询、聚合。
- 集合全名由框架加组件前缀 `<组件名>.<name>`，组件只能经 `Registrar.Collection` 拿自己的；租户由框架从 ctx 填，组件不能指定别的租户。
- 迁移：`Registrar.Migration`，`After` 声明跨组件依赖，进度记 `schema_versions`，失败拒绝启动。沿用"只加不改"。
- 事务：`Store.Tx` 里用 `tx.Collection(c)` 绑定句柄，只能写同一分区（租户 + `Partition` 字段值）。memstore 的 `Tx` 仍只做执行分组、不保证回滚，与 T3 的既有约定一致，文档与用例注明。
- **验收**：`storetest` 新增集合一致性用例，两个实现都过；workgroup 的 `p_workgroup_tasks` 改为 `Collection`（`Put` 的 `ifVersion` 替代现在的 `rev` CAS）；回归快照无未说明差异。`p_workgroup_runs` 仍是投递账、走 SQL，`Requires{SQL: true}` 留到投递账也迁走再删。文件、类型与顺序见 [04 - T4a 执行方案](<./04 - T4a 执行方案.md>)。

### T4b 持久事件（04 4.6）

- 现状是事件在内存总线里带 `seq`，`Follow` 的回放来源是会话日志。缺的是一条独立于会话日志的持久事件日志：进程重启后订阅者按自己记住的序号接着读，至少一次送达。
- 新增事件日志表（序号单调、来源、动作、载荷），`bus.Source` 增加该日志作为回放来源；订阅者登记自己的读位点，重启后续读。
- 失败隔离维持 04 4.6 的边界：订阅方处理失败不影响主流程，记日志、按策略重试；订阅者按序号去重，幂等由订阅方保证。
- 不在本步做的：跨机器续读。那要远端传输，归 T6a；本步只保证同一存储上的进程重启可续读。
- **验收**：订阅者读到序号 N 后杀进程，重启后从 N 继续，不漏不重；订阅者返回错误时主流程（回合、投递）不受影响。文件、类型与顺序见 [06 - T4b 执行方案](<./06 - T4b 执行方案.md>)。

### T4c 资源与订阅（04 4.7、05 5.8）——完成（2026-11-10）

- 资源类型点位 `Registrar.ResourceType` 与匹配器点位 `Registrar.Matcher` 落地。内核只内置程序规则匹配器（精确、前缀、名单）；模型判断类匹配器归 T5c。
- 资源与订阅的存储走 T4a 的 `Collection`，不新建专用表（05 5.8 的"资源与订阅"行由此满足）。
- 订阅扇出：资源产生记录时，按订阅关系与匹配器决定投给哪些会话，投递走现有信封与守卫，不新开通道。
- **验收**：注册一个资源类型、两条订阅、一个精确匹配器，记录进来后只有匹配的订阅者收到信封；守卫照常生效（联系名单、跳数）。文件、类型与顺序见 [07 - T4c 执行方案](<./07 - T4c 执行方案.md>)。

### T4d 插件包带定义 + explain 视图——完成（2026-11-10）

- 插件包清单增加 `agents` 字段，指向包目录内一个 `agentdef.Dir` 布局的目录，加载时走 `agentdef` 的同一套校验与信任规则：项目级包只在受信时加载。定义按目录布局归入平台 / 租户 / 用户三层，不新增命名空间；同名定义用户级包优先于项目级包。
- `explain` 补插件包视图：包名、来源、清单路径、内容摘要、贡献的定义。插件包没有开关位，开关不在本步做。
- **验收**：一个只含 `tenon-plugin.toml` 与定义文件的目录，不写 Go 代码，装上后定义出现在可用定义列表里，`explain` 能看到它；取消受信后项目级包的定义不再加载。文件、类型与顺序见 [08 - T4d 执行方案](<./08 - T4d 执行方案.md>)。

### T4e 小组模块（13 13.4）

- 新模块 `modules/collab/group`：群记录存 `Collection`（序号单调），投递规则按 13 篇的例子实现。
- 每个机器人在每个群一个会话，会话键 `key=群 id`，不跨群共用。
- 只有 @ 才投 `wake`；唤醒时按该机器人的已读位置一次补齐背景，不逐条投递。
- 机器人发言只有 @ 了别的机器人才唤醒对方，`hop` 上限兜底。
- 智能体提问的 `corr` 与本轮触发者绑定，只有触发者能回答。
- 转人工开关（缺省关闭）：打开后会话挂上一个小组，三方发言都先入组记录；人工客服是人，没有自己的会话。
- **验收**（09 9.7）：用两个定义文件加一个资源配置拼出"带 @ 的小组"，不写 Go 代码；A 被 @ 时 B 不收到信封，B 后来被 @ 时背景里含 A 的回复。

### T4f 多人会话与权限收尾（08 8.3、02 2.4）

- 多人会话里本轮触发者可以中断本轮（`control` 放行范围扩展，02 2.4）。
- 有效权限补上租户上限与用户上限两项求交（08 8.3 现状差距：现在只做了 `tools` ∩ `[use.permission]` ∩ `caps`）。用户指本轮触发者，不是会话创建者。
- 预算按 `budget_ref` 记账与挂起（08 现状差距：字段已有，只参与分轮，不记账）。
- 跳数上限租户可调（约束清单已登记缺省 8，本步接租户配置）。
- 13 13.5 的待定项在本步定案：**按人分轮**。理由：08 8.3 已规定"一轮只合并同一权限主体的信封"，按群身份合并会与这个规定冲突，也让"低权限成员触发不了高权限工具"无法强制。敏感操作的个人确认由现有 `corr` 绑定触发者覆盖，不另做机制。
- **验收**（09 9.7）：多人会话里低权限成员的消息触发不了高权限工具；两个权限主体的消息同时到达时分两轮处理。

### T4 不做的

- `SessionLocal[T]`（04 4.9，资源模型的一部分）与六个点位统一（同篇）仍留 v1 后，不塞进 T4。理由：小组与订阅不依赖它们，放进来会把 T4 从"交付能力"变成"顺手重构"。
- 配置链的 `tenon.toml` 与环境变量覆盖（06 现状差距）不在 T4。T4f 的租户上限沿用现有 `[use.*]` 配置链。

## 四、T5 常驻与外部入口

### T5a 常驻定义（02 2.2、D6）

- `agentdef` 去掉 `resident = true` 的"未支持"报错。
- 每租户一个会话，固定 id `resident:<租户>/<名字>`，唯一性靠固定 id，不走会话键。创建者记 `system:<租户>`，用户层使用配置不参与。
- 发往 `agent:<名字>` 时按该 id 查找：存在就投，不存在就建。
- 可休眠、不回收；进程重启后有待处理信封才唤醒（复用 T2a 的休眠与扫描）。
- 守卫不变：别人能否联系它只看 `agent:` 的定义守卫。
- **验收**（09 9.8）：两个节点同时向常驻定义投递，只产生一个会话；重启后无待处理信封不唤醒，有则唤醒且上下文连续。

### T5b 定时与外部事件入口（13 13.4）

- 统一入口把定时触发与外部事件转成信封：`origin = external`（由入口类型决定，组件不能自己声明）、`mode = wake`，`from` 为 `component:<组件名>`。
- 目标二选一：常驻会话，或 `agent:<名字>` 不带 key（每次新建）。
- 定时的调度本身用现有进程内调度即可，不引入外部调度器。webhook 入口走 `transport`，鉴权与现有令牌机制相同。
- **验收**（09 9.8）：用定义文件拼出 Router + Worker，外部事件进来后由 Router 分发到 Worker，全程不写 Go 代码。

### T5c 模型判断类匹配器（04 4.7）

- 只能由组件登记，内核与扩展进程都不能内置。
- 每次判断的模型开销记入订阅者预算（接 T4f 的预算记账）。
- 判断失败按"不匹配"处理，不阻塞扇出。
- **验收**：一个模型匹配器订阅，预算用尽后停止判断并记 `guard.denied` 类事件，其余订阅不受影响。

## 五、T6 远端

### T6a 远端地址与 Agent Card（08、11）

- `remote:<host>/agent:<名字>` 可投递。传输出站复用 `transport`，入站复用现有令牌 + Host / Origin 检查。
- 本地定义的公开部分导出 Agent Card（名字、描述、公开工具清单），不导出提示词、权限与使用配置。
- 跨机器调用时联系名单、权限交集、预算记账照常生效：`caps` 仍由发送方内核写入，接收方再与自己的权限求交。
- 事件的跨机器续读（T4b 留的口）在本步补：续读请求带序号，响应走同一传输。
- **验收**（09 9.9）：跨机器调用时，接收方定义不在发送方联系名单内被拒绝；接收方权限窄于 `caps` 时按接收方权限执行；预算按 `budget_ref` 记在发送方。

### T6b 扩展进程协议（04 4.8）

- stdio 上的 JSON-RPC 2.0，MCP 的超集。握手时报告要登记的点位，框架按 4.2 的规则检查，等同一次 `Setup`。
- 只开这些能力：工具、`ToolCall` 与 `Deliver` 两个中间件点位、事件订阅、匹配器、资源类型、渲染器。
- 明确不开：`Guard`、`Provide` 服务、`ModelCall` 与 `Context` 点位。守卫规则只能来自编译进程序的代码。
- 一个插件进程服务所有会话，请求带租户、会话 id、触发者，靠 JSON-RPC 请求 id 并发。不可信插件可配置按租户各起一个进程。
- 监管：崩溃退避重启，缺省连续 5 次后标记不可用，发 `plugin.crashed`；不可用期间中间件按登记的 `fail_open` / `fail_closed` 处理，缺省 `fail_closed`。
- 04 4.8 声明：实现时以 04 篇为准，归档的 [10 - 框架模块/16](<../90 - 归档/10 - 框架模块/16 - 扩展进程协议.md>) 作废，不从它抄行为。
- **验收**：一个外部进程贡献一个工具与一个 `Deliver` 中间件，杀进程后框架按退避重启；超过次数后该工具调用返回错误且主流程继续；该进程尝试登记守卫时握手被拒绝。
