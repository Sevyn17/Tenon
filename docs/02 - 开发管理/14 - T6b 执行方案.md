# 14 T6b 执行方案

> 状态：生效（2026-11-11）。T6b「扩展进程协议」是最后一步，协议一旦发布就不能改（[03 T4-T6 方案](<./03 - T4-T6 方案.md>) 第六节）。实现以 [04 4.8](<../01 - 设计文档/框架设计/04 - 扩展模型.md>) 为准；归档的 `90 - 归档/10 - 框架模块/16` 作废，不从它抄行为。

## 一、现状核对

- 扩展进程协议（第 3 档插件）尚不存在。第 1 档插件包（T4d）、第 2 档 MCP（已实现）在前。
- 组件登记点位：`Registrar.RegisterAt`（工具、层、系统块、事件订阅 `On`、匹配器 `Matcher`、资源类型 `ResourceType`、渲染器）。
- 组件规范：`component.Component`（Meta/Setup/Start），`Registrar` 是登记面。

## 二、协议边界（04 4.8 硬边界）

- **stdio 上的 JSON-RPC 2.0**，MCP 的超集。
- **握手报告要登记的点位**，框架按 04 4.2 规则检查，等同一次 `Setup`。
- **只开这些能力**：工具、`ToolCall` 与 `Deliver` 两个中间件点位、事件订阅、匹配器、资源类型、渲染器。
- **明确不开**：`Guard`、`Provide` 服务、`ModelCall` 与 `Context` 点位。守卫规则只能来自编译进程序的代码。

## 三、交付物

1. **进程监管**：一个插件进程服务所有会话；请求带租户、会话 id、触发者，靠 JSON-RPC 请求 id 并发。不可信插件可配置按租户各起一个进程。
2. **握手**：插件进程报告要登记的点位（工具清单、中间件、订阅、匹配器、资源类型、渲染器），框架校验范围（只允许上面的能力，越界握手被拒）。
3. **调用回桥**：框架把工具调用 / 中间件 / 事件投给进程，进程返回结果。工具与中间件按登记的 `fail_open` / `fail_closed` 处理失败（缺省 `fail_closed`）。
4. **崩溃退避重启**：连续 5 次崩溃后标记不可用，发 `plugin.crashed`；不可用期间中间件按缺省 `fail_closed`，该工具调用返回错误，主流程继续。

## 四、文件与类型（预估）

- `runtime/extproc`（新包）：JSON-RPC 2.0 编解码、握手结构（`Handshake{Points}`）、连接、请求/响应路由、进程生命周期与退避重启。
- `runtime/component`：把 extproc 的登记项接到现有 `Registrar`（工具/中间件/订阅/匹配器/资源类型/渲染器）。
- `modules/extend/extproc`（组件）：装配一个外部进程插件，`Setup` 走握手登记，`Start` 起进程，`OnClose` 杀进程树。
- 复用 `modules/internal/proc`（进程启动与杀进程树，shell/hooks/mcp 共用）做进程管理。

## 五、验收

1. 一个外部进程贡献一个工具与一个 `Deliver` 中间件，框架能用。
2. 杀进程后框架按退避重启。
3. 超次数后该工具调用返回错误、主流程继续。
4. 该进程尝试登记守卫时握手被拒绝。

## 六、不显然的取舍（决策日志记）

1. **能力只开子集**：工具 / ToolCall 与 Deliver 中间件 / 事件订阅 / 匹配器 / 资源类型 / 渲染器。守卫、服务、ModelCall、Context 一律不开——守卫必须编译进程序（安全边界）。
2. **握手即 Setup**：把外部进程的点位登记映射到现有 `Registrar`，不新造登记模型。
3. **缺省 fail_closed**：不可信插件失败时按拒绝处理，主流程继续（不阻塞）。
4. **一进程多会话 + 按租户分进程（可选）**：JSON-RPC 请求 id 并发。

## 七、依赖与风险

- 依赖进程管理（`modules/internal/proc`）与 JSON-RPC 编解码。
- 风险最大：协议一旦发布不能改；点位范围以 04 4.8 为硬边界，超范围就是返工。必须有握手越界被拒的反例测试。

## 八、落地状态（2026-11-11）

已落地（协议层与进程监管，可独立验证）：
- **`runtime/extproc`**（协议包）：JSON-RPC 2.0 `Request`/`Response`/`RPCError` 编解码；`Handshake{Version, Capabilities, Middleware, Tools, Matchers, Resources}`；`Validate` 强制 04 4.8 硬边界——能力只开 `tools/middleware/events/matcher/resource/renderer`，中间件点位只开 `tool_call/deliver`，**`guard`/`provide`/`model_call`/`context` 一律拒**，版本不一致或没报能力也拒。`TestHandshakeAllowsSubset` / `TestHandshakeRejectsOutOfScope` / `TestEncodeDecodeRequest`。
- **`modules/extend/extproc`**（进程监管）：`Supervisor` 启动外部进程、接 stdin/stdout、崩溃按指数退避重启、连续 `MaxCrashes`（缺省 5）次后标记不可用并回调 `OnUnavailable`、`Stop` 杀进程树且不再重启（复用 `modules/internal/proc`）。`TestSupervisorUnavailableAfterCrashes` / `TestSupervisorStopNoRestart`。

**2026-11-11 补充（回桥主线已通）**：`runtime/extproc.Conn` 在 stdio 上跑 JSON-RPC 2.0 请求-响应循环（按 id 并发路由、ctx 取消、断连唤醒）；`Handshake.ToolSpecs` 报告工具（必须声明 tools 能力）；`modules/extend/extproc` 组件起进程 → 握手 → Validate（越界拒绝启动）→ 按 ToolSpecs 登记会话工具，工具调用经 `tools/call` 转发（60s 超时、fail_closed）。端到端用例 `TestConnHandshakeAndCall`（本测试二进制当子进程）与 `TestHandshakeGuardRejectedE2E`。

**2026-11-11 再补（中间件与事件订阅已通）**：协议加 `MiddlewareCall`/`MiddlewareResult`/`EventNotice` 与 `Handshake.Events`，`Validate` 交叉校验（报中间件须声明 middleware、报事件须声明 events、报匹配器/资源类型须声明对应能力）。组件把握手从 `Start` 提前到 `Setup`（否则拿不到 events 清单无法登记 `On`；事件名不支持全通配，只能用具体名或前缀 `x.*`），按 events 逐个 `cx.On`、按 ToolSpecs 登记工具、注册 `tool_call` 中间件层（deny 即拒、可改写 args、失败 fail_closed）。用例 `TestMiddlewareDeny` / `TestHandshakeMiddlewareAndEvents`。

**2026-11-11 再补（匹配器与资源类型/渲染器已通）**：协议加 `MatcherSpec` / `ResourceSpec` 与 `MatchCall` / `MatchResult` / `RenderCall` / `RenderResult`；`Validate` 交叉校验（有 MatcherSpecs 须声明 `matcher`、有 ResourceSpecs 须声明 `resource`、声明缺名字也拒）。组件按握手声明用 `cx.Matcher` 登记匹配器（判断经回桥 `matcher` 方法转发给进程，失败按不匹配、不阻塞扇出）、用 `cx.ResourceType` 登记资源类型并把 `Render` 转发给进程（`render` 方法，失败退回记录正文）。用例 `TestMatcherAndRenderBridge`（命中/不命中 + 渲染格式）/ `TestHandshakeSpecCapMismatch`。

> 注：04 4.8 的「渲染器」就是 `ResourceType.Render`，不是独立点位，所以登记资源类型即覆盖渲染器能力。

**已落地的能力面**（对照 04 4.8 允许清单）：工具 ✅、`tool_call` 中间件 ✅、事件订阅 ✅、匹配器 ✅、资源类型 ✅、渲染器 ✅（随资源类型）。真实 stdio 请求-响应循环见 `runtime/extproc.Conn`。

**2026-11-11 再补（`deliver` 中间件已通）**：内核落了 04 4.3 的洋葱式中间件链（见下条决策日志），extproc 组件据此用 `component.Wrap(cx, component.Deliver, ...)` 登记 `deliver` 中间件——信封经回桥交给插件决定放行/拦截（deny → `Delivered:false` 不报错；回桥失败 → 错误，fail_closed）。用例 `TestDeliverMiddlewareBridge`。

**已落地的能力面（对照 04 4.8 允许清单）**：工具 ✅、`tool_call` 中间件 ✅、`deliver` 中间件 ✅、事件订阅 ✅、匹配器 ✅、资源类型 ✅、渲染器 ✅（随资源类型）。

**仍未落地**：不可信插件按租户分进程（部署层，需真实多租户需求）。

1. **`deliver` 中间件点位** —— 不是「补一个桥接」能做完的，它卡在**内核还没有洋葱式中间件链**：
   - 04 4.3 规定同步扩展只有一种形式：`Middleware[Req,Resp]` + `Point[Req,Resp]` + `Wrap(r, p, mw)`，`Deliver` 点位包住「一封信封投递到会话信箱」，用途是过滤 / 改写 / 按规则转投别的 `session:`。
   - 当前代码里 `Wrap` / `Point[Req,Resp]` / `DeliverReq,DeliverResp` **都还没有实现**（`Renderer(kind, rd)` 同样没有）。现有的 `ToolCall` 中间件是用 `SessionLayer`（工具层）近似的，不是 4.3 的中间件链。
   - 所以 `deliver` 中间件要先在内核落「中间件链」这一特性（新增点位类型、泛型 `Wrap`、在 `Host` 投递路径上插链），属于**内核架构改动 + 公开 API 变化**，不是 T6b 的桥接工作量。建议单独立项做 4.3 中间件链，之后 extproc 的 `deliver` 桥接只是几行。
2. **不可信插件按租户分进程** —— 需要进程池与租户路由，属部署层，可在有真实多租户需求时再做。
