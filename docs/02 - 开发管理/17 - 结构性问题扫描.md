## 一、问题是什么：四条信号

这类缺陷的形态是：**一个类型 + 一个判别字段，字段含义随判别值变化**，于是必须靠运行时检查补救。
`toolhub.Layer` 是最典型的例子（`Guard` 布尔同时编码「拒绝权」和「排序位置」，`Timeout`/`FailOpen`
只对其中一种有效）。

判断口诀：**注释里出现「只对」「仅在」「无效」这类限定词，就是拆的信号。**

四条信号（出现任一条就该拆）：

| # | 信号 | 例子 |
|---|---|---|
| 1 | 布尔字段 + 注释说「只对 X 有效」 | `Layer.FailOpen // 只对 Transform 有效` |
| 2 | 字段含义随另一个字段的取值变化 | `Guard:true` 时 `FailOpen` 无意义 |
| 3 | 需要运行时检查来防止误用 | `if out.Kind == Confirm && !l.Guard { 报错 }` |
| 4 | 一个字段同时表达「是什么」和「在哪/权限」 | `Guard` 既表权限又表排序 |

## 二、已修（历史记录）

### P1 `toolhub.Layer` → `Transform` + `Gate` + `Authorizer`（`58d5676`）

- **原形态**：`Guard`（拒绝权 + 排序）、`Authorizes`（谁是拍板的）、`Timeout`/`FailOpen`（只对改写层有效）
- **修法**：拆成 `Transform`（只能改）/ `Gate`（只能判，可并行）/ `Authorizer`（可挂起问人）。
  执行链：改写链 → 准入判定（并行 reduce）→ Authorizer → 执行器
- **收益**：`Gate` 并行、`Gate` panic 自动 fail-closed、误用编译不过
- **详见**：[15 - 扩展点重构方案](<./15 - 扩展点重构方案.md>) 第六节

### P2 `modelhub.Layer`（`9263632`）

- 同一反模式，且**生产零调用**（死代码）。删层机制。
- **注意**：R2 结构校验（`CheckShape`，防中间件偷偷放宽工具集）必须保留，
  改由 `agent.sendModel` 在 ModelCall 中间件链之后调用。

### P3 `instructions.Layer()` 死代码（`58d5676`）

- 已被 `Middleware()` 取代、无人调用，但带着 `Timeout`/`FailOpen` 误导维护者。删。

### H1 `WrapGuard` 判定从未接线（`b15fa80`）—— 安全

- **症状**：`WrapGuard` 只写进 `Assembly.guardsByPoint`，**全仓无生产代码调 `EvalPoint`**。
  redact 的 `WriteGuardFn`（拦「把脱敏占位符写回文件」）注册成功、函数级单测绿，
  但**真实会话里永不触发**（数据损坏防护失效）。
- **根因**：第 2 步迁 redact 时，原来 `redact-guard` 是 `SessionLayer` 的 Guard 层（会真跑），
  改成 `WrapGuard` 后没接线。**测试测的是函数，不是接线。**
- **修法**：`Builder.PointGuards` + `Build` 里 `AddGate("component-guardpoint")` 调 `EvalPoint`；
  `Wire` 用 `pointGuards(asm)` 注入（没登记时 nil）。用例 `runtime/assemble/pointguard_test.go`。
- **2026-11-12 核查补充（重要）**：接线修好了，但**真实用户默认仍拿不到 redact**——
  `apphost`（CLI/桌面端）走 profile 装配，只看 `Meta.Default`，而 **redact 没有 `Meta.Default: true`**。
  这是**有意设计**（[04 - 核心与扩展模块清单](<../01 - 设计文档/04 - 核心与扩展模块清单.md>) 第 143 行写明），
  且 `presets_internal_test.go` 的 `TestDefaultIsEveryStandardComponent` 强制「`Default()` = 所有标准组件」。
  **影响**：`tenon.Default()` 26 个组件，apphost profile 路径只启用 16 个（少 redact/skills/hooks/
  sandbox/code-mode/mcp/todo/web/subagent/workgroup 共 10 个）。要不要给这些组件补 `Meta.Default: true`
  是**产品决策**，不是 bug——记在下面「待决策」一节。

### M8 `Tool.Dangerous()` 文档承诺是假的（`5acd7a6`）—— 安全

- **症状**：文档说「权限插件按档位要人确认（缺省档位下也要）」，但只设 `Risk = Dangerous`，
  而 `modules/security/permission` **完全不读 `Risk`**（读 `AttrDestructive`）。
  所以 `Dangerous` 与 `Writes` **行为完全等价**。
- **修法**：`Dangerous` 同时设 `attrDestructive`，permission 的「声明破坏性 → AskUser」逻辑即生效。
  用例 `dangerous_test.go`。

### D1 组件默认开关：**已决策，不是待决策**（2026-11-12 结案）

**结论：默认关闭是既定原则，不改。**

依据（`03 - 约束清单`，不是推测）：

- **第 19 行**：「默认开启的插件只保留『没有它就不能正常工作』的那些。其余由用户开启。
  **开启后会改写模型所见内容的插件（如脱敏），要在 `explain` 和启动横幅里明示。**」
- **第 203 行**（2026-10-31 决策记录）：「缺省关闭 skills / redact / hooks / mcp / web /
  subagent / workgroup / code-mode，需要时在 `~/.tenon/profile.toml` 或受信项目的
  `.tenon/profile.toml` 写 `enabled = true`」
- **第 90 行**：「沙箱 | 插件缺省关闭；开启后沙箱级别随档位」
- **`sandbox` 的 `Meta` 显式写了**：`Default: false, // 独立开关，缺省关闭（§9.9）`

**为什么不改成默认开**：

1. 按第 19 行原则，默认开只保留「没有它就不能工作」的（models / store / prompt / permission）。
   `redact` 属于「改写模型所见内容」，按原则就该明示后由用户开。
2. **安全透明度**：脱敏会改写工具输出。默认开 + 用户不知情，比默认关 + 明示开启更糟。
3. **平台限制**：`sandbox` 只在 Windows 有实现，其他平台开了是 no-op 还告警。

**真正的问题不是默认值，是「明示」没实现** —— 见下面 H5。

  - 开启 `redact` 时启动提示里出现明示
  - 关闭时不出现

- **优先级**：**提到第 1 步之前**——它是约束清单的明确要求，且实现成本低（利用已有 `Notes`）

### D2 M2+M3 拆 `Item` 的替代方案（2026-11-12 评估）

**原方案**（拆成 `SwitchItem`/`MatchItem`/`LevelItem` 三个类型）**建议改**：

**数据**：`toolhub.Item{` 定义点 **10 处**（每模块 1 个 `[]toolhub.Item` 字面量，约 20-25 条）；
`ItemType` 分布：`ItemSwitch` 5、`ItemMatch` 若干、`ItemLevel` 1。

**为什么建议改方案**：

| 维度 | `Layer`（已拆） | `Item` |
|---|---|---|
| 字段重叠 | `Guard` 同时管「权限」和「排序」**两个正交概念** | `Type` 只是**一个判别字段** |
| 误用后果 | `FailOpen` 静默失效（**安全隐患**） | `Levels` 被忽略（**配置不生效**） |
| 改动面 | 3 个适配点、60 行 | **10 个模块 + `permissions.toml` 格式 + explain + adapters** |

**关键**：拆类型会**破坏 `permissions.toml` 的格式**（用户可见的配置），收益只是类型安全。

**替代方案（推荐）：构造函数 + 提前校验**

```go
// 现在：Item.Validate() 在 RegisterItem 时才调（离声明点很远）
// 改成：构造时立即校验
func SwitchItem(id, title string, class Effect) Item
func MatchItem(id, title string, class Effect, subject SubjectFunc, bounded bool) Item
func LevelItem(id, title string, class Effect, levels []string, suggest string) Item
```

**收益**：误用在声明点报错；不改 `Item` 结构体、不改配置格式、不改 explain；
10 个模块机械替换构造调用；`Validate()` 保留作兜底。
**代价**：比完全拆类型弱一点（`Item` 仍可被直接构造），但收益/成本比高得多。

### 第 2 步：M1 `Meta.Config any` 静默降级

**问题**：`Meta.Config any`（`runtime/component/plugin.go:24`）同时承载「Schema 原型」与
「已解码实例」，类型由声明方与读取方各自约定。13 处调用点全是 `cx.Config().(*XxxConfig)`，
其中 **9 处丢掉了 `ok`**。

**2026-11-12 核查修正**：`decodeConfig`（`runtime/component/config.go:98`）返回
`reflect.New(structType(proto)).Interface()`，类型与 `Meta.Config` **保证一致**，
所以断言**当前不会失败**。报告原先说的「`-mode` 静默失效」**不成立**。

真实情况：13 处调用点里
- **4 处直接断言**（`c := cx.Config().(*XxxConfig)`，不检查 ok）：类型真变了会 **panic**，不是静默
- **6 处丢 ok**（`cfg, _ := ...`）：类型变了会静默降级
- **3 处正确检查**（`if c, ok := ...; ok && c != nil`）

**为什么仍要改**：这是**隐患**而非当前故障——一旦有人改了 `Meta.Config` 的类型而忘了改断言，
4 处 panic、6 处静默降级。而且「4 处 panic / 6 处静默 / 3 处正确」这种不一致本身就是维护负担。
**优先级从「高」降为「中」**，因为当前不会出问题。

**怎么改**（推荐方案 A）：

- **方案 A（推荐）**：`Assemble` 末尾做一次反射校验——`Meta().Config` 的静态类型
  与组件在 `Setup` 里断言的目标类型一致，不一致则**装配期报错**。改动集中在 `component` 包，
  13 个调用点不用动。
- 方案 B：`Registrar.Config[T]()` 泛型方法，编译期保证类型。改动面大（13 处 + API 变化），
  但更彻底。**如果选 B，要和 04 4.2 的 `Registrar` 文档一起改。**

**验收**：
- 新增测试：故意让某组件的 `Meta.Config` 与断言类型不符 → 装配期报错（不是静默降级）
- 现有组件全部通过（尤其 permission / hooks / sandbox / shell）
- `gofmt`/`vet`/`go test ./...`/回归快照/公开面快照全绿

### 第 3 步：H4 `GuardRequest` 五点位共用

**问题**（`runtime/component/guard.go:65`）：5 个点位共用一个结构体，字段有效性靠注释
（「GuardDeliver 时有值」「GuardToolCall 时有值」）。且 `GuardModelCall`/`GuardTurn`
**零生产触发**，`Model` 字段恒零值；`Risk` 字段零读取方。

**怎么改**：按点位拆——`DeliverReq`/`SessionOpenReq`/`ToolCallReq`（后者已存在于
`middleware_toolcall.go`）。`GuardRule` 泛型化，或每点位一个 `Guard` 方法。

**注意**：这一步与 `WrapGuard` 的 `GuardFn[Req]` 是同一套设计，**一起改**否则两套并存。

**验收**：现有守卫测试（`guard_test.go`、`toolGuard`）全部迁移；装配期检查不变。

### 第 4 步：M2 + M3 `Item` / `ItemSetting`（**方案已改：构造函数 + 提前校验，不拆类型**）

**原方案**（拆成 `SwitchItem`/`MatchItem`/`LevelItem` 三个类型）**已否决**，理由见第三节 D2：
拆类型会**破坏 `permissions.toml` 格式**（用户可见配置），而 `Item` 的缺陷程度比 `Layer` 轻
（`Type` 是单一判别字段，不是布尔编码两个正交概念）。

**采用方案：构造函数 + 提前校验**

```go
// runtime/toolhub/items.go 新增三个构造函数（内部仍造 Item，但参数即校验）
func SwitchItem(id, title string, class Effect, suggest map[string]ItemAction) Item
func MatchItem(id, title string, class Effect, subject SubjectFunc, bounded bool,
               suggest map[string]ItemAction) Item
func LevelItem(id, title string, class Effect, levels []string, suggestLevel string,
               suggest map[string]ItemAction) Item
```

- 构造函数内部只填该型有意义的字段，误用**在声明点就报错**（或类型上写不出来）
- 保留 `Item.Validate()` 作为兜底（防直接构造 `Item{}`）
- `ItemSetting`（`permission/modes.go`）同理：加 `SwitchSetting`/`MatchSetting`/`LevelSetting`
  构造，`eval.go:40` 那个三重取反的条件可以简化

**改动面**：10 个模块的 `Items()` 各改构造调用（机械替换）+ `ItemSetting` 的构造点。
**不改**：`Item` 结构体、`permissions.toml` 格式、`explain` 输出、`adapters`。

**验收**：`items_test.go` 的 4 条 Validate 测试改为「构造时即错」；权限档位判定全部不变；
回归快照无差异。

### 第 5 步：M5 `Cx.Approved` 一个布尔多语义（语义不清，非当前漏洞）

**问题**（`runtime/toolhub/toolhub.go:131`）：注释自己承认两种（「免确认」+「免重判」），
而 5 个读取方实际有 **3 种语义**：

| 读取方 | 语义 |
|---|---|
| `DefaultAuthorizer`（`toolhub.go:215`） | **免重判**：直接 Allow，连 deny 都不判 |
| `exec.go:340`/`:355`（Gate/Authorizer 的 Confirm 分支） | 免确认 |
| `permission` 的 Authorizer（`permission.go:416`） | 只在 AskUser 分支放行，Deny 仍拒 |
| `sandbox.go:122` | 「本次有效」 |

**2026-11-12 核查修正**：报告原先说的「`ChainAuthorizers` 里混进 `DefaultAuthorizer` 导致
一个批准连带放行其他判定」**不成立**——`DefaultAuthorizer` 只在 `!hub.Authorized()`
（没装权限组件）时加，与 `permission` 的 Authorizer **互斥**（`assemble/runtime.go:190`）。

真实问题：6 个读取方（不是 5 个）语义确实不一致，且 `shell.go:203` 也用 `cx.Approved`
做「已批准则跳过沙箱提示」。这是**语义不清**而非当前漏洞。

**怎么改**：拆成 `ApprovedOnce`（本次确认已过）与 `PreApproved`（恢复出的持久批准）；
或让 Authorizer 拿到的 `Decision` 带「这次是 Confirm 而非 Allow」的语义，不靠布尔。
**优先级从「高」降为「中」。**

**风险**：动安全边界。**单独提交，有任一测试红就整体回退。**
