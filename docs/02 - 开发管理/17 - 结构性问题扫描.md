## 一、问题是什么：四条信号

这类缺陷的形态是：**一个类型 + 一个判别字段，字段含义随判别值变化**，于是必须靠运行时检查补救。
`toolhub.Layer` 是最典型的例子（`Guard` 布尔同时编码「拒绝权」和「排序位置」，`Timeout`/`FailOpen`
只对其中一种有效）。

判断口诀：**注释里出现「只对」「仅在」「无效」这类限定词，就是拆的信号。**

四条信号（出现任一条就该拆）：

| # | 信号 | 例子 |
|---|---|---|
| 1 | 布尔字段 + 注释说「只对 X 有效」 | `Layer.FailOpen // 只对 Transform 有效` |
| 2 | 字段含义随另一个字段的取值变化 | `Guard:true` 时 `FailOpen` 无意义 |
| 3 | 需要运行时检查来防止误用 | `if out.Kind == Confirm && !l.Guard { 报错 }` |
| 4 | 一个字段同时表达「是什么」和「在哪/权限」 | `Guard` 既表权限又表排序 |

## 二、已修（历史记录）

### P1 `toolhub.Layer` → `Transform` + `Gate` + `Authorizer`（`58d5676`）

- **原形态**：`Guard`（拒绝权 + 排序）、`Authorizes`（谁是拍板的）、`Timeout`/`FailOpen`（只对改写层有效）
- **修法**：拆成 `Transform`（只能改）/ `Gate`（只能判，可并行）/ `Authorizer`（可挂起问人）。
  执行链：改写链 → 准入判定（并行 reduce）→ Authorizer → 执行器
- **收益**：`Gate` 并行、`Gate` panic 自动 fail-closed、误用编译不过
- **详见**：[15 - 扩展点重构方案](<./15 - 扩展点重构方案.md>) 第六节

### P2 `modelhub.Layer`（`9263632`）

- 同一反模式，且**生产零调用**（死代码）。删层机制。
- **注意**：R2 结构校验（`CheckShape`，防中间件偷偷放宽工具集）必须保留，
  改由 `agent.sendModel` 在 ModelCall 中间件链之后调用。

### P3 `instructions.Layer()` 死代码（`58d5676`）

- 已被 `Middleware()` 取代、无人调用，但带着 `Timeout`/`FailOpen` 误导维护者。删。

### H1 `WrapGuard` 判定从未接线（`b15fa80`）—— 安全

- **症状**：`WrapGuard` 只写进 `Assembly.guardsByPoint`，**全仓无生产代码调 `EvalPoint`**。
  redact 的 `WriteGuardFn`（拦「把脱敏占位符写回文件」）注册成功、函数级单测绿，
  但**真实会话里永不触发**（数据损坏防护失效）。
- **根因**：第 2 步迁 redact 时，原来 `redact-guard` 是 `SessionLayer` 的 Guard 层（会真跑），
  改成 `WrapGuard` 后没接线。**测试测的是函数，不是接线。**
- **修法**：`Builder.PointGuards` + `Build` 里 `AddGate("component-guardpoint")` 调 `EvalPoint`；
  `Wire` 用 `pointGuards(asm)` 注入（没登记时 nil）。用例 `runtime/assemble/pointguard_test.go`。
- **2026-11-12 核查补充（重要）**：接线修好了，但**真实用户默认仍拿不到 redact**——
  `apphost`（CLI/桌面端）走 profile 装配，只看 `Meta.Default`，而 **redact 没有 `Meta.Default: true`**。
  这是**有意设计**（[04 - 核心与扩展模块清单](<../01 - 设计文档/04 - 核心与扩展模块清单.md>) 第 143 行写明），
  且 `presets_internal_test.go` 的 `TestDefaultIsEveryStandardComponent` 强制「`Default()` = 所有标准组件」。
  **影响**：`tenon.Default()` 26 个组件，apphost profile 路径只启用 16 个（少 redact/skills/hooks/
  sandbox/code-mode/mcp/todo/web/subagent/workgroup 共 10 个）。要不要给这些组件补 `Meta.Default: true`
  是**产品决策**，不是 bug——记在下面「待决策」一节。

### M8 `Tool.Dangerous()` 文档承诺是假的（`5acd7a6`）—— 安全

- **症状**：文档说「权限插件按档位要人确认（缺省档位下也要）」，但只设 `Risk = Dangerous`，
  而 `modules/security/permission` **完全不读 `Risk`**（读 `AttrDestructive`）。
  所以 `Dangerous` 与 `Writes` **行为完全等价**。
- **修法**：`Dangerous` 同时设 `attrDestructive`，permission 的「声明破坏性 → AskUser」逻辑即生效。
  用例 `dangerous_test.go`。

#### H4 的真相：整套守卫机制在生产里是**空的**，应该删掉而不是拆

**核查**：`cx.Guard()`（`component.Registrar.Guard`）在**生产代码里零登记**——
只有 `examples/component/main.go` 和测试调用。所以：

- `Assembly.GuardRules()` 恒返回空
- `Host.Guards` 恒为空 → `Host.evalGuard` 恒返回 `Abstain`（`host/envelope.go:974`）
- `toolGuard()` 恒返回 `false`（`assemble/runtime.go:421`）
- 五个 `GuardPoint` 里 `GuardTurn`/`GuardModelCall` 连调用点都没有

**所以「拆 `GuardRequest`」是给一套空转机制做精装修。**

**更优解：分两步**

1. **先删死掉的**：`GuardTurn` / `GuardModelCall` 两个点位（零调用点）直接删；
   `GuardRequest.Model` / `Risk` 两个字段（零读取方）删。
2. **再判断 `GuardDeliver` / `GuardSessionOpen` 要不要留**：
   这两个点位**有调用点**（`host/envelope.go:268/293/387/395/447`），但**规则恒空**。
   它们的内核缺省行为（联系名单、跳数、预算）**已经在别处硬编码实现了**。
   所以问题变成：**「组件登记投递/建会话守卫」这个扩展点，现在需要吗？**

**我的判断：现在不需要，但留着点位、删掉 `GuardRequest` 的字段重载。**

理由：投递和建会话的准入已经由 `Authorizer`（工具）+ 内核硬编码（联系名单/跳数/预算）覆盖，
没有实际场景需要组件再插一手。而 04 4.2 里 `GuardPoint` 的注释「与 4.3 的中间件点位同名」
说明它本来就是为「守卫与中间件对称」设计的——**但现在中间件有了 `WrapGuard` 判定区，
`GuardRule` 是第二套做同一件事的机制**。

**所以更优解是：`GuardRule` 整体并入 `WrapGuard`**（一套判定机制，不是两套），
`Host` 侧改用 `Assembly.EvalPoint`。这样：
- 删掉 `GuardRule` / `GuardRequest` / `EvalGuards` / `Host.Guards` / `toolGuard`
- 六个点位的判定统一走 `WrapGuard` + `EvalPoint`
- `examples` 改成用 `WrapGuard`

**改动面**：`component/guard.go`（删大部分）、`host/envelope.go`（5 处 evalGuard 改成
`EvalPoint`）、`assemble/runtime.go`（删 toolGuard）。**净减少代码约 150 行。**

#### H2 的更优解：只删，不拆类型

原方案「`Config` 拆成 `ConfigFile` + `Rules`」——**过度设计**。

实际情况：`Allow` 字段只在**两处**被读（`Parsed:63`、`Merge:82`），而 `LoadConfig:48`
保证它恒为空。所以：

**更优解**：
1. `Parsed()` 的循环去掉 `{c.Allow, Allow}` 这一组
2. `Merge()` 去掉 `out.Allow = append(...)` 那一行
3. `Config.Allow` 字段**保留**但注释写明「恒为空：公共规则只认 deny/ask（§9.7）」——
   保留是因为 `LoadConfig` 要用它**检测并报错**（用户写了 allow 要给出清晰错误）

**不拆类型**的理由：拆了要改 `LoadConfig`、`Merge`、`Parsed`、以及所有构造 `Config` 的地方，
而收益只是「编译器保证 Allow 不被误用」——但 `LoadConfig` 的运行时检查已经做到了。
**净减少 2 行 + 1 条注释，比拆类型（改 4 处 + 新增类型）优。**

#### M1 的真相：需求不成立，撤项

**核查**：`decodeConfig`（`config.go:98`）用 `structType(proto)` 从 `Meta.Config` 推类型，
再 `reflect.New(t)` 造实例。**类型由 `Meta.Config` 唯一决定，断言不可能失败。**

所以：
- 「`-mode` 参数静默失效」**不可能发生**
- 13 处调用点里 4 处直接断言（`c := cx.Config().(*Xxx)`）也**不会 panic**

**真实需求只是「代码风格不统一」**（4 处直接断言、6 处丢 ok、3 处正确检查）。

**更优解：不改代码，只统一风格 + 加一条注释**

在 `Registrar.Config()` 的文档注释里写明：
「返回值的类型由 `Meta.Config` 唯一决定，断言必然成功；写 `c, _ :=` 或直接断言都可以，
但推荐 `c, ok :=` 以便未来 `Meta.Config` 允许 nil。」

**收益**：零代码改动，消除「隐患」的认知。**这比加反射校验（装配期多一次反射）优。**

#### M5 的更优解：改注释与命名，不拆字段

原方案「拆成 `ApprovedOnce` / `PreApproved`」——**过度设计**。

**核查**：6 个读取方里，5 个的语义其实是**一致的**：「本次确认已过，允许执行」。
唯一不同的是 `DefaultAuthorizer`（直接 Allow，连 deny 都不判）——但它在
`!hub.Authorized()` 时才装，与 permission **互斥**，实际不会同时出现。

**更优解**：
1. `Cx.Approved` 注释改成准确的一句话：「本次调用已获人工批准（参数哈希一致）。
   读取方只应据此跳过**确认**，不应据此跳过**判定**（deny 仍要重判）。」
2. `DefaultAuthorizer` 里 `if cx.Approved { return Allow }` 改成
   `if cx.Tool == nil || cx.Tool.Risk == Read || cx.Tool.NoAuth { return Allow }`，
   **去掉 `cx.Approved` 分支**——因为「已批准」是确认流程的事，DefaultAuthorizer
   的职责是「没有权限组件时的缺省判定」，它本就不该关心批准状态。

**收益**：改 2 行 + 1 条注释，消除「一个布尔 3 种语义」的认知负担。比拆字段（改 6 个读取方）优。

#### H5 的更优解：不加新机制，复用已有的 `Effects` + `Notes`

原方案「`Explain()` 加一节 + `Notes` 追加一条」方向对，但可以更彻底：

**核查**：`Meta.Effects` 已经有完整数据（每个组件都声明了 `EffectRewriteResult` /
`EffectSystemPrompt` / `EffectTools` 等），**只是没人用**。`apphost.Runtime.Notes`
已经是现成的「装配提示」通道。

**更优解**：
1. **`Explain()` 里复用**：在插件列表每个条目后面加 `[改写模型输入]` / `[改写模型输出]` 标签
   （不用新开一节，信息在原位更好读）
2. **`Notes` 里复用**：装配完成后，把「已开启的改写类组件」拼一条 Note
   （`apphost/runtime.go` 在 `LoadAll` 之后已有追加 Notes 的位置）
3. **不加新字段、不加新类型**——`Effects` 和 `Notes` 都是现成的

**这比「新增一个 `Rewrites bool` 字段」优**，因为 `Effects` 已经表达了这件事。

#### M4 的方案要重新评估（暂缓）

原方案「`Header.Status` + 三个 `*Pending` 子结构体」。**核查后觉得可能过度设计**：

- `restore.go:129-145` 的三条检查是**恢复校验**（防损坏数据），不是「防误用补救」——
  按第五节的标准，这**不算**结构性问题

**所以 M4 的需求是「代码整洁」而非「正确性」。** 建议：**先不动**，等真有跨回合脏状态的
bug 再说。如果要动，最小改法是加一个 `Header.clearPending()` 方法统一清零

### D1 组件默认开关：**已决策，不是待决策**（2026-11-12 结案）

**结论：默认关闭是既定原则，不改。**

依据（`03 - 约束清单`，不是推测）：

- **第 19 行**：「默认开启的插件只保留『没有它就不能正常工作』的那些。其余由用户开启。
  **开启后会改写模型所见内容的插件（如脱敏），要在 `explain` 和启动横幅里明示。**」
- **第 203 行**（2026-10-31 决策记录）：「缺省关闭 skills / redact / hooks / mcp / web /
  subagent / workgroup / code-mode，需要时在 `~/.tenon/profile.toml` 或受信项目的
  `.tenon/profile.toml` 写 `enabled = true`」
- **第 90 行**：「沙箱 | 插件缺省关闭；开启后沙箱级别随档位」
- **`sandbox` 的 `Meta` 显式写了**：`Default: false, // 独立开关，缺省关闭（§9.9）`

**为什么不改成默认开**：

1. 按第 19 行原则，默认开只保留「没有它就不能工作」的（models / store / prompt / permission）。
   `redact` 属于「改写模型所见内容」，按原则就该明示后由用户开。
2. **安全透明度**：脱敏会改写工具输出。默认开 + 用户不知情，比默认关 + 明示开启更糟。
3. **平台限制**：`sandbox` 只在 Windows 有实现，其他平台开了是 no-op 还告警。

**真正的问题不是默认值，是「明示」没实现** —— 见下面 H5。

### H5 约束清单要求的「开启后明示」没有实现（**新发现，安全透明度**）

- **要求**（`03 - 约束清单` 第 19 行）：「开启后会改写模型所见内容的插件（如脱敏），
  要在 **`explain` 和启动横幅**里明示。」
- **现状**：
  - `Meta.Effects` 字段的注释写着「对会话的影响，取 `Effect*` 常量（**explain / 启动横幅明示**）」

    点位登记、degraded，**唯独没有 `Effects`**。
  - **全仓没有「启动横幅」代码**（grep `横幅|banner` 只命中两处注释）。
  - `Meta.Effects` 的**唯一真实消费方**是 `appapi/v2.go:1421`（给前端 UI 的插件列表）。
- **后果**：用户在 CLI / 桌面端开启 `redact`（或 `hooks`、`instructions` 这些
  `EffectRewriteResult` 的组件）后，**看不到任何「你的模型输入/输出会被改写」的提示**。

  1. **`Explain()` 加一节**：把开了 `EffectRewriteResult` / `EffectSystemPrompt` 的组件列出来，

     作为一条 Note 加进去即可——**基础设施已有，只差一条 Note**。
- **验收**：
  - `Explain()` 输出含「改写模型所见内容」一节，列出 `redact`/`hooks`/`instructions`/`compact-basic`
  - 开启 `redact` 时启动提示里出现明示
  - 关闭时不出现
- **严重度**：**中高**（安全透明度要求未实现，但无数据损坏）
- **优先级**：**提到第 1 步之前**——它是约束清单的明确要求，且实现成本低（利用已有 `Notes`）

### D2 M2+M3 拆 `Item` 的替代方案（2026-11-12 评估）

**原方案**（拆成 `SwitchItem`/`MatchItem`/`LevelItem` 三个类型）**建议改**：

**数据**：`toolhub.Item{` 定义点 **10 处**（每模块 1 个 `[]toolhub.Item` 字面量，约 20-25 条）；
`ItemType` 分布：`ItemSwitch` 5、`ItemMatch` 若干、`ItemLevel` 1。

**为什么建议改方案**：

| 维度 | `Layer`（已拆） | `Item` |
|---|---|---|
| 字段重叠 | `Guard` 同时管「权限」和「排序」**两个正交概念** | `Type` 只是**一个判别字段** |
| 误用后果 | `FailOpen` 静默失效（**安全隐患**） | `Levels` 被忽略（**配置不生效**） |
| 改动面 | 3 个适配点、60 行 | **10 个模块 + `permissions.toml` 格式 + explain + adapters** |

**关键**：拆类型会**破坏 `permissions.toml` 的格式**（用户可见的配置），收益只是类型安全。

**替代方案（推荐）：构造函数 + 提前校验**

```go

// 改成：构造时立即校验
func SwitchItem(id, title string, class Effect) Item
func MatchItem(id, title string, class Effect, subject SubjectFunc, bounded bool) Item
func LevelItem(id, title string, class Effect, levels []string, suggest string) Item
```

**收益**：误用在声明点报错；不改 `Item` 结构体、不改配置格式、不改 explain；
10 个模块机械替换构造调用；`Validate()` 保留作兜底。
**代价**：比完全拆类型弱一点（`Item` 仍可被直接构造），但收益/成本比高得多。

### 五条铁律（2026-11-12 复盘后定，**每次扫描和修复都必须遵守**）

这一轮暴露了系统性的判断错误：16 项里 **1 项根本不存在**（M1）、**2 项应删整套而非拆**（H4/H2）、
**3 项可大幅简化**（M5/M4/H5），只有 4 项维持原方案。下面是提炼出的规则。

#### 铁律一：每个发现先过「三问」

```
① 有生产者吗？（谁会写它 / 登记它）
② 有消费者吗？（谁会读它 / 调用它）
③ 在生产路径上吗？（不是 examples / 测试）
```

**三者缺一 → 是死代码，删，不是改。**

- **H4**：①零登记 → 死代码 → 删 150 行（不是拆成五个类型）
- **M1**：①有但产物类型恒定（`decodeConfig` 从 `Meta.Config` 推类型）→ 需求不成立 → 撤项
- **H2**：①有（用户可能写 allow）但被 `LoadConfig` 拦死 → 死分支 → 删 2 行

#### 铁律二：严重度必须带证据等级

| 等级 | 判据 | 处理 |
|---|---|---|
| **已发生** | 有测试红 / 有复现步骤 / 有 bug 报告 | 高，立即修 |
| **可能发生** | 类型系统允许，但当前路径不经过 | 中，改注释或加校验 |
| **只是不优雅** | 无实际后果 | 低，记文档，不改代码 |

**禁止把「代码看起来能出错」写成「已经出错」。** M1 就是这条的违例——
`cfg, _ := cx.Config().(*PluginConfig)` 看着危险，但断言不可能失败。

#### 铁律三：方案先比「删」，再比「改」，最后才「加」

```
能不能删掉？              → 能删就删（H4 删 150 行、H3 删 1 常量、H2 删 2 行）
不能删，能只改 1-2 行？   → 改（M5 改注释 + 删 1 分支）
必须加东西？              → 才考虑加类型/加机制（M2/M3 构造函数）
```

**「拆成 N 个类型」是最后手段，不是第一反应。** 对一个已经能正常工作的系统，
加抽象的成本远高于删冗余。

#### 铁律四：改完必须验证「运行时路径」，不能只验证「编译 + 单测」

H1 的教训：`WrapGuard` 注册成功、函数级单测绿——**但没有任何生产代码调 `EvalPoint`**，
安全防护静默失效。

**验证清单**：
