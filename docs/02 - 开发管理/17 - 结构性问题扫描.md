# 17 结构性问题扫描：一个类型编码多种语义

> 状态：生效（2026-11-12）。拆掉 `toolhub.Layer` 后，系统扫了一遍「同类结构性缺陷」。
> 本篇记录**扫描方法、确认的问题、以及判定为「不是问题」的候选**（避免以后重复讨论）。

## 一、扫描什么：四条信号

一个类型如果出现下面任一信号，说明它在**用同一个类型/字段编码多种语义**，该拆：

1. **布尔字段 + 注释说「只对 X 有效」** —— 该字段在另一种取值下是死字段
2. **字段含义随另一个字段的取值变化**（`Guard:true` 时 `FailOpen` 无意义）
3. **需要运行时检查来防止误用**（「只有 Guard 能返回 Confirm」）
4. **一个字段同时表达「是什么」和「在哪/权限」**（`Guard` 既表权限又表排序）

判断口诀：**注释里出现「只对」「仅在」「无效」这类限定词，就是拆的信号。**

## 二、确认的问题（已修）

### P1 `toolhub.Layer`：一个结构体 + 一个布尔编码三种语义

- **位置**：`runtime/toolhub/toolhub.go`（已删）
- **原形态**：`Guard`（拒绝权 + 排序）、`Authorizes`（谁是拍板的）、`Timeout`/`FailOpen`（只对改写层有效）
- **症状**：`Layer{Guard:true, FailOpen:true}` 编译通过但 `FailOpen` 是死字段（安全隐患）；
  改写层能返回 `Confirm` 要靠运行时检查补救；纯判定被迫带 `next` 而串行
- **修法**：拆成 `Transform`（只能改）+ `Gate`（只能判）+ `Authorizer`（可问人），
  见 [15 - 扩展点重构方案](<./15 - 扩展点重构方案.md>) 与 [框架设计/04 4.3.1](<../01 - 设计文档/框架设计/04 - 扩展模型.md>)
- **提交**：`58d5676`

### P2 `modelhub.Layer`：同一个反模式，且是死代码

- **位置**：`runtime/modelhub/scheduler.go`（已删）
- **原形态**：`Guard bool` + `FailOpen bool // 只对 Transform 有效` —— 与 P1 逐字同款
- **症状**：生产代码**零调用**（`AddLayer` 只在测试里用）；`Guard` 只在 panic 恢复里读一次
- **修法**：删层机制。**但 R2 结构校验（`CheckShape`）必须保留**——它防「中间件偷偷放宽工具集」，
  原来挂在层链上，层删了就丢了保护。改由 `agent.sendModel` 在 ModelCall 中间件链**之后**调用，
  并补 `TestCheckShapeRejectsSmuggledTools`
- **提交**：`9263632`

### P3 `instructions.Layer()` 死代码

- **位置**：`modules/context/instructions/agentsmd.go`（已删）
- **症状**：已被 `Middleware()` 取代、无人调用，但带着 `Timeout`/`FailOpen` 字段，
  会误导维护者以为这两个字段还有活用户
- **提交**：`58d5676`

### 第二轮扫描（2026-11-12，深度扫描后的补充）

第一轮只覆盖了 `Layer` 一族。第二轮做了完整扫描（逐类型核查 + grep 验证调用点），
发现的问题按严重程度：

#### H1 `component.WrapGuard` 登记的判定在生产路径上从不执行（**已修** `b15fa80`）

- **位置**：`runtime/component/guardpoint.go:42`（`WrapGuard`）→ `Assembly.guardsByPoint`；
  唯一调用方 `modules/context/redact/plugin.go:27`
- **症状**：`guardsByPoint` 有写入方、**没有读取方**——全仓只有 `guardpoint_test.go` 调 `EvalPoint`。
  redact 的 `WriteGuardFn`（拦「把脱敏占位符写回文件」）注册成功、函数级单测绿，
  但**真实会话里永不触发**：模型把 `<REDACTED>` 写进源码不会被拦（数据损坏防护失效）。
- **根因**：第 2 步迁 redact 时，原来 `redact-guard` 是 `SessionLayer` 的 Guard 层（会真的跑），
  改成 `WrapGuard` 后没接线。**测试测的是函数，不是接线**。
- **修法**：`Builder.PointGuards` + `Build` 里 `AddGate("component-guardpoint")` 调 `EvalPoint`；
  `Wire` 用 `pointGuards(asm)` 注入（没登记时 nil，零开销）。用例在 `runtime/assemble/pointguard_test.go`。

#### M8 `Tool.Dangerous()` 文档承诺是假的（**已修** `5acd7a6`）

- **位置**：`tools.go:38`（`Dangerous`）、`runtime/toolhub/toolhub.go:18-22`（`Risk`）
- **症状**：文档说「权限插件按档位要人确认（缺省档位下也要）」，但它只设 `Risk = Dangerous`，
  而 `modules/security/permission` **完全不读 `Risk`**（grep 零命中）——读的是 `AttrDestructive`。
  所以 `Dangerous` 与 `Writes` **行为完全等价**，应用作者的安全预期落空。
- **修法**：`Dangerous` 同时设 `attrDestructive`，permission 已有的「服务端声明破坏性 → AskUser」逻辑即生效。

## 三、判定为「不是问题」的候选（记录理由，避免重复讨论）

| 位置 | 形态 | 为什么不拆 |
|---|---|---|
| `toolhub.Output` | `Kind` 决定哪些字段有意义（`Done` 用 `Content`/`Status`，`Confirm`/`Pending` 用 `Reason`） | 这是**线格式/协议**性质：拆分要改几十处调用点与序列化，代价远大于收益。且 `Kind` 的语义是封闭的（三个值） |
| `toolhub.Tool.Parallel *bool` | 三态指针（`nil` = 按 `Risk` 推） | 这是**明确的三种状态**，不是多语义混用。`*bool` 是表达三态的标准做法 |
| `toolhub.Tool.Attrs map[string]any` | 通用属性袋 | 这是**正当的扩展点**（工具自定义属性，如 `AttrWorkspace`/`AttrSandboxed`），不是语义重载 |
| `toolhub.Tool.NoAuth` + `Items` | 两字段互斥（`Validate` 检查） | 两个**正交**字段 + 一条一致性约束，语义清晰。拆开反而要引入新类型 |
| `mail.Envelope.Key` | 注释「只对 `agent:` 有效」 | 这是**字段适用范围**的业务说明，不是多语义编码——`Key` 在任何地址下含义都是「会话键」 |
| `callctx.Ctx` 的 `untrusted`/`trigger`/`reResolve` | 三个独立字段 | 各管一件事（不可信标记 / 本轮触发者 / 重解函数），无重载 |
| `appapi` 的 `Kind`-driven switch | 协议消息分发 | 协议适配层的本职：`Kind` 就是消息类型，不同消息带不同字段是**协议设计**而非缺陷 |
| `session.Content` 的 `Kind` | 内容部件类型（text/image/…） | 同上，线格式 |
| `useconf.Tag` 的 `Tenant`/`Secret`/`Hot` | 三个独立布尔 | 各管一件事（可否覆盖 / 是否敏感 / 是否热生效），无重载 |

## 四、方法沉淀

**扫描用的命令**（可复用）：

```powershell
# 信号1：注释里的「只对…有效」
Get-ChildItem -Recurse -Filter "*.go" | Where-Object { $_.FullName -notmatch "_test" } |
  ForEach-Object { Select-String -Path $_.FullName -Pattern "只对.*有效|仅在.*时有效" }

# 信号4：Kind 驱动的 switch（人工判断是协议适配还是语义重载）
Get-ChildItem -Recurse -Filter "*.go" | ForEach-Object {
  if ((Get-Content $_.FullName -Raw) -match "switch .*\.Kind") { $_.FullName } }
```

**经验**：信号 1 最有效（P1、P2 都是它抓到的）。信号 4 会命中大量协议适配代码，
需要人工判断——**协议消息类型不是语义重载**。
