### ~~L2 T6a 跨机器预算的「发送方记账」~~ **已撤销：不该做，不是待做（2026-11-12）**

原以为这是「设计有、实现缺」的待办。核查后判定 **不是遗漏，而是不该做**。

**为什么不该做**：

1. **它在解一个不存在的部署场景**。`transport/web/remote.go` 的 `RemoteClient` **没有被任何
   主程序接上**（`apphost` / `tenon.New` 都没注入 `Host.Remote`）——框架具备跨机器能力，
   但没有真实多节点部署。
2. **就算做了，语义也是错的**。「被调用方的工作记到调用方账上」在分布式系统里是反模式：
   - B 崩溃 → A 永远收不到 usage → **账目永久丢失**
   - A 收不到回信 → 不知道 B 花了多少 → **无法判断该不该继续**
   - 要可靠就得两阶段确认（预扣/记账/结算），复杂度爆炸
   - 真实的分布式配额系统（云厂商）都是「各记各的 + 定期对账」，不是「调用方记账」
3. **单机内预算已经完整**。`budget_ref` 记账、`budgets` 表、超限挂起都已实现
   （`accountBudget` / `AccountBudget` / 迁移 v15）。跨机器记账属于分布式部署阶段，
   那时预算模型要重新设计，不是补一个字段能解决的。

**改为设计约束**（写进 08 8.4 更合适，此处记录）：

> 跨机器调用**不做**发送方记账。预算按机器本地记账；需要跨机器预算时，
> 由部署层用外部配额系统（网关限流、云配额）实现，不塞进框架。

**为什么要明确「不做」而不是留着**：留着会误导后来人以为这是遗漏，花时间去做一件
「听起来完整但没有真实价值」的事——正是本轮治理反复出现的同一个错误
（用架构完整性代替真实需求）。

### L3 插件进程的故障隔离粒度（原「按租户分进程」，**需求已修正**）

**原需求是错的**：原写「多租户下不可信插件能读到别的租户数据」。
核查发现 `runtime/store/store.go` 的 `const Tenant = "local"` 注释就是
「**当前租户（单机固定）**」——框架**没有多租户概念**，`Tenant` 是编译期常量。
按租户分进程是在解一个不存在的问题。

**但「分进程」本身在特殊场景有价值**。现状（`modules/extend/extproc/plugin.go`）：

```go
type plug struct {
    sup  *Supervisor   // 一个组件一个进程
    conn *extproc.Conn // 所有会话共用这一个连接
}
```

**一个 extproc 组件 = 一个进程 = 所有会话共用。** 真实问题不是租户隔离，而是：

| 问题 | 说明 |
|---|---|
| **崩溃爆炸半径** | 插件进程崩了，**所有会话**的该插件工具都不可用（`MaxCrashes` 后标记不可用） |
| **无资源隔离** | 一个会话的重负载插件调用会拖慢所有会话 |
| **无状态隔离** | 插件进程内的状态（缓存、连接池）所有会话共享 |
| **无法按会话重置** | 想重置某会话的插件状态，只能重启全局进程 |

**该按什么分**：不是租户，而是**故障域**。三种可选粒度：

| 粒度 | 适用场景 | 代价 |
|---|---|---|
| **按组件**（现状） | 默认，最简单 | 崩溃爆炸半径 = 全部会话 |
| **按会话** | 高价值会话需独立插件状态；或要能单独重置 | 进程数 = 会话数，内存开销大 |
| **进程池 + 租约** | 折中：N 个进程轮转，崩溃只影响当前调用方 | 复杂度中 |

**触发条件**（满足任一再做）：
- 出现「某插件崩溃影响了不该影响的会话」的**实际投诉**
- 需要「单独重置某会话的插件状态」的真实需求

**状态**：⬜ 等真实故障隔离需求。**不要为「架构完整性」提前做**——
进程池的复杂度（生命周期、路由、租约、健康检查）远高于收益。

### ~~D3 `TestShellBackgroundJob` 的偶发失败~~ **已修根因（2026-11-13）**

**现象**：本地全量测试时出现过**一次**，12.79 秒后 step2 断言不符（「等待结束后应有全部输出」）。
此后单跑 10 次、包内 3 次、全量 2 次、`-race` 5 次、重负载 12 轮（CPU×4 忙循环）**均未复现**。
查 Gitea CI 近 10 个 Go job，**从未失败过**。

**已做的加固**（`7aaa609`）：
1. 不再硬编码 `job-1`/`job-2`——从启动输出解析实际 id（id 来自 `Shell.seq` 全局计数，
   将来共用实例或改编号会让硬编码断言失效）
2. `sleepCmd(1)` → `sleepCmd(2)`（负载高时 PowerShell 启动要几百毫秒，1 秒余量不足）；
   等待上限 20→10 秒（失败更快暴露，不靠等满）

**根因（2026-11-13 复查代码定位）**：`command()` 里 `cmd.WaitDelay = 2 * time.Second`。
`WaitDelay` 只在「进程已退出、但还有子进程占着 stdout/stderr 管道」时生效，到点强制关管道。
高负载下最后一段输出还没被读进 `tailBuf`，管道就被关掉，于是「已结束」出现了但输出不全——
正是失败断言的形态。原先以为是 PowerShell 启动慢（所以加了 `sleepCmd(2)`），那只是掩盖。

**修法**：`WaitDelay` 放宽到 10 秒。正常情况进程退出后管道立刻 EOF，不会等满；
只有残留子进程才走这条路径，宁可多等也不要丢输出。

**顺带修掉一个同类缺陷**：`job_output` 增量读时，切点可能落在 ANSI 转义序列中间，
`stripANSI` 会把残缺序列连同它后面的正常文本一起吞掉（`\x1b[3` + `end` 里的 `e` 被当成
CSI 终止字节）。改为 `stripANSIHolding` 报告「末尾多少字节是残缺的」，`callOutput`
据此回退读偏移，等序列闭合再吐。新增 `ansi_test.go` 锁住这条。

**验证**：`go test ./modules/tools/shell ./runtime/host ./appapi -count=2` 全绿；
全量 `go test ./...` 全绿。**风险**：低（`WaitDelay` 只在异常路径生效）。

**复查补漏（2026-11-13，同一轮）**：`callOutput` 里读偏移的「读」和「写」分在两次加锁之间，
并发两次 `job_output` 会各自读到旧偏移、再互相覆盖，同一段输出被吐两次。已改成锁内一次完成
（`cleanHolding` 不碰 `s.mu`，无死锁风险）。**注意**：这条改动**没有**配套的回归测试——
写过一个并发测试，但回退修复后它仍然通过，说明抓不到问题，已删掉不留充数。
理由是这种竞态窗口极小，用 shell 子进程做端到端并发很难稳定命中。

### D5 `TestV2Workspaces` 在 CI 上偶发清理失败（**已修根因**，2026-11-13）

- **现象**：Gitea CI run 807（`7b41d61`，第 2 步 mcp 提交）的 Go job 失败，唯一报错是
  `TestV2Workspaces` 的 `TempDir RemoveAll cleanup: unlinkat .../001: directory not empty`。
  测试断言本身通过了，失败发生在测试结束后删临时目录。
- **已核实**：本地 `go test ./appapi -run TestV2Workspaces -count=20` 全过；
  CI 对失败包 `-v` 重跑时该用例通过。与第 2 步改动无关（`appapi` 这次没改）。
- **第二次出现**（2026-11-12）：run 830（`5fdb93e`，第 5 步提交）的 Go job 同样只报这一条清理错误，
  `-v` 重跑通过。两次间隔 6 个提交，不是连续出现。
- **根因（2026-11-13 复查代码定位）**：`runtime/host/envelope.go` 的 `kickFlush` 起后台派发协程，
  用的是 `context.Background()`——不受调用方 context 约束，也不受测试结束影响。
  `newApp` 的 `t.Cleanup` 关掉 db 后，这个协程可能还在跑 `FlushOutbox`，继续访问数据库、
  写 WAL 文件，与 `t.TempDir` 的删除撞上。这就是「断言过了、清理才失败」的形态。
- **修法**：`Host` 加 `closed` 标志与 `Close()`；`kickFlush` 在关闭后不再起协程，已在跑的循环也退出。
  `appapi` 测试的清理改成 `h.Close()` → `b.Close()` → `db.Close()`（先停后台派发，再关库）。
  新增 `runtime/host/close_test.go` 锁住「Close 后不再派发」。
- **状态**：✅ 已修根因（2026-11-13）。本地 `-count=2` 与全量测试全绿；CI 需再观察几次确认不再复发。
- **复查补漏（2026-11-13，同一轮）**：首版修法只改了测试里的清理顺序，**生产路径没接**——
  `tenon.App.Close()` 没有调 `Host.Close()`，真实进程退出时后台派发仍会在关存储后跑。
  已补：`App.Close()` 在 `stop()` 之后、`scope.Close()` 之前调 `a.host.Close()`。
  这条漏掉的原因是「只按失败测试改测试」：测试绿了不等于生产路径修好了。
- **测试有效性已验证**：把 `kickFlush` 的 `closed` 判断回退，`TestHostCloseStopsFlush`
  变红，且暴露出回退后的真实危险——协程在关库后跑 `FlushOutbox` 会 nil 指针 panic。
