### L2 T6a 跨机器预算的「发送方记账」（**核查后：暂不做**）

- **是什么**：设计 08 8.4「记账按触发：被调用方的工作记到调用方的账上」。当前接收方已正确
  （`batchBudgetRef` 跳过远端信封，不重复记账），但**发送方拿不到远端调用的 usage**，
  所以跨机器调用的花费没有记到发送方账上。
- **依据**：[08 - 管控与安全](<../01 - 设计文档/框架设计/08 - 管控与安全.md>) 8.4；同篇第 117 行
  「没有按触发记账：`budget_ref` 字段已有，只参与「同一权限主体」分轮，不记账」列为 T4 待做。
- **核查结论（2026-11-12）**：**需求真实但无使用场景**。
  - `RemoteSender.Send(ctx, host, env) error` 只返回 error，**没有返回值**，发送方拿不到 usage
  - 要实现需要：改接口（`Send` 返回 usage）+ 改 HTTP 协议（对端回传）+ 改 transport 实现
  - **关键**：`transport/web/remote.go` 的 `RemoteClient` **没有被任何主程序接上**
    （`apphost` / `tenon.New` 都没注入 `Host.Remote`），即框架具备跨机器能力但**无真实多节点部署**
  - 按铁律二属「可能发生」而非「已发生」；按铁律一「三问」第③问（在生产路径上）**不满足**
- **量**：中偏大（协议改动）。**风险**：中。
- **状态**：**等真实跨机器部署需求**。真要做时的最小路径：
  1. 接收方回合结束时，在回信信封里带 `usage`（新增字段，或用 `Body` 承载）
  2. 发送方收到回信后 `accountBudget` 到自己的 `budget_ref`
  3. 需同时防「双方都记」——已有 `isRemoteOrigin` 判据可复用

### L3 T6b 不可信插件按租户分进程（**核查后：暂不做**）

- **是什么**：`extproc` 现在一个组件一个进程、所有会话共用；多租户下不可信插件能读到别的租户数据。
  需要进程池 + 租户路由 + 生命周期管理。
- **依据**：[14 - T6b 执行方案](<./14 - T6b 执行方案.md>) 末尾「仍未落地」
- **核查结论（2026-11-12）**：**需求不成立（当前）**。
  `runtime/store/store.go` 的 `const Tenant = "local"` 注释就是「**当前租户（单机固定）**」——
  整个框架**没有多租户概念**，`store.Tenant` 是编译期常量，所有存储调用都传它。
  所以「租户间数据隔离」这个问题在当前架构下不存在。
- **量**：中偏大。**风险**：中。
- **状态**：**等真实多租户需求**。真要做的前提是先把 `store.Tenant` 从常量改成运行期值
  （涉及所有存储调用点、租户路由、配额、身份认证），那是一个独立的架构阶段，
  不是「给 extproc 加进程池」能解决的。

### ~~D2 `Turn` 点位的 `Resumed` 判定依赖 `ag.Pending()`~~ **已完成（2026-11-12，`91db1bd`）**

`a.ag.Pending()` 返回 `a.resumed.need != nil`，而 `Recover()` 会把它清空。
当前能工作是因为 `TurnReq` 在调用链最内层 kernel **之前**构造（那时 `Recover` 还没执行），
但这个正确性依赖一个**隐式时序**：一旦有人把构造挪进 kernel、或 `f` 提前执行，`Resumed` 就失真。

**修法**（不新增机制，把语义显式化）：
- `turnWithMiddleware(ctx, resumed bool, f)` 和 `turn(ctx, resumed bool, f)` 加参数
- 4 个调用点按语义传值：`Recover` 路径 → `true`、`turnFailed` 的 `Retry` → `true`、
  `Drive` / `SendContent`（新回合）→ `false`
- 删掉对 `a.ag.Pending()` 的读取

**为什么更优**：`Resumed` 是「这一轮是不是恢复」的语义，应由**发起方**告诉链，
而不是让链去猜当前全局状态。读代码时能直接看出哪条路径算恢复。

### D3 `TestShellBackgroundJob` 的偶发失败（**未根治**，只加固了脆弱点）

**现象**：本地全量测试时出现过**一次**，12.79 秒后 step2 断言不符（「等待结束后应有全部输出」）。
此后单跑 10 次、包内 3 次、全量 2 次、`-race` 5 次、重负载 12 轮（CPU×4 忙循环）**均未复现**。
查 Gitea CI 近 10 个 Go job，**从未失败过**。

**已做的加固**（`8529446`）：
1. 不再硬编码 `job-1`/`job-2`——从启动输出解析实际 id（id 来自 `Shell.seq` 全局计数，
   将来共用实例或改编号会让硬编码断言失效）
2. `sleepCmd(1)` → `sleepCmd(2)`（负载高时 PowerShell 启动要几百毫秒，1 秒余量不足）；
   等待上限 20→10 秒（失败更快暴露，不靠等满）

**没改生产代码**：实测 `job_kill` 耗时 118–263ms（含重负载），远低于 `callKill` 的 5 秒阈值；
无证据支持放宽，贸然改只会掩盖真问题。

**状态**：⬜ **未根治**——加固的是「可以改进的脆弱点」，不是「确认的根因」。
**下次失败时需要的材料**：完整测试输出（不是只有 `--- FAIL` 一行），特别是：
- 失败发生在哪一步（step1/2/3/5）
- 实际拿到的 `out` 内容（断言消息里有，但需要完整上下文）
- 当时机器负载情况

**如果再次失败**：说明上面两个假设不对，需要重新定位，不要继续「再放宽一点超时」。
**量**：不定。**风险**：低（只影响测试稳定性，不影响功能）。
