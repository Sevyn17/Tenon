### ~~L2 T6a 跨机器预算的「发送方记账」~~ **已撤销：不该做，不是待做（2026-11-12）**

原以为这是「设计有、实现缺」的待办。核查后判定 **不是遗漏，而是不该做**。

**为什么不该做**：

1. **它在解一个不存在的部署场景**。`transport/web/remote.go` 的 `RemoteClient` **没有被任何
   主程序接上**（`apphost` / `tenon.New` 都没注入 `Host.Remote`）——框架具备跨机器能力，
   但没有真实多节点部署。
2. **就算做了，语义也是错的**。「被调用方的工作记到调用方账上」在分布式系统里是反模式：
   - B 崩溃 → A 永远收不到 usage → **账目永久丢失**
   - A 收不到回信 → 不知道 B 花了多少 → **无法判断该不该继续**
   - 要可靠就得两阶段确认（预扣/记账/结算），复杂度爆炸
   - 真实的分布式配额系统（云厂商）都是「各记各的 + 定期对账」，不是「调用方记账」
3. **单机内预算已经完整**。`budget_ref` 记账、`budgets` 表、超限挂起都已实现
   （`accountBudget` / `AccountBudget` / 迁移 v15）。跨机器记账属于分布式部署阶段，
   那时预算模型要重新设计，不是补一个字段能解决的。

**改为设计约束**（写进 08 8.4 更合适，此处记录）：

> 跨机器调用**不做**发送方记账。预算按机器本地记账；需要跨机器预算时，
> 由部署层用外部配额系统（网关限流、云配额）实现，不塞进框架。

**为什么要明确「不做」而不是留着**：留着会误导后来人以为这是遗漏，花时间去做一件
「听起来完整但没有真实价值」的事——正是本轮治理反复出现的同一个错误
（用架构完整性代替真实需求）。

### L3 插件进程的故障隔离粒度（原「按租户分进程」，**需求已修正**）

**原需求是错的**：原写「多租户下不可信插件能读到别的租户数据」。
核查发现 `runtime/store/store.go` 的 `const Tenant = "local"` 注释就是
「**当前租户（单机固定）**」——框架**没有多租户概念**，`Tenant` 是编译期常量。
按租户分进程是在解一个不存在的问题。

**但「分进程」本身在特殊场景有价值**。现状（`modules/extend/extproc/plugin.go`）：

```go
type plug struct {
    sup  *Supervisor   // 一个组件一个进程
    conn *extproc.Conn // 所有会话共用这一个连接
}
```

**一个 extproc 组件 = 一个进程 = 所有会话共用。** 真实问题不是租户隔离，而是：

| 问题 | 说明 |
|---|---|
| **崩溃爆炸半径** | 插件进程崩了，**所有会话**的该插件工具都不可用（`MaxCrashes` 后标记不可用） |
| **无资源隔离** | 一个会话的重负载插件调用会拖慢所有会话 |
| **无状态隔离** | 插件进程内的状态（缓存、连接池）所有会话共享 |
| **无法按会话重置** | 想重置某会话的插件状态，只能重启全局进程 |

**该按什么分**：不是租户，而是**故障域**。三种可选粒度：

| 粒度 | 适用场景 | 代价 |
|---|---|---|
| **按组件**（现状） | 默认，最简单 | 崩溃爆炸半径 = 全部会话 |
| **按会话** | 高价值会话需独立插件状态；或要能单独重置 | 进程数 = 会话数，内存开销大 |
| **进程池 + 租约** | 折中：N 个进程轮转，崩溃只影响当前调用方 | 复杂度中 |

**触发条件**（满足任一再做）：
- 出现「某插件崩溃影响了不该影响的会话」的**实际投诉**
- 需要「单独重置某会话的插件状态」的真实需求

**状态**：⬜ 等真实故障隔离需求。**不要为「架构完整性」提前做**——
进程池的复杂度（生命周期、路由、租约、健康检查）远高于收益。

### ~~D3 `TestShellBackgroundJob` 的偶发失败~~ **已修根因（2026-11-13）**

**现象**：本地全量测试时出现过**一次**，12.79 秒后 step2 断言不符（「等待结束后应有全部输出」）。
此后单跑 10 次、包内 3 次、全量 2 次、`-race` 5 次、重负载 12 轮（CPU×4 忙循环）**均未复现**。
查 Gitea CI 近 10 个 Go job，**从未失败过**。

**已做的加固**（`7aaa609`）：
1. 不再硬编码 `job-1`/`job-2`——从启动输出解析实际 id（id 来自 `Shell.seq` 全局计数，
   将来共用实例或改编号会让硬编码断言失效）
2. `sleepCmd(1)` → `sleepCmd(2)`（负载高时 PowerShell 启动要几百毫秒，1 秒余量不足）；
   等待上限 20→10 秒（失败更快暴露，不靠等满）

**根因（2026-11-13 复查代码定位）**：`command()` 里 `cmd.WaitDelay = 2 * time.Second`。
`WaitDelay` 只在「进程已退出、但还有子进程占着 stdout/stderr 管道」时生效，到点强制关管道。
高负载下最后一段输出还没被读进 `tailBuf`，管道就被关掉，于是「已结束」出现了但输出不全——
正是失败断言的形态。原先以为是 PowerShell 启动慢（所以加了 `sleepCmd(2)`），那只是掩盖。

**修法**：`WaitDelay` 放宽到 10 秒。正常情况进程退出后管道立刻 EOF，不会等满；
只有残留子进程才走这条路径，宁可多等也不要丢输出。

**顺带修掉一个同类缺陷**：`job_output` 增量读时，切点可能落在 ANSI 转义序列中间，
`stripANSI` 会把残缺序列连同它后面的正常文本一起吞掉（`\x1b[3` + `end` 里的 `e` 被当成
CSI 终止字节）。改为 `stripANSIHolding` 报告「末尾多少字节是残缺的」，`callOutput`
据此回退读偏移，等序列闭合再吐。新增 `ansi_test.go` 锁住这条。

**验证**：`go test ./modules/tools/shell ./runtime/host ./appapi -count=2` 全绿；
全量 `go test ./...` 全绿。**风险**：低（`WaitDelay` 只在异常路径生效）。

**复查补漏（2026-11-13，同一轮）**：`callOutput` 里读偏移的「读」和「写」分在两次加锁之间，
并发两次 `job_output` 会各自读到旧偏移、再互相覆盖，同一段输出被吐两次。已改成锁内一次完成
（`cleanHolding` 不碰 `s.mu`，无死锁风险）。**注意**：这条改动**没有**配套的回归测试——

### 审查记录：devkit 性能面审查（2026-11-13）

对象=整体，领域=性能（Q2），问题=缺陷。框架是库不是服务，没有前端与容量规划对象，
所以只对照 Q2.2 服务端、Q2.3 数据库、Q2.4 传输。

**Q2.3 数据库性能**

- **分页用游标，不是 OFFSET**：`ListSessionsIn` 用 `updated_at < ?` 加
  `ORDER BY updated_at DESC LIMIT ?`，配 `sessions_recent(tenant, updated_at)` 索引。
  这正是 Q2.3 说的「C 端无限滚动用游标」。深分页扫全表的问题不存在。
- **LIMIT 有硬上限**：`limit <= 0 || limit > 500` 一律改成 50，防止调用方传一个巨大的值。
- **无 `SELECT *`**：全部按列名显式列出，不会把 `meta`、`body` 这类大字段顺带查出来。
- **索引覆盖到位**：19 个索引，按查询场景建（`sessions_list`、`sessions_recent`、
  `session_entries_seq`、`session_inbox_drain`、`tool_results_deadline` 等），
  含两个部分索引（`sessions_key` 带 `WHERE session_key IS NOT NULL`）。
- **读写连接分离**：单写连接（`SetMaxOpenConns(1)`，SQLite 单写者语义）+
  4 个只读连接（`query_only=1`）。WAL 下读不必排在写后面，这是 2026-11-04 审查 P1-33
  修掉的串行问题。`busy_timeout=5000` 放在 pragma 第一位，后面的语句才有等待。

**Q2.2 服务端性能**

- **没有 N+1**：扫到的「循环内查询」19 处全是批量写（并库、迁移、删除）或分页拉取，
  都在事务里，不是逐条查询。
- **内存有界**：超大工具结果超过 32 KiB / 1000 行就存成工件，只回 16 KiB 预览，
  模型用 `read_artifact` 按行翻页（每页 1000 行）。上下文按模型窗口自动压缩。
- **背压处理正确**：事件总线的订阅者跟不上时**断开并给出断点 seq**（`ErrSlow`），
  不静默丢单条，客户端用 `Follow(after=Breakpoint)` 补齐。这是事件流该有的语义。

**Q2.4 传输**

- 未查 HTTP/2、压缩：框架用标准 `net/http`，压缩由部署层决定，不在框架职责内。

**结论**：性能上没有发现实质缺陷。分页、索引、连接池、内存边界、背压五处都是按
SQLite 与事件流的正确做法实现的，且注释里能看出踩过坑（P1-33 的读写串行、
`busy_timeout` 的 pragma 顺序）。

**没有做的**：容量模型与压测。框架不提供部署产物，QPS 与数据量级属应用层；
但 `docs` 里可以补一句「单库单写连接」的上限含义，让应用方知道写入是串行的。
这条并入 L16（备份与恢复文档）一起写。

### 审查记录：devkit 可观测性面审查（2026-11-13）

对象=整体，领域=可观测性（Q4），问题=缺陷。框架是库，没有告警与 SLO 对象
（属部署层），所以只对照 Q4.2 日志与 Q4.3 追踪。

**Q4.2 日志与请求记录**

- **结构化程度高**：`runtime/reqlog` 把一次模型请求拆成外壳（model / system / tools /
  params）+ 前缀（日志区间，可带压缩视图）+ 后缀（Transform 追加的消息），存储只记三部分
  的引用与 `final_hash`。存储量随步数线性增长，恢复时按三部分重组再校验 hash。
  这比「把整个请求写进日志」省得多，也比只记一行摘要可查得多。
- **无敏感信息落日志**：全仓 grep 没有把 `APIKey` / `Secret` / `token` 打进
  `Printf` / `Sprintf` 的地方。
- **trace 事件落表**：`recordTrace` 写 `trace_events`，带 `Trace`、`Session`、`Kind`、
  `Detail`。守卫拒绝（`guardDenied`）、信封投递、人工确认都有记录。

**Q4.3 追踪完整性**

- **span 树是完整的**：`turn` → `step` → `attempt` / `compact` / 工具调用，
  父子关系通过 `startSpan(kind, name, parent)` 传递，落 `trace_spans` 表
  （带 `session_id, started_at` 索引）。慢请求能定位到具体是哪一步、哪次尝试。
- **发现一处断链**（见 L17）。

**结论**：日志与请求记录的设计优于平均（分段引用 + hash 校验，兼顾存储与可查性）。
追踪的 span 树结构正确，但跨会话入口会重新分配 trace，导致父→子链路断开。

### L17 子会话不继承父会话的 trace，跨会话链路断开（2026-11-13 审查发现，方案已二次审查）

**核实过的现状**（方案前提，逐条读过代码）：

| 路径 | trace 处理 | 判定 |
|---|---|---|
| `Deliver`（人类/应用入口） | 第 61 行清空，`deliverCore` 第 144 行新分配 | 正确 |
| `DeliverAgent`（SDK `Ask`、小组） | 第 225 行清空，第 235 行新分配 | 正确（也是入口） |
| `DeliverRemote`（跨机器入站） | trace 为空才分配 | 正确 |
| `deliverQueued`（发件箱派发） | 完全沿用 | 正确 |
| **`spawn`（子智能体/工作组成员）** | 用 `hd.Do(Command{Kind: Send})` 投任务 | **断链在这里** |

**根因**：`Send` 不是信封，`actor.go:61-89` 把它写成 `store.InboxItem{ItemID, Kind, Input, Trust}`，
**没有 trace 字段**。回合开始时 `renderBatch`（`envelope.go:692`）只从
`parseEnvelope(it)` 取 env；`Send` 路径不写 `InboxItem.Envelope`，所以 `first` 是零值，
`env.Trace` 必然为空 → `actor.go:492` 的 `SetTrace("")` 把子会话 trace 置空。

**为什么不能简单改成「Send 也继承 trace」**：`actor.go:491` 那条规则是对的
（同一会话连发两条消息是两个独立任务），`TestTraceNotCarriedIntoPlainTurn` 在守它。

#### 方案（二次审查后修订）

**原方案有缺陷**：只给 `host.Command` 加 `Trace` 字段。但 `Send` 会先把命令写进
**持久化的 inbox 表**（`Admit`），重启后从表里重放——内存里的 `Command.Trace` 早没了。
跨进程重启后 trace 仍然丢。而且 `InboxItem` 有 `Envelope` 字段，`Send` 路径没用它。

**修订方案：把 trace 存进 inbox 项，随 inbox 一起持久化。**

1. `store.InboxItem` 加 `Trace string` 字段；`session_inbox` 表加 `trace TEXT NOT NULL DEFAULT ''`
   列（走一次迁移）。这比复用 `Envelope` 干净：`Send` 不是信封，硬塞一个假信封会让
   `renderBatch` 误判它是信封路径（会改变 `content` 的渲染方式与 `untrusted` 判定）。

2. `actor.go` 的 `Admit` 调用带上 `Trace: c.Trace`（`Command` 仍加 `Trace` 字段作为入口）。

3. `renderBatch` 返回值加一个 trace：批次里第一个非空 `it.Trace`。
   `actor.go:492` 改成：

   ```go
   trace := env.Trace
   if trace == "" {
       trace = batchTrace   // 来自 inbox 项的 Trace
   }
   a.ag.SetTrace(trace)
   ```

4. `spawn` 投任务时带上父会话当前 trace：

   ```go
   parentTrace := ""
   if phd, ok := h.Get(parent); ok {
       parentTrace = phd.Agent().TraceID()
   }
   hd.Do(Command{Kind: Send, ItemID: NewItemID(), Text: task, Source: "agent",
       Trust: TrustOf(untrusted), Trace: parentTrace})
   ```

5. `modules/collab/workgroup` 派成员同样带上组长当前 trace。

**为什么选这条而不是别的**：

| 方案 | 否决理由 |
|---|---|
| 让 `Send` 一律继承上一回合 trace | 违反「普通 Send 不沿用旧 trace」，`TestTraceNotCarriedIntoPlainTurn` 会红 |
| 只加 `Command.Trace`（原方案） | **跨重启丢失**：`Send` 走持久化 inbox，内存字段不落库 |
| 复用 `InboxItem.Envelope` 塞假信封 | `renderBatch` 会把它当信封路径处理，改变内容渲染与可信度判定 |
| 把 `spawn` 改成走信封（`deliverQueued`） | `spawn` 要同步等子回合结束取最终文本，信封是异步投递，语义不匹配 |

**代价**：一次 schema 迁移（加一列，有默认值，向后兼容）。迁移成本低，
但这是**唯一能跨重启保住 trace 的方案**——如果只在内存里传，重启后链路照样断。

#### 验收

- 新用例：父会话调 `subagent`，`explain <父 trace>` 能同时列出父与子会话的事件。
- 新用例：同一路径下进程重启（重新 `Open` 会话）后，子会话仍记在父 trace 下。
- `TestTraceNotCarriedIntoPlainTurn` 保持绿（普通 Send 仍不继承）。
- `TestExplainTraceListsPath` 保持绿（信封链路不受影响）。
- `storetest` 的 inbox 契约测试补 `Trace` 字段的读写往返。

#### 顺带修

`envelope.go:96-97` 的注释两次引用 `host.StampOutbound`，但全仓没有这个函数
（grep 只命中注释）。改成说明内核字段实际在哪写（`deliverCore` 第 144 行与各入口）。

- **量**：小到中（一次迁移 + 约 40 行 + 两个用例）。**风险**：中低（动 inbox 表结构，
  但有默认值且只增列；不影响现有路径语义）。
