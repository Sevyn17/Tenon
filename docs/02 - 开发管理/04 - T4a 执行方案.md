## 二、交付物

## 三、文件与类型

### 3.1 存储接口（`runtime/store/collection.go`，新文件）

```go
type CollectionSpec struct {
    Version   int      // 结构版本；0 视作 1
    Indexes   []string // 可等值查询的字段；必须是 Doc 里存在的键
    Partition string   // 分区字段，缺省 "tenant"；写入时必须等于 part
}

type Doc struct {
    Key     string
    Version int64          // 从 1 起；Put 成功后存储加一
    Body    map[string]any // 含 Partition 字段
}

type Page struct {
    After string // 上一页最后一条的 Key；空 = 从头
    Limit int    // 缺省 100，最大 1000
}

type Collection interface {
    Get(ctx context.Context, part, key string) (Doc, error)
    Put(ctx context.Context, part string, doc Doc, ifVersion int64) error
    Delete(ctx context.Context, part, key string, ifVersion int64) error
    Query(ctx context.Context, part, index string, eq any, page Page) ([]Doc, Page, error)
}

type CollectionStore interface {
    // Open 打开或登记一个集合。同名再次打开时 spec 必须相同，否则返回错误。
    Open(ctx context.Context, tenant, owner, name string, spec CollectionSpec) (Collection, error)
}
```

规则：

- 全名是 `<owner>.<name>`，由调用方传入的 owner、name 组成。存储不解析组件身份。
- `ifVersion = 0` 表示必须不存在；其他值必须等于当前 `Version`。不符返回已有的 `store.ErrConflict`，不存在返回 `store.ErrNotFound`。`Delete` 同样：0 只用于删除一个尚未写入的 key（必定返回 `ErrNotFound`），不表示"不看版本直接删"。
- `Query` 只查等值，**不提供"列出一个分区的全部"**。要全量就自己声明一个恒为固定值的索引字段。理由见 3.6：有了这个口子，调用方会靠它做序号生成，而分页会把结果截断。
- `Query` 只做等值，按 `Key` 升序，返回的 `Page.After` 为空表示没有下一页。`index` 不在 `Indexes` 里返回错误。
- 分区 = 租户 + `part`。`Put` 时 `Body[spec.Partition]` 必须等于 `part`，否则返回错误。
- 不做查询语言、关联查询、聚合。`Body` 用 JSON 存，字段类型只保证 JSON 往返（数字在 JSON 里是 `float64`，调用方自己转换）。

### 3.2 SQLite（`runtime/store/sqlite/collection.go`，新文件）

核心迁移加 **v13**，只加表：

```sql
CREATE TABLE collections(
    tenant TEXT NOT NULL, owner TEXT NOT NULL, name TEXT NOT NULL,
    spec TEXT NOT NULL, version INTEGER NOT NULL,
    PRIMARY KEY(tenant, owner, name));
CREATE TABLE collection_docs(
    tenant TEXT NOT NULL, owner TEXT NOT NULL, name TEXT NOT NULL,
    part TEXT NOT NULL, key TEXT NOT NULL,
    version INTEGER NOT NULL, body TEXT NOT NULL, updated_at INTEGER NOT NULL,
    PRIMARY KEY(tenant, owner, name, part, key));
CREATE TABLE collection_versions(
    tenant TEXT NOT NULL, owner TEXT NOT NULL, name TEXT NOT NULL,
    version INTEGER NOT NULL,
    PRIMARY KEY(tenant, owner, name));
```

索引不预建。`Indexes` 里的字段存在 `body` JSON 里，`Query` 先按主键前缀（tenant, owner, name, part）取出该分区，再在内存里等值过滤、按 `key` 排序、按 `Page` 截断。一个分区的文档量是组件数据，不是会话日志；真的需要索引时再加版本，不在本步猜。

`Open` 在一个事务里写 `collections`：已有行的 `spec` 文本必须与本次相同。

### 3.3 内存（`runtime/store/memstore/collection.go`，新文件）

用 `map` 按（tenant, owner, name, part, key）存。`Tx` 沿用现有深复制：进入事务时复制集合状态，出错恢复（`runtime/store/memstore/substore.go`）。

### 3.4 事务

`Store.Tx` 传进 fn 的视图也实现 `CollectionStore`。在事务里 `Open` 到的句柄，写入随事务提交或回滚。sqlite 的实现把 `*sql.Tx` 放进句柄，与现有 `q()` 走当前执行器的做法相同。

跨分区不支持：一个 `Collection` 句柄的每次调用都带 `part`，不提供"一次写两个 part"的方法。组件要写两个分区就开两个事务，接受中间状态。

### 3.5 登记入口（`runtime/component/collection.go`，新文件）

```go
// Collection 登记并返回句柄。句柄在 Start 之前不能用，用了返回"集合尚未打开"。
func (cx *Registrar) Collection(name string, spec store.CollectionSpec) (store.Collection, error)
func (cx *Registrar) CollectionMigration(m store.CollectionMigration) error
```

`Collection` 在 `Setup` 里调用，只登记、不碰存储，把句柄交给组件自己保存（`workgroup` 存在 `Group` 上）。同组件同名重复登记返回错误。

句柄何时打开，按这个顺序，放在 `Assembly.Start` 之前、由 `apphost` 与 SDK 的启动路径调用：

1. 取存储。没实现 `CollectionStore` 就报"存储不支持集合"，带上登记了集合的组件名。
2. 跑迁移（见下）。
3. 对每个登记调用 `Open`，成功后句柄可用。任一个失败，启动失败，带组件名与集合名。

`Open` 必须在迁移之后。反过来就会把新 `spec` 写进 `collections` 而数据还是旧形状，随后的写入按新版本读旧数据。

`CollectionMigration`：

```go
type CollectionMigration struct {
    Collection string
    From       int
    After      []string // "<组件>.<集合>"，那些集合先迁完
    Run        func(ctx context.Context, c store.Collection) error
}
```

跑法：按 `After` 拓扑排序，环与未知依赖拒绝启动。每个集合从 `collection_versions` 的版本迁到 `spec.Version`，一次只升 1，缺行视作版本 0。`Run` 拿到的句柄是**迁移中的旧版本**：只保证 `Get` / `Put` / `Delete` 可用，`Query` 按旧 `Indexes` 走，不能依赖本次要升到的 spec。`Run` 里的写入走同一个存储事务，失败整批回滚并拒绝启动。`Run` 为 nil 表示该版本没有数据要改，只推进版本号。

版本只允许加 1 的登记：`From` 必须从 0 连续到 `spec.Version - 1`，跳号拒绝启动。否则一个没写迁移函数的版本会被跳过，旧数据按新版本读。

租户：登记入口不接收租户参数。`Open` 的租户取 `store.Tenant`（当前固定 `local`）。多租户时改这一处，不改组件代码。

### 3.6 workgroup 任务板

改 `modules/collab/workgroup/workgroup.go` 的 `Create`、`List`、`get`、`update`：

- `Setup` 里登记 `Collection("tasks", CollectionSpec{Version: 1, Indexes: []string{"status", "owner"}, Partition: "team"})`，句柄存进 `Group`。
- 分区键用现有的 `team`（领导会话 id）。`Doc.Key` 用任务 id 的十进制、固定 10 位补零（`fmt.Sprintf("%010d", id)`）。不补零的话 `Query` 按 `Key` 字符串升序，`10` 会排在 `2` 前面，`List` 的 `ORDER BY id` 就保不住了。
- `Create` 的自增 id 不走 `Query`：`Query` 必须带索引和等值条件，没有"列出分区全部"这个操作，而任务 id 不在任何索引里。改为集合外的计数器，每个分区一行，放同一集合、固定 key `__seq__`：`Get` 读到当前值，`Put` 带 `ifVersion` 写回下一个，冲突就重试。计数器行用 `Body` 里的标记字段与任务行区分，`List` 时跳过。不再用 `INSERT ... SELECT MAX(id)`。
- `update` 的 `rev` 列改为 `Doc.Version`：`Put(..., ifVersion: t.Rev)`，返回后 `Rev = t.Rev + 1`。`ErrConflict` 的文本保持不变。
- `p_workgroup_tasks` 的数据要搬。v0.1.x 已发布，别人的库里可能有任务板；01 的规则是旧版本的库升级后能直接用，不能靠"开发库是空的"跳过。搬法放在 workgroup 的 `Start` 里、集合打开之后，跑一次：表不存在就跳过（内存存储没有这张表），表在就读出全部行，按上面的 key 规则 `Put` 进集合，然后 `DROP TABLE`。这一步走 `store.SQL`，不进 `CollectionMigration`——来源是 SQL 表，集合迁移函数拿不到 SQL。失败就返回错误，不删表，下次启动重跑；`Put` 用 `ifVersion: 0`，重跑时已搬过的行会冲突，冲突按"已存在"跳过。
- `p_workgroup_runs` 与 `Requires{SQL: true}` 不动。03 方案里"删掉 Requires"这一句按本篇修正：投递账还在 SQL 表上，删了启动不了。

## 四、测试

加进 `runtime/store/storetest/storetest.go` 的 `Run`，两个实现都跑：

| 用例 | 断言 |
|---|---|
| `CollectionRoundTrip` | Put 后 Get 读回；Version 从 1 起，第二次 Put 后为 2 |
| `CollectionConflict` | ifVersion 不符返回 `ErrConflict`；0 对已存在的 key 同样冲突；不存在返回 `ErrNotFound` |
| `CollectionQueryPage` | 只按声明的索引等值查；未声明的索引报错；分页不重不漏；按 Key 升序 |
| `CollectionPartition` | 一个 part 读不到另一个 part；Body 的分区字段与 part 不符时报错 |
| `CollectionTx` | 事务内写入提交后可见；fn 返回错误后不可见（memstore 与 sqlite 都要，沿用 `TxRollback` 的口径） |
| `CollectionSpecStable` | 同名再次 Open 且 spec 不同，返回错误，原数据不变 |

workgroup 现有测试不改断言：`workgroup_test.go` 的任务板用例全走 `Group` 的方法，没有直接插入 `p_workgroup_tasks` 的语句。`settle_test.go` 查 `p_workgroup_runs` 的语句不动。另加一个用例：先用 SQL 建一张带两行数据的 `p_workgroup_tasks`，再跑 `Start`，断言两行进了集合、表已删除、任务 id 与 `rev` 保持原值。

回归：`go vet ./...`、`go test ./...`，两套快照无差异。快照覆盖的是模型请求，任务板不进请求，预期无差异。
