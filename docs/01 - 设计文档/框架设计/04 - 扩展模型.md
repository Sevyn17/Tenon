## 4.1 三条扩展路

| 路 | 写什么 | 运行在哪 | 能做什么 | 适合 |
|---|---|---|---|---|
| 组件 | Go 代码，实现 `tenon.Component` | 编进同一个程序 | 本篇列出的全部点位 | 标准组件、应用自己的业务组件 |
| 插件 | Node / Python 等任意语言，独立进程 | 子进程或远端 | 点位的一个子集（4.8） | 不想写 Go、要隔离、第三方分发 |
| 定义 | 定义包（`agent.toml` + 文件） | 不运行代码 | 组合已有能力 | 新增一个智能体 |

原则：**能用定义解决的不写组件，能用组件解决的不改内核**。内核本身不提供扩展点之外的修改方式。

## 4.2 组件接口

```go
type Component interface {
    Name() string                 // 全局唯一，也是 [use.<名>] 的 key，也是集合和事件名的前缀
    Setup(r *Registrar) error     // 装配期：登记点位、声明依赖和配置
}

// 可选接口，实现了才调用
type Starter   interface { Start(ctx context.Context) error }          // 所有组件 Setup 完成后，按依赖顺序
type Stopper   interface { Stop(ctx context.Context) error }           // 逆序
type Requirer  interface { Requires() Requires }                      // 对框架的要求，如 SQL 存储（05 5.7）
type Validator interface { ValidateAgent(def *tenon.Agent) error }     // 配置结构之外的定义级检查（03 3.6）
```

`Registrar` 是组件拿到的唯一入口，装配期之后失效：

```go
type Registrar struct{ /* 内部 */ }

func (r *Registrar) Config(v any)                          // 组件配置结构，见 06
func (r *Registrar) AgentConfig(v any)                     // [use.<名>] 的结构，见 03 3.2、06 6.2
func (r *Registrar) DependsOn(names ...string)             // 只影响装配和启动顺序（4.5）
// 提供服务用泛型函数 tenon.Provide[T](r, impl)，见 4.5；Go 方法不能带类型参数，所以不是 Registrar 的方法

func (r *Registrar) Collection(name string, spec CollectionSpec) (Collection, error) // 自己的数据集合，实际名 <组件名>.<name>；只登记不碰存储，句柄在 Assembly.Start 之前由框架打开，之前调用返回 ErrCollectionClosed（05 5.6）
func (r *Registrar) CollectionMigration(m CollectionMigration) error               // 集合的版本迁移，From 从 0 连续到 spec.Version-1（05 5.6）

func (r *Registrar) Tool(t Tool)                           // 工具
// 中间件用泛型函数 tenon.Wrap[Req, Resp](r, point, mw)，见 4.3；类型和点位不匹配编译不过
func (r *Registrar) On(event string, h EventHandler)       // 事件订阅（4.6）
func (r *Registrar) Matcher(name string, m Matcher)        // 订阅匹配器
func (r *Registrar) ResourceType(t ResourceType)           // 资源类型（group、board…）
func (r *Registrar) Renderer(kind string, rd Renderer)     // 信封怎样注入会话
func (r *Registrar) Guard(g GuardRule)                     // 向守卫登记规则（下文、08 8.1）
func (r *Registrar) Template(src SpecSource)               // 内置定义模板，归入平台命名空间
func (r *Registrar) Status(key string, fn StatusFunc)      // 状态片段，状态更新的唯一提交方式（12 12.5）
func (r *Registrar) Mailer() *Mailer                       // 绑定到本组件的发信句柄（4.7），Start 之后可用
```

`Collection` 的句柄和事务：

```go
type Coll struct{ /* 内部 */ }

// part 是分区值；传空串表示按集合的 Partition 从 *Ctx 推出，缺省为租户（05 5.6）
func (c *Coll) Get(ctx context.Context, part, key string) (Doc, error)
func (c *Coll) Put(ctx context.Context, part string, doc Doc) error
func (c *Coll) Delete(ctx context.Context, part, key string) error
func (c *Coll) Query(ctx context.Context, part string, q Query) ([]Doc, error)
func (c *Coll) Tx(ctx context.Context, part string, fn func(tx CollTx) error) error

type CollTx interface {                    // 只能读写本集合、本分区
    Get(key string) (Doc, error)
    Put(doc Doc) error
    Delete(key string) error
}

type Migration struct {
    Collection string                      // 本组件的集合名
    From, To   int                         // 版本号
    Run        func(ctx context.Context, tx MigrateTx) error
}
```

存储怎样实现这些接口、分区怎样落表，由 05 5.6 规定。

`StatusFunc` 的签名是 `func(c *Ctx) []StatusItem`。`key` 可以以 `*` 结尾表示动态前缀（如 `file.*`），这时 `fn` 返回的每一项自己带完整 key，且必须落在这个前缀下。框架每次调模型前调用全部 `fn`，只发变化的 key（12 12.5）。中间件和工具里没有别的提交途径。

工具的结构：

```go
type Tool struct {
    Name        string
    Description string
    Params      any                                    // Go 结构体，生成 JSON Schema（10 10.1）
    Idempotent  bool                                   // 崩溃后能否安全重跑（02 2.6），缺省 false
    Risk        Risk                                   // RiskLow | RiskHigh；external 触发的高风险调用要人工确认（08 8.5）
    Visible     func(c *Ctx) bool                      // 可空：本会话是否暴露（子会话不带委派工具、工作组成员只拿成员工具）
    Run         func(c *Ctx, args json.RawMessage) (Result, error)
}
```

工具对象全局一份：装配期构造、注册进每个会话的工具集，会话之间共用同一批只读对象；会话差异只看 `Visible` 和调用时的 `*Ctx`，**不按会话重造工具**（4.4）。`Run` 里需要会话信息时从 `c` 取，不从闭包里预先捕获。

装配时框架做的检查：

- 名字重复、依赖缺失、依赖成环 → 启动失败。
- `Template` 带来的定义归入平台命名空间。与应用定义同名 → 启动失败。
- `Requires()` 不满足（如要 SQL 但存储是 KV）→ 启动失败。
- 某个定义写了 `[use.x]` 但 `x` 没装 → 加载该定义失败（03 3.6）。

这些检查都在启动时做完，运行中不会出现"组件不存在"。

守卫规则的结构（D4）：

```go
type Verdict int
const (
    Abstain Verdict = iota // 不表态，交给其他规则和内核缺省
    Allow                  // 只能放开"往 session: 投递"的缺省限制
    Deny                   // 任一条 Deny 即拒绝
)

type GuardPoint int
const (                                      // 与 4.3 的中间件点位同名
    GuardDeliver GuardPoint = iota           // 投递，对应 Deliver
    GuardSessionOpen                         // 建会话，对应 SessionOpen
    GuardTurn                                // 一轮开始或恢复，对应 Turn
    GuardModelCall                           // 调模型，对应 ModelCall
    GuardToolCall                            // 调工具，对应 ToolCall
)

type GuardRule struct {
    Name  string
    On    GuardPoint
    Check func(c *Ctx, req GuardRequest) (Verdict, string) // string 为拒绝原因，进 guard.denied
}

type GuardRequest struct {
    Point    GuardPoint
    Envelope *Envelope                       // GuardDeliver、GuardSessionOpen 时有值
    Agent    string                          // 目标定义名，GuardSessionOpen 时有值
    Tool     string                          // GuardToolCall 时有值
    Args     json.RawMessage                 // GuardToolCall 时有值
    Risk     Risk                            // GuardToolCall 时为工具声明的风险
    Model    string                          // GuardModelCall 时有值
}

type Risk int
const (
    RiskLow  Risk = iota
    RiskHigh                                 // external 触发时要人工确认（08 8.5）
)
```

`Context` 点位不设守卫：它只组装上下文，不产生外部效果。

`Allow` 放不开可联系名单、预算、跳数、租户边界（08 8.1）。规则只能来自编译进程序的组件（4.8）。

## 4.3 中间件链

同步扩展只有一种形式：**洋葱式中间件**，包在内核的固定点位外面。没有另一套"生命周期钩子"。

```go
type Middleware[Req, Resp any] func(c *Ctx, req Req, next func(*Ctx, Req) (Resp, error)) (Resp, error)

type Point[Req, Resp any] struct{ /* 内部 */ }  // 点位带着自己的请求 / 响应类型

func Wrap[Req, Resp any](r *Registrar, p Point[Req, Resp], mw Middleware[Req, Resp])

// 用法：类型不匹配编译不过
tenon.Wrap(r, tenon.ToolCall, func(c *tenon.Ctx, req *tenon.ToolCallReq,
    next func(*tenon.Ctx, *tenon.ToolCallReq) (*tenon.ToolCallResp, error)) (*tenon.ToolCallResp, error) {
    return next(c, req)
})
```

| 点位 | 请求 / 响应类型 | 包住的是 | 典型用途 |
|---|---|---|---|
| `SessionOpen` | `SessionOpenReq` / `SessionOpenResp` | 新建一个会话（02 2.2） | 写入缺省 `meta`、登记成员、拒绝创建 |
| `Deliver` | `DeliverReq` / `DeliverResp` | 一封信封投递到会话信箱 | 过滤、改写、按规则转投到别的 `session:` |
| `Turn` | `TurnReq` / `TurnResp` | 一轮运行中的一段（02 2.4）：从取信或恢复开始，到这一轮完成、挂起或中断为止 | 回合前准备、回合后处理、压缩 |
| `Context` | `ContextReq` / `ContextResp` | 组装发给模型的上下文 | 记忆召回、多人发言的格式 |
| `ModelCall` | `ModelCallReq` / `ModelCallResp` | 一次模型请求 | 脱敏、换模型、记账、重试 |
| `ToolCall` | `ToolCallReq` / `ToolCallResp` | 一次工具调用 | 权限确认、沙箱、审计、限流 |

各类型的字段在实现时定，原则是：请求带本点位的输入，响应带本点位的输出，`*Ctx` 带公共信息（4.4）。

`Context` 中间件的限制（B15、B16）：

- 不能改系统提示词。系统提示词只来自定义和框架（12 12.5 的 L0–L1）。
- 不能加不进历史的注入。要让模型看到会变的信息，只能走 `Registrar.Status`（12 12.5）。
- 能做的是：重排、改写历史条目的渲染格式，以及在组装时附加进历史的内容。

`ModelCall` 中间件换模型会让前缀缓存失效（12 12.3），应只在必要时用。

规则：

- **顺序确定**：按组件依赖拓扑排序，同层按名字；`tenon.New` 可以显式覆盖。`explain` 能列出每个点位上的中间件顺序。
- **可以短路**：不调用 `next` 就是拦截（如权限拒绝），返回的错误按正常错误处理。
- **不能绕过守卫**：守卫在最内层、紧贴内核执行，中间件改写后的请求仍要过守卫（08）。
- **`Turn` 不跨挂起**：一轮等工具、等人、预算挂起或进程重启后，`Turn` 中间件链在恢复时重新调用一次，`req.Resumed = true`，并能读到检查点。中间件不能把状态放在闭包或调用栈里等它"回来"，需要跨段保留的状态写进会话或组件集合。
### 4.3.1 四类扩展，四个 API（2026-11-11 定案）

原写「现有的层、系统块、回合后点位都收进这六个点位，不再各写一套」。落地后发现「层」（`SessionLayer`）
同时承担了三件事，混在一起才产生了 `Authorizes` / `Guard` / `Timeout` / `FailOpen` 四个补丁字段。
所以不是「收进六个点位」，而是**按本质分成四类，各有正确的 API**：

| 类别 | 本质 | API | 例子 |
|---|---|---|---|
| **贡献** | 往会话里放一份数据 | `Tool` / `SystemBlock` / `Status` / `PermissionItem` / `ResourceType` / `Matcher` | 工具、系统提示块、状态项 |
| **拦截** | 包住一次操作，可改写、可短路 | `Wrap[Req,Resp](r, point, mw)`（六个点位） | 脱敏、审计、限流 |
| **决策** | 这次操作准不准（纯判定，可挂起问人） | `WrapGuard[Req](r, point, name, fn)` 判定区 + `r.Authorizer(a)` 服务 | 权限档位、沙箱逃逸、预算 |
| **通知** | 事情发生了，告诉我（不能否决） | `OnSessionReady` / `OnAfterTurn` / `OnSessionDelete` | hooks、group |

**「会话层」（`SessionLayer` / `LayerEntry` / `toolhub.Layer`）要拆掉**，8 个注册者按上表归位：

| 组件 | 实质 | 归到 |
|---|---|---|
| permission | 决策（授权判定，原 `Authorizes`） | `Authorizer` 服务 + `ToolCall` 判定区 |
| sandbox | 决策（逃逸）+ 改写（限参数） | `ToolCall` 判定区 + 改写区 |
| redact（2 个登记） | 改写（脱敏）+ 决策（写守卫） | `ToolCall` 改写区 + 判定区 |
| hooks（2 个登记） | 副作用 / 决策（pre 可拒绝） | `ToolCall` 改写区 + 判定区 |
| instructions | 改写（追加项目指令，原 `Timeout`+`FailOpen`） | `ToolCall` 改写区（超时由中间件自己 `select`） |
| extproc | 改写 / 拦截 | `ToolCall` 改写区 |

**判定区为什么是纯谓词而不是中间件**：多条判定不是洋葱叠加，而是「任一拒绝即拒绝」（reduce）；
且「恰好一个授权者」是内核不变量，链结构表达不了。

**`Authorizer` 服务只给 `ToolCall`**：只有工具调用需要「挂起问人」。其余点位的准入用判定区谓词就够
（`Deliver` 的联系名单、`ModelCall` 的预算、`SessionOpen` 谁能建会话都是无副作用判定）。

**判定区永远在改写区之内**（更靠内核）：改写完的请求才交给判定，「改写绕过守卫」不成立。

**`FailOpen` 不引入新字段**：中间件自己负责（超时后 `select` 走放行分支），框架不提供通用开关——
通用开关会让「这个中间件失败该不该阻断」变成配置问题，而不是组件作者的显式决定。

**链在装配期编译**：`Wrap` 只登记元数据，`Assemble` 结束把每个点位编译成具体类型的闭包；
调用路径无 `any` 断言、无每调用分配；空链直接是内核函数本身（零开销）。
组件是全局单例（4.4），链静态、会话差异靠 `*Ctx`——1000 个会话也是 6 条链。

迁移顺序（风险从低到高，每步独立可验证）：补原语 → `extproc` → `redact` → `instructions`+`hooks` →
`permission`+`sandbox` → 删 `SessionLayer`。执行方案见 [02 - 开发管理/15 - 扩展点重构方案](<../../02 - 开发管理/15 - 扩展点重构方案.md>)。

## 4.4 组件是全局单例

每个组件在进程里只有一份，同时服务所有会话。这和 HTTP 服务器一样：处理函数只有一份，每次请求带自己的上下文。

**每次调用的 `*Ctx`** 由内核填好，组件不需要自己传：

| 字段 | 含义 |
|---|---|
| `Tenant()` | 租户（一等字段，不从 `meta` 取） |
| `Session()` | 当前会话 id、所属定义及版本、创建者、父会话 |
| `Trigger()` | 本轮主触发者（信封 `from`）；多人会话里每轮可能不同（02 2.4，B21） |
| `Envelopes()` | 本轮合并的全部信封（同一权限主体：同一触发用户、同一 `budget_ref`，B21） |
| `Config()` | 本会话算好的使用配置 `[use.<本组件>]`（06，D8），只读 |
| `Meta()` | 会话 `meta`（05 5.4），只读 |
| `Trace()` | trace id、`budget_ref`、`origin`、`caps`（08） |

**组件的状态分两类**：

| 类型 | 例子 | 做法 |
|---|---|---|
| 无会话状态 | 模型客户端、记忆检索、权限判断、连接池 | 纯单例；需要按会话或用户区分的数据，以（租户、会话 / 用户）为键存进存储 |
| 有会话状态的资源 | shell 进程和当前目录、浏览器标签页、沙箱容器、有状态的 MCP stdio 服务 | 单例管理器 + 会话级句柄：首次用到时创建，会话休眠或空闲超时回收，设总量上限 |

框架提供 `tenon.SessionLocal[T]` 帮组件管理会话级句柄：按会话 id 取或建，会话休眠、关闭时自动调用句柄的 `Close`。

**组件必须满足的约束**：

- **并发安全**：同一个组件会同时被很多会话调用。不能把某个会话的信息存在组件字段里。
- **隔离**：框架对每次中间件和工具调用单独 recover、设超时，一个会话的 panic 或超时不影响其他会话。组件自己的后台协程同样要 recover。
- **公平**：组件按租户设并发上限，防止一个租户占满共享资源（连接池、浏览器、沙箱）。
- **不在进程内存里放唯一副本**：会话可能在另一个节点被唤醒（02 2.2），需要跨轮保留的状态都写存储。

## 4.5 带类型的依赖注入

组件之间通过接口取服务，不通过全局变量或字符串查找：

```go
// memory 组件提供
tenon.Provide[MemoryService](r, m)

// context 组件使用
func (c *Context) Setup(r *tenon.Registrar) error {
    tenon.Need[MemoryService](./r)            // 按类型声明依赖
    return nil
}
func (c *Context) Start(ctx context.Context) error {
    c.mem = tenon.Use[MemoryService](./ctx)   // 只能取 Need 过的类型；装配期已经保证取得到
    return nil
}
```

- 服务按 Go 类型登记和查找，同一类型只能有一个提供者；要多个就用不同接口类型。
- `Need[T]` 让框架找到 `T` 的提供者，并据此决定启动顺序。没人提供 → 启动失败。`Use` 一个没 `Need` 过的类型 → 启动失败。
- `DependsOn(names...)` 只用于"不取服务，但要在某组件之后启动"的情况。
- 应用可以在 `tenon.New` 里用 `tenon.Override[T](./impl)` 替换某个服务，测试套件（10）靠这个注入假实现。

## 4.6 中间件和事件（B7）

| | 中间件 | 事件 |
|---|---|---|
| 时机 | 同步，在调用链上 | 异步，事后 |
| 能做什么 | 改请求、改结果、拦截 | 只能读 |
| 失败影响 | 本次调用失败 | 不影响主流程，记日志、按策略重试 |
| 顺序 | 确定 | 不保证跨订阅者顺序；同一会话内按发生顺序 |
| 例子 | 权限确认、脱敏、记账 | 写审计库、推界面、同步到应用自己的数据库 |

两套不重叠：**想改行为用中间件，想知道发生了什么用事件**。不提供"异步但能改结果"的东西。

事件来自内核写下的日志（会话日志、信箱、资源日志），所以：

- 每个事件有单调递增的序号，订阅者记住自己读到哪，重启后接着读，至少一次送达。
- 订阅者要按序号去重，做到幂等。
- 应用把数据同步到自己的库就走这条路（05 5.3 第三条路）。

**组件事件日志与会话事件日志是两条**（T4b，2026-11-10 落地）。会话事件表 `session_events` 按会话、服务界面订阅、有保留期，走 `bus.Source`。组件事件日志是另一条：全局一条序号、不按事件名分、没有保留期，组件用 `Registrar.On` 订阅，读位点由框架按"<组件>.<事件名>"记住，进程重启后从记下的位置接着读。

- 读位点只前进。`SetCursor` 的序号小于已记下的值时拒绝，框架不会把同一条再交给同一个订阅。
- 订阅方处理失败不影响主流程：记宿主日志，按 1 秒起翻倍重试三次，用尽后跳过这条继续。不重试到永久，否则一个坏订阅会把后面的事件全部堵住。
- 发布在存储事务提交之后，回滚不产生事件。
- 不跨机器。同一存储上的进程重启可续读；跨机器续读要远端传输，归 T6a。
- 事件名只允许小写字母、数字、点，可选末尾一个 `.*` 表示前缀。

事件名用 `<来源>.<动作>`：`session.created`、`turn.done`、`tool.called`、`mail.delivered`、`guard.denied`。组件事件不在 07 7.5 那张表里——那张表是应用协议的线上事件。

## 4.7 显式点位清单

框架刻意只开下面这些点位，新增点位要改本篇：

| 点位 | 登记方法 | 内核用它做什么 |
|---|---|---|
| 工具 | `Tool` | 按定义 `tools` 白名单挂载 |
| 中间件 | `tenon.Wrap[Req, Resp]` | 六个调用点（4.3） |
| 事件 | `On(name, fn) error` | 异步通知；`name` 末尾 `.*` 表示前缀，处理函数签名 `func(ctx, ComponentEvent) error`（4.6） |
| 资源类型 | `ResourceType(t) error` | 小组、看板、外部线程。`t.Name` 是地址类型（小写字母、数字、下划线，最长 32），跨组件同名拒绝 |
| 匹配器 | `Matcher(name, fn) error` | 订阅扇出时判断投给哪个会话。名字与资源类型同一规则；内置 `exact`、`prefix`、`list`，组件同名登记拒绝。模型判断类匹配器只能由组件登记（内核不内置）：组件用 `component.ModelMatcher(judge, max)` 把「可调模型的判断函数 + 失败按不匹配 + 判断次数上限」包成标准匹配器（T5c）；按订阅者预算记账随预算账本，v1 后 |
| 渲染器 | `Renderer` | 信封注入会话的格式 |
| 守卫规则 | `Guard` | 投递和调用前的强制检查 |
| 定义模板 | `Template` | 组件自带的定义，归入平台命名空间 |
| 定义字段 | `AgentConfig`、`Validator` | 校验 `[use.<名>]` |
| 数据 | `Collection(name, spec) (Collection, error)`、`CollectionMigration(m) error` | 组件自己的数据；句柄在 `Assembly.Start` 之前打开，之前调用返回 `ErrCollectionClosed`（05 5.6） |
| 服务 | `tenon.Provide[T]`、`tenon.Get[T]` / `GetOptional[T]`（4.9） | 组件之间调用 |
| 状态提交 | `Status(key, fn)` | 每次调模型前收集，只发变化的 key，写成一条 `status` 条目（12 12.5） |
| 投递 | `Mailer()` | 组件发信封、建会话（下文） |

不开的：改内核表结构、改会话状态机、替换守卫、替换调度器。需要这些说明框架设计有缺口，应当改框架本身。

**投递句柄 `Mailer`**。渠道、定时、小组、工作组这类组件要自己发信封或建会话。`Registrar.Mailer()` 返回绑定到本组件的句柄，组件冒充不了别的组件：

```go
type Mailer struct{ /* 内部，绑定登记它的组件 */ }

func (m *Mailer) Send(ctx context.Context, to Address, body Body, opts ...SendOption) (SendResult, error)
func (m *Mailer) Spawn(c *Ctx, agent string, opts ...SendOption) (SendResult, error) // 建子会话并发 request，内核签发 corr
```

`Address`、`Body`、`SendOption`、`SendResult` 与 07 7.3 是同一组类型。`WithKey(key)` 只有 SDK 和 `Mailer` 能用，模型工具不能传 key（07 7.3）。

信封字段怎样填：

| 场景 | `from` | `via` | `origin` |
|---|---|---|---|
| 在会话里调用（`ctx` 带 `*Ctx`） | 当前会话 | 无 | 取自 `*Ctx`，`caps`、`hop`、`budget_ref` 也取自 `*Ctx` |
| 会话外转发用户消息（渠道） | 应用鉴权后经 `tenon.WithUser` 带入的用户 | 本组件 | `human`，由入口类型决定 |
| 会话外的定时、webhook | `component:<本组件名>` | 无 | `external` |

- `origin` 由入口类型决定，组件不能声明 `origin = human`，只能把信任降级。
- 组件能投给哪些定义，按登记 `Mailer` 时声明的定义名单（08 8.1）。守卫照常检查（`GuardDeliver`、`GuardSessionOpen`）。

**资源扇出 `Mailer.Fanout`**（T4c，04 4.7）。资源记录存在组件自己的集合里，内核不存、也不发现"有新记录"。组件写完一条记录后，把该资源的订阅从自己的集合查出来传进来：

```go
func (m *Mailer) Fanout(ctx context.Context, rec ResourceRecord, subs []Subscription) (FanoutResult, error)
```

一封扇出信封这样填：`from` 是记录的发言者（联系名单看的是发言者，不是转发组件），`via` 是本组件，`to` 是订阅的 `subscriber`（只接受 `session:`，别的地址记一条错误并跳过），`kind` 是 `notify`，`mode` 由匹配器给（空则 `notice`），`origin` 是 `external`，正文用资源类型的 `Render`（没有就用记录正文）。`hop`、`trace`、`caps` 不填，由 `Host.Deliver` 写。

订阅的 `exclude` 在跑匹配器之前按来源地址排除，用来防"自己的回复又投回自己"，不靠跳数。单条订阅的地址不对、匹配器报错、投递被拒都记日志并收进 `FanoutResult`，不挡住其余订阅；`Fanout` 返回错误只表示没有投递服务。联系名单缺省会拒扇出信封（发言者通常不是会话创建者），持有资源的组件须登记一条 `Allow` 规则放行"本组件转发"的信封；这条规则放不开跳数。

**标准模块只用公开点位**：`tenon/context`、`tenon/chat`、`tenon/group` 等随 SDK 发布的模块，和第三方组件一样只能用本节列出的点位，内核不给它们留后门。这样每个标准模块都可以不装，也可以被应用自己的实现整个替换（01 1.2）。

## 4.8 插件（外部进程）

插件和组件走同一套装配、开关、`explain` 和信任规则，差别只是跑在另一个进程里。按接入成本分四档（沿用草案 9.4）：

| 档 | 形式 | 能贡献 |
|---|---|---|
| 1 | 插件包：目录 + `tenon-plugin.toml` | 定义、提示词、技能、MCP 配置、缺省配置。不运行代码 |
| 2 | MCP server | 工具 |
| 3 | 扩展进程：stdio 上的 JSON-RPC 2.0，是 MCP 的超集 | 工具，加上中间件、事件订阅、匹配器、资源类型、渲染器 |
| 4 | 远端智能体（A2A） | 一个 `remote:` 地址 |

第 3 档的协议要点：

- 握手时插件报告自己要登记的点位，框架按 4.2 的规则检查，等同于一次 `Setup`。
- **一个插件进程服务所有会话**（和组件一样是单例）：每个请求带租户、会话 id、触发者，插件必须支持多个请求并发进行（靠 JSON-RPC 请求 id 区分）。需要强隔离的不可信插件可以配置成按租户各起一个进程。
- 中间件跨进程调用有延迟，插件只能挂 `ToolCall`、`Deliver` 两个点位；`ModelCall`、`Context` 这类每轮都会走的点位只对组件开放。
- 插件不能 `Provide` 服务，也不能 `Guard`。守卫规则只能来自编译进程序的代码。
- **插件进程由插件宿主监管**：崩溃后按退避重启（缺省最多连续 5 次，之后标记不可用并发 `plugin.crashed`）。不可用期间它挂的中间件按登记时声明的 `fail_open` / `fail_closed` 处理，默认 `fail_closed`；它的工具调用直接返回错误。这和 02 的子会话重启策略无关。
- 插件来的工具和定义同样受权限交集和 `origin` 标记约束（08），装进来不等于被信任。
