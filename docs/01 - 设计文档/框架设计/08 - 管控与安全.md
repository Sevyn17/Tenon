# 08 管控与安全

> 状态：草案（2026-11-01）。整理自 [99 存档](<./99 - 目标态架构草案(原文存档).md>) 第八节和 12.2，补上和组件、配置的关系。

## 8.1 原则

**配置写在组件里，强制执行在内核守卫里**（03 3.2）。组件负责解释 `[use.agent] contact`、`[use.budget]` 这些配置，并通过 `Registrar.Guard` 把规则交给守卫；守卫在内核里、紧贴投递和调用执行，中间件和模型都绕不过去（04 4.3）。

守卫检查的时机：

| 时机 | 检查 |
|---|---|
| 信封投递前 | 可联系名单、跳数、预算、租户边界 |
| 工具调用前 | 工具白名单、有效权限、来源标记、预算 |
| 模型调用前 | 预算 |
| 新建会话前 | 发往 `agent:` 的可联系名单；派生子会话的可派生名单、所属树深度 |
| 一轮开始前 | 并发上限（8.4） |

被拒绝时：返回错误给调用方（模型能看到原因，可以换做法），写 `guard.denied` 事件。

**组件规则怎么合并**（D4）：组件通过 `Registrar.Guard` 登记的 `GuardRule` 返回 `Deny`、`Allow` 或 `Abstain`。任一条 `Deny` 即拒绝；全部 `Abstain` 走内核缺省规则；`Allow` 只能放开"往 `session:` 投递"的缺省限制，放不开可联系名单、预算、跳数和租户边界。

> 落地（2026-11-02，T3）：`plugin.GuardRule` / `Verdict` / `GuardPoint` / `GuardRequest` 已在 `runtime/component`，组件在 `Setup` 里 `Registrar.Guard` 登记；`Host` 在信封投递前（`GuardDeliver`）与新建会话前（`GuardSessionOpen`）执行规则并合并结论（`Deny` 优先，`Allow` 只放开 `session:` 投递的缺省联系名单），拒绝写 `guard.denied`。一轮/调模型/调工具三个点位的规则执行随守卫中间件在后续步骤接入。

## 8.2 联系与派生

联系规则只以本节为准，02、13 引用这里，不另写（D4）。

| 地址 | 缺省谁能投 | 怎么放开 |
|---|---|---|
| `session:<id>` | 会话创建者、同一所属树里的会话（父子、派生链）、通过 `corr` 核对的回信。不按定义名放行 | 成员组件通过 `Registrar.Guard` 返回 `Allow`（多人会话、跨用户投递，T4） |
| `agent:<名字>` | 智能体：发送方 `[use.agent] contact` 里有这个名字。人：按定义的可见性和这个人的创建权限。组件：按 `Registrar.Mailer()` 登记时声明的定义名单 | 不能由 `Allow` 放开，只能改名单或可见性 |
| `human:<用户>` | 本会话的创建者、本轮触发者、成员组件登记的成员 | 在 `[use.agent] contact` 里显式写 |

- 名单的来源是 `[use.agent] contact / spawn`，没写等于空，即默认谁都不能联系。
- 派生（创建子会话）查可派生名单 `spawn`。
- 定义的创建者不再默认可联系；需要时由定义来源填 `owner`，模型改不了。
- 回信核对见 02 2.3：`corr` 由内核签发，存在、未过期、未用过、发送者是预期回复方才收，只收第一条。
- 读别的会话历史的工具也过守卫：本轮触发者要有权访问目标会话（02 2.5）。
- 跨租户投递不支持，任何地址都不行，组件的 `Allow` 也放不开（8.8）。

**`control` 信封**：只有会话创建者、父会话、内核和登记了该会话的组件能发。其他发送者的 `control` 拒绝并记 `guard.denied`。多人会话（T4）里，本轮触发者可以中断本轮（02 2.4）。

**组件发信**：组件通过 `Registrar.Mailer()` 拿到绑定到本组件的发信句柄，冒充不了别的组件。在会话外调用时 `from = component:<名>`。渠道转发用户消息时，`from` 是应用鉴权后经 `tenon.WithUser` 带入的用户，组件只记为经手方 `via`。会话键 `key` 只开放给 SDK 和 `Mailer`，模型工具不能传（02 2.3）。

## 8.3 权限只降不升

被调用方本次处理的有效权限 = 它自己的权限（`tools` ∩ `[use.permission]`）∩ 信封里的 `caps` ∩ 租户上限 ∩ 用户上限。`caps` 是解析后的具体工具集合，不含通配，由内核在投递时写入，等于发送方那一轮的有效权限；调用方传入的值忽略（D2）。这里的用户是本轮触发者，不是会话创建者：多人会话里，低权限用户的消息触发不了高权限工具；一轮只合并同一权限主体（同一触发用户、同一 `budget_ref`）的信封，不同权限主体分轮处理（02 2.4，B21）。v1 一个会话只支持创建者一个用户，多人会话和转人工放在 T4（B23，13）。

`[use.permission]` 是上限，只收窄定义的 `tools`，不额外授予工具。写法 `mode = "<档位>"`：每次调用按会话档位与该档位各判一次，取更严的结论（2026-11-02 落地，`permission.UseConfig` / `Policy.Cap`）。

- 低权限智能体不能借高权限智能体越权：A 没有 `shell`，调 B（有 `shell`）时，B 这次也不能用 `shell`。
- 权限随信封沿链传递，存在信封的 `caps` 里，不靠会话上下文推断。
- 回信（`reply`）触发的一轮，`caps` 沿用原请求那一轮，不被回信方压低（D5）。
- 应用运行时新建的定义（B3）同样受租户、用户上限约束：用户层定义的 `tools` 和 `[use.permission]` 超出创建者自己的有效权限时，写定义接口在保存时拒绝，报错列出超出项，不静默截断。已存的定义在创建者之后被降权时，加载不报错，靠运行时求交兜底；运行时再与触发者求交（03 3.5，D7）。用户不能给自己建一个超出自己权限的智能体，别人调用它也拿不到超出自己权限的工具。

## 8.4 预算与归属

区分归属（谁创建了谁，用于取消和回收）和成员关系（谁在哪个小组）。

记账按**触发**：信封带 `budget_ref`，由它引起的工作记到这个账上。一轮只合并同一 `budget_ref` 的信封，记到本轮主触发者的账上（D5）。

- 被调用方的工作记到调用方的账上（**仅限同一进程内**；跨机器见下）。
- 小组里的消息记到小组归属者的账上。
- 一个加入多个小组的智能体，各组消耗分开记。

**跨机器调用不做发送方记账**（2026-11-12 定案）。理由：

1. 「被调用方的工作记到调用方账上」在分布式系统里是反模式——B 崩溃则 A 永远收不到 usage，
   账目永久丢失；A 收不到回信则无法判断该不该继续。要可靠就得两阶段确认（预扣/记账/结算），
   复杂度远超收益。
2. 真实的分布式配额系统（云厂商）都是「各记各的 + 定期对账」，不是「调用方记账」。
3. 单进程内 `budget_ref` 记账已完整（`accountBudget`、`budgets` 表、超限挂起）。
   跨机器预算属于分布式部署阶段，那时预算模型要重新设计。

**部署层需要跨机器预算时**，用外部配额系统（网关限流、云配额）实现，不塞进框架。
接收方仍然**跳过**远端信封的记账（`batchBudgetRef` 的 `isRemoteOrigin` 判据），
避免「双方都记」重复计费。

预算层级按 06 6.3 取最小：定义 `[use.budget]`、用户、租户各一层；用户层取本轮触发者。标了 `limit:"intersect"` 的字段每轮按本轮触发者重新求交，不沿用创建会话时算好的值（06，D8）。用尽时：当前步做完、不再发起新的模型或工具调用，会话转入"预算挂起"（02 2.2），发 `budget.exceeded`，等应用加额度或人确认后 `Resume`。

**并发上限**：会话之间并行，并发总量由守卫控制。按定义、租户、用户各设"同时在跑的一轮"上限，超出的会话在信箱里排队；模型供应商的限速由模型调度统一处理。原来实例串行顺带压住了并发，改成会话并行后必须显式限流。

## 8.5 不可信输入

- `origin` 由入口类型决定：应用鉴权后的用户 = `human`，定时和 webhook = `external`，智能体发出的 = `agent`。外部事件、外部线程、工具返回的网页 / 文件内容标记 `origin = external`。
- 组件只能降低 `origin` 的可信度，不能升高，自己不能声明 `origin = human`。渠道转发的用户消息算 `human`，是因为 `from` 是应用鉴权过的用户（8.2）。
- 标记沿触发链传递，经过一个智能体转述不会变成可信。一轮合并的信封里任一封是 `external`，本轮就是 `external`（02 2.4）。
- `origin = external` 的信封不在运行中插入，排队到本轮结束后另起一轮（02 2.4）。
- 由 `external` 触发的工作调用高风险工具时必须走人工确认，不能靠提示词放行。哪些工具算高风险由工具登记时声明。
- 事件源白名单用程序规则写，不用模型判断。

## 8.6 人作为地址

- `human:x` 可挂多个端点，请求推到所有在线端点，按 `corr` 取第一条回复，其余端点的待办自动关闭。
- 请求带 `deadline`；人不在线时留在信箱，上线后推送；到期按定义里声明的缺省动作处理（默认拒绝）。
- 智能体问人和问智能体走同一条路。

## 8.7 防刷屏与追溯

- 信封带 `hop`，由内核写入，调用方传入的值忽略。规则：
  - 人、应用、定时和 webhook 入口发出的信封 `hop = 0`。
  - 会话在一轮里发出的 `request`、`notify`（发往 `agent:`、`session:`、派生子会话），`hop` = 触发本轮的信封里最大的 `hop` 加一。
  - `reply` 不加一，沿用对应请求的 `hop`；`control` 不加一。
  - 到上限（默认 8，见约束清单；租户可调小随 T4）时，守卫拒绝投递，记 `guard.denied`，发送方的工具调用收到 `ErrHopLimit`，模型能看到原因。已签发的 `corr` 随之作废，不会留下等不到的回信。
- 小组另有单条消息的回复数上限和冷却时间（组件配置）。
- 一次任务的全部信封共享 trace id，`explain trace <id>` 能画出经过的会话、资源、工具和花费。
  - 落地（2026-11-02，v1 收口）：`store.TraceStore`（`trace_events` 表 + memstore 同语义）；`Host.Deliver` 缺省分配 trace id 并沿用调用方的值；投递/会话开始/工具调用/守卫拒绝记 trace 事件；`host.ExplainTrace` 渲染会话、信封、工具与拒绝原因，CLI `tenon explain trace <id>`（`runtime/host/explain_test.go` 覆盖）。花费与资源级明细（按 trace 汇总 token/成本）未做，留给调试界面。

## 8.8 租户隔离

- 所有内核表带 `tenant` 列（05 5.8），存储原语的每个接口都要求带租户，取不到租户的调用直接报错。
- 地址解析限定在本租户内。跨租户投递不支持，组件的 `Allow` 也放不开（8.2）。
- 缓存、事件订阅、`explain` 都按租户过滤。
- 组件的 `Collection` 自动按租户分区，组件代码拿不到别的租户的数据。

## 8.9 密钥与日志

- `secret` 字段（06 6.2）不进日志、请求记录、`explain`、事件。
- 请求记录（reqlog）默认保存完整模型请求，应用可以按租户关闭或只存摘要，用于合规场景。
