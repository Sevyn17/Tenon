## 一、为什么要改

现在的内核以**会话**为中心：`session` 是状态机，`agent` 只是把 session、toolhub、modelhub 串起来的驱动循环，`host` 管的也是会话。智能体在概念上和功能上都不存在：

- 没有定义。所有会话用同一份工具、层、系统块构造（`runtime.Builder.Build(id string, child bool)`），不同会话只靠 `child` 一个布尔值区分。
- 没有身份。角色靠插件猜 ID，例如工作组用 `strings.Contains(sc.ID, "/m-")` 判断成员。恢复时只能再猜一遍。
- 不能被找到。智能体之间没有地址，子智能体是同步阻塞的工具调用，深度 1 写死在 `Child` 的语义里。

目标态把中心换成**智能体**：会话降为智能体的一段工作记录。用户、界面、其他智能体打交道的对象都是智能体。

## 三、核心概念

只有四个基本概念，加上一类"资源"：

| 概念 | 含义 | 由现在的什么演进 |
|---|---|---|
| **智能体定义（AgentSpec）** | 声明式的"用什么模型、按什么提示词、能用哪些工具、挂哪些组件" | 新增 |
| **智能体实例（Agent）** | 按定义创建的持久实体，有地址、状态、归属 | 新增 |
| **地址（Address）** | 能收信封的东西都有地址：智能体实例、人、资源、远端智能体 | 新增 |
| **信封（Envelope）** | 消息的统一格式 | 由 inbox 项加上路由字段而来 |
| **资源（Resource）** | 有地址、有追加式日志、有成员和归属者的共享对象。小组、看板、外部线程都是资源 | 新增 |

另有两个从属概念：

- **信箱（Mailbox）**：实例的收件队列，按实例收，不按会话收。由现在的 `session_inbox` 升级而来，保留"先落库再确认、按 item id 幂等"的规则。
- **线程（Thread）**：实例内部的一段对话上下文，就是现在的 session，状态机照用。一个实例可以有多条线程。

### 3.1 地址

格式为 `类别:名字`：

| 类别 | 例子 | 说明 |
|---|---|---|
| `agent` | `agent:router`、`agent:router/coder-1` | 实例。子实例的地址带上归属者前缀 |
| `human` | `human:qsevn` | 人。一个人可以挂多个端点（CLI、桌面、网页、IM） |
| `group` | `group:dev-room` | 小组 |
| `board` | `board:dev-room` | 看板 |
| `ext` | `ext:github/owner/repo#123` | 外部线程，由桥接插件映射 |
| `remote` | `remote:host/agent:x` | 远端智能体（A2A） |
| `exec` | `exec:laptop-01` | 执行端：工具在哪里执行（12.5） |

所有地址都在某个租户内（12.2）。完整形式为 `类别:租户/名字`，例如 `agent:acme/router`；单机形态租户固定为 `local`，可以省略。

### 3.2 信封

```
id            全局唯一，幂等键
from, to      地址
kind          request / reply / notify / control
corr          关联 id：回复和请求对上；一次任务的全部信封共享一个 trace id
reply_to      回复投到哪里（缺省回 from）
hop           智能体触发智能体的跳数
origin        来源可信度：human / agent / external（见 8.3）
budget_ref    记账归属（见 8.2）
body          正文；长内容只放摘要和续读入口
deadline      可选：超时后视为无回复
```

## 四、智能体定义

### 4.1 原则

定义只回答三件事：**用什么模型、按什么提示词、能用哪些工具**。其他能力（记忆、协作、预算、定时唤醒）都是"挂一个组件，再给它一段配置"。这样内核认识的字段很少，场景再多也不用改定义格式。

### 4.2 字段

| 字段 | 含义 | 缺省 |
|---|---|---|
| 键名 | `[agent.<名字>]`，就是定义名 | 必填 |
| `description` | 一句话说明。别的智能体把它当工具用时，工具描述就取这句 | 必填 |
| `model` | 模型或模型档位（`light` / `strong`） | 全局缺省模型 |
| `prompt` | 系统提示词，文件路径或内联文本 | 无 |
| `tools` | 工具白名单，支持通配。组件提供的工具也在这里点名 | 空，即只能回复 |
| `use` | 挂载的组件及各自的配置，`use.<组件名> = { ... }` | 无 |
| `resident` | 是否常驻。缺省空闲即休眠，有新信封时再激活 | `false` |

版本不写在定义里，内核按内容哈希自动记录，会话行记下用的是哪个哈希。

```toml
[agent.router]
description = "接需求、拆任务、派给成员、验收结果"
model       = "light"
prompt      = "prompts/router.md"
tools       = ["agent.*", "group.*", "board.*"]   # 不给执行类工具，只能派发
resident    = true
use.agent   = { spawn = ["coder", "reviewer"], contact = ["human:*", "group:*"] }
use.budget  = { tokens = "5M", max_depth = 3, max_instances = 10 }

[agent.coder]
description = "按任务契约改代码并自测"
model       = "strong"
tools       = ["fs.*", "shell.*"]

[agent.support]
description = "电商客服，回答商品和订单问题"
model       = "light"
prompt      = "prompts/support.md"
tools       = ["kb.search", "order.query", "memory.*"]
use.memory  = { store = "memlib", by = "user" }     # 记忆按会话的使用者分区（第十三节）
```

### 4.3 从定义里拿掉的东西

上一版定义分八块。审视后，下面这些都不再是定义字段：

| 原来的块 | 现在怎么做 | 理由 |
|---|---|---|
| 版本 | 内容哈希，自动记录 | 手写版本号容易忘改 |
| 记忆（线程策略、压缩、作用域） | 挂 `compact`、`memory` 组件 | 记忆的做法因场景而异，内核不必知道 |
| 接口（能否当工具、能否移交） | 由 `agent` 组件根据 `description` 生成工具；调用方有没有这个工具就决定能不能用 | 能力由调用方的 `tools` 决定，不需要被调用方再声明一次 |
| 关系（`can_spawn`、`can_contact`） | 写在 `use.agent` 里；组件把它登记给守卫执行 | 只有用协作工具的智能体才需要它 |
| 生命周期三档 | 只留 `resident` 一个布尔值。临时实例由创建者回收（归属树），其余空闲即休眠 | `ephemeral` / `persistent` 的区别其实是"谁创建、谁回收" |
| 约束（权限档位、预算） | 挂 `permission`、`budget` 组件 | 这两个是安全组件，由守卫执行，配置仍跟着定义走 |

内核仍负责执行约束：组件把配置翻译成规则登记给守卫，守卫在投递和调用工具时检查。配置在组件里，执行在内核里。

### 4.4 来源

定义来源有三处，后者覆盖前者：组件内置模板、用户目录、项目目录。项目目录里的定义沿用"项目受信才加载"的规则。第一版**不允许智能体在运行时新建定义**，智能体只能从已有定义里挑，并可覆盖提示词。用户可以通过管理接口新建和修改自己的定义。

### 4.5 组件总表

审视现有内置插件后，目标态的组件如下。"变化"一列说明和现在相比改了什么：

| 分组 | 组件 | 作用 | 变化 |
|---|---|---|---|
| 协作 | `agent` | 调用、异步调用、当工具用、移交、开子实例 | 取代 `subagent`；子智能体只是"开一个实例再调用它" |
| 协作 | `group` | 小组资源、@ 和关键词参与规则 | 从 `workgroup` 拆出 |
| 协作 | `board` | 看板任务、契约、依赖、认领、完成关卡 | 从 `workgroup` 拆出；工作组 = 定义模板 + `group` + `board` |
| 协作 | `scheduler` | 定时投递信封，`schedule` 匹配器 | 新增 |
| 协作 | `watchdog` | 按时检查实例有无真实进展 | 新增，本身就是一个挂了 scheduler 的智能体定义 |
| 上下文 | `prompt`、`instructions`、`skills` | 系统提示词、项目说明、技能 | 不变 |
| 上下文 | `compact` | 线程压缩 | 原 `compact-basic` |
| 上下文 | `memory` | 记忆库：写入、召回、遗忘、列出 | 新增；后端可换（本地 SQLite、向量库、OntoMem 等） |
| 上下文 | `render` | 信封注入线程时的 Inline / Spill | 新增 |
| 上下文 | `redact` | 脱敏 | 不变 |
| 模型 | `models`、各模型适配器 | 模型档位与协议适配 | 不变 |
| 工具 | `fs`、`shell`、`web`、`mcp`、`todo`、`codemode` | 执行类工具 | 不变 |
| 工具 | `ask-user` | 向人提问 | 改为"向 `human:` 地址发请求"的一层包装 |
| 安全 | `permission`、`sandbox` | 权限档位、沙箱 | 不变；规则登记给守卫 |
| 安全 | `budget` | 预算账本 | 新增，从守卫里拆出配置部分 |
| 存储 | `store-sqlite`，以后 `store-postgres` | 存储接口的实现 | 内核只依赖接口（12.7） |
| 接入 | IM、GitHub、邮件桥接 | 外部群和线程映射成资源 | 新增，T5 |
| 扩展 | `hooks` | 钩子 | 不变 |

## 五、小组与参与规则

小组 = 地址 + 共享消息记录 + 成员表 + 每个成员的参与规则。界面上显示为一个群。

```toml
[group.dev-room]
title   = "开发小组"
owner   = "agent:router"     # 归属者：负责生命周期，承担预算
lead    = "agent:router"     # 可选：对结果负责的成员；没有就是纯群聊
members = [
  { who = "human:qsevn",    join = "always" },
  { who = "agent:coder",    join = "mention" },
  { who = "agent:reviewer", join = "mention", also = ["keyword:PR"] },
  { who = "agent:tester",   join = "claim" },
  { who = "agent:watcher",  join = "semantic", prompt = "有人报 bug 时才介入" },
]
rules = { max_replies_per_msg = 2, agent_hop_limit = 3, cooldown = "30s" }
board = true
```

参与方式：

| 方式 | 含义 | 由谁判断 |
|---|---|---|
| `always` | 每条都收 | 内核匹配器 |
| `mention` | 被 @ 才收 | 内核匹配器 |
| `keyword` / `source` / `type` | 命中关键词、来源、消息类型 | 内核匹配器 |
| `assigned` | 负责人点名 | 内核匹配器 |
| `claim` | 看板上有匹配任务时认领 | 看板组件 |
| `schedule` | 定时查看 | scheduler 组件 |
| `semantic` | 模型判断与自己是否相关 | 组件（消耗 token，第一版可不做） |

程序规则先过滤，过滤剩下的才交给 `semantic`（两级过滤）。

**一条 @ 消息的流程**：消息追加到小组日志 → 内核按订阅表对每个成员跑匹配器 → 命中的成员各收到一封信封，信封里内联近几条相关消息的摘要，全文留在小组里 → 成员在自己"对应这个小组的线程"里处理 → 回复投回小组地址，所有成员可见。

**子智能体团队**：主智能体用 `group_create` 建小组，用 `use.agent.spawn` 里列出的定义开出成员并拉进来。小组的归属者是主智能体，预算从它身上扣，它结束时按归属树一起回收。成员还能再建小组，层数不写死，由 `use.budget.max_depth` 限制。

## 六、协作方式

不做流程图式的编排（A5）。可靠性靠机制约束边界，路线由智能体自己定：

| 问题 | 机制 |
|---|---|
| 该分工时不分工 | 按角色裁剪能力：主智能体的定义里不给执行类工具 |
| 跳步、没验证就说完成 | 完成关卡：任务完成须附验收证据；机制检查证据是否齐全，派发方判断是否够（A9） |
| 打转、互相推诿 | 预算沿归属链扣减；跳数上限；Watchdog 判断有没有真实进展 |
| 结果不可预期 | 任务契约：派发时写明目标、验收标准、输出格式 |

协作用到的组件工具，都建在"投递信封"这一个原语上：

| 用法 | 组成 |
|---|---|
| 同步调用 | 发 `request`，等同一 `corr` 的 `reply` |
| 异步调用 | 发 `request` 立即返回 Started，`reply` 作为新信封回到信箱 |
| 当工具用 | 由定义的描述和接口自动生成工具，工具内部就是调用 |
| 移交 | 把线程的控制权连同摘要交给另一个实例 |
| 小组发言 | 投递到小组地址，按订阅扇出 |
| 认领 | 看板任务条件写入（rev），依赖由 `blocked_by` 决定先后 |
| 脚本批量派发 | 可选工具（A8） |

## 七、运行时行为

每个实例是一个 actor：

1. **激活。** 信封投到休眠实例时，运行时按需激活它：从存储加载定义、信箱和线程。`resident` 实例常驻；其余空闲一段时间后休眠，释放内存，不丢状态。
2. **选线程。** 按信封决定交给哪条线程：缺省规则是同一 `corr`、同一资源或同一发送者的信封进同一条线程，其余开新线程。多人使用同一个智能体时，每个人自然落在自己的线程里（第十三节）。需要别的分法时由组件替换这条规则。
3. **跑一步。** 同一时刻只有一个推理在跑（A2）。"串行"是按步，不按任务：耗时工具和对其他智能体的调用默认异步，返回 Started 后实例就能处理下一封信封，结果回来时作为新信封进信箱。
4. **合并。** 推理期间到达的多封信封，下一步一次性注入（原文的批处理，Router 的吞吐靠它）。
5. **落库。** 每步 checkpoint，崩溃后按信箱、请求记录、幂等记录恢复，沿用现有机制。

## 八、管控

### 8.1 联系与权限

- 投递前检查 `use.agent.contact`。没列出的地址拒绝投递，错误回给发送方。
- **权限只降不升**：被调用方本次处理的有效权限 = 它自己的权限 ∩ 触发链上各方的权限。低权限智能体不能借高权限智能体越权。

### 8.2 预算与归属

区分**归属**和**成员关系**：

- 归属：谁创建了谁。取消、回收沿归属树进行。
- 成员关系：谁在哪个小组里。一个不由别人创建的智能体可以加入多个不属于自己的小组。

记账按**触发**而不是按归属：一封信封带 `budget_ref`，由它引起的工作记到这个账上。小组里的消息记到小组归属者的账上；被调用方的工作记到调用方的账上。这样一个加入多个小组的智能体，各小组的消耗不会混在一起。

### 8.3 不可信输入

外部事件、外部线程里的内容按 `origin = external` 标记，这个标记沿触发链传递，不会因为经过一个智能体转述就变成可信。由 `external` 触发的工作调用高风险工具时，必须走权限确认，不能靠提示词放行。事件源白名单用程序规则写。

### 8.4 人作为地址

- `human:x` 可以挂多个端点，请求同时推到所有在线端点，按 `corr` 取第一条回复，其余端点的待办自动关闭。
- 请求带 `deadline`（沿用现在的确认截止时间）。人不在线时请求留在信箱里，上线后再推送。
- 智能体问人和智能体问智能体走同一条路，子会话转发确认这类特殊处理取消。

### 8.5 防刷屏与追溯

- 每条信封带 `hop`：智能体触发智能体时加一，到上限停止。小组另有单条消息的回复数上限和冷却时间。
- 一次任务的全部信封共享 trace id，`explain` 能画出它经过的实例和资源。这一项在 T2 就要做，不能拖。

## 九、架构

### 9.1 分层

```
接入层   CLI / 桌面 / 网页 / IM / GitHub / A2A      都只是地址端点，收发信封
──────────────────────────────────────────────────────────────
组件     协作：调用、移交、小组、看板、scheduler、Watchdog、语义匹配器
（内置） 能力：fs、shell、web、mcp、模型适配器、记忆、技能、脱敏、权限、沙箱
         存储：store-sqlite 等
──────────────────────────────────────────────────────────────
内核     定义注册表 · 实例生命周期 · 信箱投递 · 资源与订阅 · 调度
         线程（会话状态机） · 能力挂载 · 账本与守卫 · 归属树 · 模型调度
──────────────────────────────────────────────────────────────
存储     定义 · 实例 · 线程日志 · 信箱 · 信封 · 资源日志 · 订阅 · 账本 · 请求记录
```

### 9.2 内核

内核只回答"智能体怎么存在、怎么收消息、怎么被约束"，不知道"群"或"@"是什么：

| 模块 | 职责 | 由现在的什么演进 |
|---|---|---|
| spec | 加载、校验、合并定义；记录版本 | 新增（取代 `Builder` 里的全局配置） |
| actor | 实例的激活、休眠、按信箱驱动、选线程 | `host` + `agent` |
| mail | 地址解析、投递、幂等、关联 id、trace | inbox |
| resource | 通用资源：地址、追加日志、成员表、归属者；订阅 =（订阅者，资源，匹配器），投递时按匹配器扇出 | 新增 |
| thread | 会话状态机：回合、步、fork、rewind | `session`（基本不变） |
| mount | 按定义挂载能力：工具、层、系统块 | `toolhub` + `runtime.Builder` |
| guard | 联系权限、权限取交集、跳数、来源标记、预算账本 | 新增 |
| tree | 归属树：按树取消、回收 | `parent_id` |
| modelhub / reqlog / store / bus | 保留 | `store` 增加新表 |

内核里的匹配器只做程序规则（来源、@、关键词、类型）。需要模型判断的匹配器会消耗 token、影响线程内容，由组件登记。

### 9.3 组件

组件和内核同仓库、编译进同一个程序，由组件管理器装配。它们向内核贡献东西的点位：

| 点位 | 例子 |
|---|---|
| 工具 | `agent_call`、`group_post`、看板工具、fs、shell |
| 定义模板 | 工作组、群聊、Router + Worker 各是一套定义加小组配置 |
| 资源类型 | `group`、`board`、`ext:github` |
| 匹配器 | `claim`、`schedule`、`semantic` |
| 信封渲染器 | 信封怎样注入线程（Inline / Spill）：小组消息带前后文，PR 评论带 diff 片段 |
| 桥接 | IM、GitHub、邮件的群和线程映射成资源 |
| 层、系统块、回合后 | 现有点位保留 |
| 界面视图 | 按资源类型选视图：小组显示为群，看板显示为任务列 |

### 9.4 外部扩展

不编译进程序、在单独进程或远端运行的扩展。按接入成本从低到高：

| 档 | 形式 | 能贡献什么 |
|---|---|---|
| 1 | **插件包**：目录 + `ybase-plugin.toml` | 定义文件、提示词、技能、钩子、MCP server 配置、缺省配置。不需要新协议 |
| 2 | **MCP server** | 工具 |
| 3 | **扩展进程协议**：MCP 的超集，stdio 上跑 JSON-RPC 2.0 | 工具之外再加：资源类型、匹配器、桥接、事件订阅、信封渲染、调用层 |
| 4 | **远端智能体（A2A）** | 一个 `remote:` 地址。本地定义的公开部分导出为 Agent Card |

外部扩展接进来后和内置组件走同一套装配、开关、explain、信任规则。外部来的定义和工具受 8.1 的权限交集和 8.3 的来源标记约束，不因为是"装进来的"就被信任。

## 十二、部署形态、性能与安全

### 12.1 三种形态

| 形态 | 存储 | 运行 | 执行环境 |
|---|---|---|---|
| 单机 | SQLite | 单进程 | 本机 fs / shell，经本地沙箱 |
| SaaS | Postgres + 对象存储 | 多个无状态节点，实例按租户和实例 id 分片 | 租户隔离的沙箱容器，或用户电脑上的端侧守护进程（12.4） |
| 嵌入 | 由宿主项目提供（实现存储接口） | 作为 Go 库，或作为服务（HTTP / WebSocket） | 由宿主项目决定，常见是只开业务工具、不开 fs / shell |

三种形态共用同一套内核，差别只在装哪些组件。内核里的接口不能直接依赖某个具体后端。

### 12.2 多租户隔离

- **租户是内核一级字段。** 所有表的主键都带 `tenant`，地址带租户（3.1）。守卫拒绝跨租户投递，跨租户协作只能走显式配置的 A2A。
- **凭据不进模型上下文。** 工具只拿到凭据引用，由执行层在调用时替换成真值。模型看不到，也就泄露不了。
- **每个租户有配额**：同时激活的实例数、token、存储、请求速率。配额进账本，超了就拒绝新工作。
- **定义多一层来源。** 覆盖顺序为平台模板 < 租户 < 用户。租户管理员可以锁定某些字段（可用模型、权限上限、预算上限），用户只能在锁定范围内改。SaaS 没有"项目目录"，项目目录这一层只在单机形态生效。

### 12.3 性能

- **休眠是常态。** 几十万用户里同时活跃的是少数。实例空闲就休眠，内存里只留常驻实例。激活时加载定义（有缓存）、信箱和线程头部，不加载整段历史。
- **单写者。** 每个实例同一时刻只在一个节点上运行，由实例租约保证，不用分布式锁。这和 A2"实例内部串行"一致。节点宕机后租约过期，由别的节点接管，靠落库和幂等记录恢复。
- **热路径要短。** 一次投递是一个事务；扇出走订阅索引；程序匹配器在内存里跑。需要模型判断的匹配器不在内核热路径上。
- **主要成本在模型调用。** 缓存键按实例分配；常驻 Router 合并积压信封后批量处理。
- 具体指标（激活延迟、单节点承载实例数）在 T1 之后做压测再定，本篇不写数字。

### 12.4 电脑操作

> 本节描述的是 SaaS 应用怎么用底座，守护进程不是底座的交付物（A15）。底座只定义"执行端"接口：工具调用交给哪个执行端，执行端在本进程、容器还是远端设备，由应用装配。

采用计算与执行分离：智能体在云端运行，用户电脑上装一个轻量守护进程（Go），只负责执行命令和返回结果。

- **连接方向。** 守护进程主动连云端，本机不开入站端口。首次绑定用扫码配对，之后靠设备证书认证。
- **本地策略是最后一道防线。** 允许访问的目录、本地沙箱、高风险操作的确认都由守护进程在本机执行，确认框也在本机弹出。即使云端被攻破或被提示词注入，也绕不过本机策略。这针对的是原文 8.4 提出的风险：云端失守会连带所有已连接的设备。
- **离线。** 设备不在线时，任务留在信箱里，设备上线后再执行。

### 12.5 嵌入与界面对接

- 内核对外只暴露应用接口层：发信封、订阅某个地址的事件。手机扫码、客服窗口、电商后台都是 `human:` 地址的端点适配器。
- 场景定制 = 定义模板 + 工具插件 + 桥接 + 界面视图，不改内核。比如客服场景是一个只开知识库和工单工具的智能体定义，加一个网页聊天端点。
- 接口用协议文档描述，TS 和 Python 类型从 Go 生成，不手写。

### 12.6 插件（外部，Node / Python）

- **运行方式。** 插件在独立进程里运行（单机形态）或作为远端服务（SaaS）。通信走扩展进程协议：本地用 stdio，远端用 HTTP / WebSocket，消息格式都是 JSON-RPC 2.0。官方提供 Node（TypeScript）和 Python 两套 SDK。MCP server 作为插件的一种继续支持。
- **能贡献的**：工具、资源类型、匹配器、桥接、信封渲染器、定义模板、界面视图。
- **不能贡献的**：守卫、账本、存储、沙箱。凡是安全边界上的东西只能由组件实现，防止第三方代码改变安全规则。
- **安全。** 插件在清单里声明自己要的权限，安装时由用户或租户管理员授予。插件只能拿到发给它的信封内容，看不到其他租户的数据。调用有超时和熔断。SaaS 里的第三方插件跑在租户隔离的容器里，不和内核同进程。
- **怎么选。** 对性能和安全要求高、所有场景都要用的，做成组件（Go）；面向具体场景的业务能力，做成插件。

### 12.7 审查发现的现状差距

- `core/runtime/runtime.go` 的 `Builder.DB` 类型是 `*sqlite.DB`，内核直接依赖了 SQLite。要做 SaaS 和嵌入，内核必须只依赖存储接口，这一项并入 T1。
- 事件总线 `bus` 是进程内实现。SaaS 多节点下需要一个跨节点实现，`bus` 要先抽成接口。
- 现有表没有 `tenant` 字段。T1 加字段的成本最低，往后加要做数据迁移，所以放进 T1。
- 沙箱现在只有本机实现。SaaS 下 shell 只能跑在容器沙箱或端侧守护进程里，内核不能假设本机可执行。

## 十三、多人使用与记忆

一个智能体给多人用，不需要额外的定义或概念：

- **按会话区分。** 接入层（客服窗口、手机扫码、IM）创建会话时，在会话元数据里写上使用者，例如 `user = "u123"`。内核不解释这个字段，只负责保存和传递。一个人可以开很多个会话，很多人也可以同时和同一个智能体对话，每个会话都是独立的线程。
- **记忆靠挂组件。** 需要跨会话记住用户时，在定义里挂 `memory` 组件，配置 `by = "user"`。组件按会话元数据里的使用者给记忆分区，提供 `memory.*` 工具和一个系统块。不挂就没有长期记忆，只有会话本身。
- **事实来源只有会话。** 会话日志是唯一事实来源；记忆库里的内容是组件从会话提炼出来的派生物，带来源会话的引用，可以删。
- **隔离由组件保证，不由模型保证。** 分区键取自当前会话的元数据，不取自模型给的工具参数。模型怎么写查询，也读不到别人的记忆。
- **凭据同理。** 工具需要用户身份时（比如查订单），由工具组件按会话元数据里的使用者解析凭据引用，模型看不到真值（12.2）。

这也是"内核只做智能体底座"的体现：个人助手、客服、团队 Router 用的是同一个内核，差别只在挂了哪些组件、组件怎么配置。

## 十四、底座与应用的边界（SDK）

### 14.1 分两层交付

```
应用层（各自独立的项目，引用底座）
  YBase 桌面版 · SaaS 服务 · 客服 · 电商导购 · 手机扫码 · 端侧守护进程
────────────────────────────────────────────
底座（本项目）
  内核：定义 · 实例 · 线程 · 信箱 · 资源与订阅 · 守卫 · 模型调度
  标准组件：fs、shell、agent、group、board、memory、permission、store-sqlite …
  接口：存储 · 事件总线 · 执行端 · 接入端点 · 组件注册
```

底座不带界面、不带服务进程、不假设部署形态。第十二节写的单机 / SaaS / 嵌入，是三种"应用怎样用底座"的例子，用来检验接口够不够，不是底座要实现的东西。

### 14.2 引用方式

| 方式 | 适合 | 说明 |
|---|---|---|
| Go 库 | Go 写的应用 | 直接 import，用代码装配组件和定义。这是第一优先级 |
| 服务模式 | 非 Go 应用（Node、Python、Java、手机端） | 底座附带一个可选的薄服务壳，暴露"发信封 / 订阅地址事件 / 管理定义"三类接口（HTTP / WebSocket）；Node、Python SDK 是这套接口的客户端，类型从 Go 生成 |
| 插件 | 给底座加能力 | 走扩展进程协议（12.6），和"引用底座"是反方向 |

Go 库的最小用法示意（接口名待 T1 定）：

```go
kit := ybase.New(
    ybase.WithStore(sqlite.Open("data.db")),   // 应用选存储实现
    ybase.WithModels(models.FromConfig(cfg)),
    ybase.WithComponents(fs.New(), shell.New(), memory.New(memlib)),
)
kit.LoadSpecs("agents/")                        // 加载定义文件
th, _ := kit.Open("agent:support", ybase.Meta{"user": "u123"})
events := th.Send(ctx, "我的订单到哪了？")        // 事件流：文本、工具调用、确认请求
```

### 14.3 底座必须守住的约束

- `core/` 只依赖接口，不 import 任何具体实现（SQLite、本地沙箱、具体模型协议）。这一条进 T1 验收。
- 不读全局配置文件、不写固定目录、不假设有终端；路径、配置、日志都由应用传进来。
- 一个进程里能开多个底座实例互不干扰（测试和多租户应用都需要）。
- 对外接口有版本号；破坏性变更走大版本。

### 14.4 对演进步骤的影响

- T1 加一项：抽出 `ybase.New(...)` 入口；现有 `apps/ybase` 改成"底座的第一个应用"，只通过公开接口使用底座。验收：`apps/ybase` 不 import `kernel/core` 的内部包。
- 服务壳和 Node / Python 客户端放在 T2 之后，等信封和地址定型再做，避免接口返工。
- 端侧守护进程、SaaS 节点不进 T0–T6，由各自应用项目排期。
