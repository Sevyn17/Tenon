# 05 数据与存储

> 状态：草案（2026-11-01）。索引见 [00 - 索引](<./00 - 索引.md>)。

## 5.1 本质：框架只存它运行需要的数据

框架存的数据只有一个用途：让智能体跑起来，出故障后能接着跑。包括定义、会话、对话日志、信箱、工具结果。这些数据的结构由框架定，应用不能改，因为恢复、压缩、缓存逻辑都依赖字段的确切含义。

应用要挂的信息（属于哪个用户、哪个店铺，界面上叫什么）对运行时来说是附加信息，走开放的扩展位。这和 Kubernetes（核心对象固定 + labels/annotations + CRD）、Stripe（`metadata`）是同一种做法。

## 5.2 数据归属三类

| 类别 | 谁定结构 | 例子 | 规则 |
|---|---|---|---|
| 内核数据 | 框架 | 定义、会话、日志、信箱、工具结果、追踪、blob | 应用不能加列、不能改含义；迁移由框架做 |
| 组件数据 | 组件 | 记忆条目、任务板、小组消息、客服工单 | 通过 `Collection` 声明，组件自己迁移，名字带组件前缀 |
| 应用业务数据 | 应用 | 订单、商品、用户资料、统计报表 | 放应用自己的库，框架不管 |

## 5.3 应用扩展数据的四条路（B6）

| 应用想做什么 | 怎么做 |
|---|---|
| 给框架对象贴自己的属性 | 会话上写 `meta`；定义里写 `x.*` |
| 存一套自己结构的数据，关联到框架对象 | 写组件，用组件 `Collection`，以会话 id、用户或租户关联 |
| 把框架发生的事记到自己的库 | 订阅事件（只读、异步），写进应用库 |
| 改变智能体行为 | 写组件，挂中间件（04 4.3） |

不允许：给内核表加列，或改内核字段的含义。真有这种需要，说明框架缺一个通用能力，应提成框架需求、出新版本。

## 5.4 `meta`

每个会话有一个 `meta`：字符串键值对（值可以是 JSON）。租户和用户不放 `meta`，它们是一等字段，从调用上下文取（07 7.3）。

- **谁写**：应用在新建会话时写入，例如 `app.NewSession(ctx, "support", tenon.Meta{"shop": "s9"})`（07 7.3）。之后应用可以通过 SDK 修改。
- **谁不能写**：模型。没有任何工具能改 `meta`。
- **谁用**：组件按租户、本轮触发者和 `meta` 分区（记忆按用户、凭据按用户解析，店铺数据按 `meta.shop`），这些都由内核填进 `*Ctx`（04 4.4），所以模型无法冒充其他用户。
- **查询**：应用在装配时声明需要索引的键，例如 `tenon.IndexMeta("shop", "channel")`。存储实现负责建索引（SQLite 表达式索引，Postgres JSONB 索引，Mongo 普通索引）。没声明的键只能存取，不能查询，避免全表扫描。
- **限制**：总大小上限（缺省 8 KB）；键名 `tenon.` 前缀保留给框架。

现状：`sessions` 表没有 `meta` 列，T1 加上。

## 5.5 存储原语（B2）

内核和组件都只依赖接口，不依赖具体数据库：

> 落地节奏（2026-11-02 决定）：T1b-1a 起 `Store` 保持由 `SessionStore`、`InboxStore`、`ToolResultStore`、`DefinitionStore` 嵌入组成的形状，使用方只依赖自己用到的小接口（如 `agent.PersistStore`、`host.Store`、`agent.ToolStore` 依赖 `store.ToolResultStore`）。下面"按子存储访问"（`Sessions()`、`Queue()` 等）随 `Tx` 在 T3 落地，那时发件箱和 `session_pending` 出现，拆分形状才确定。
>
> 落地（2026-11-10，T4a）：`Collection` 已落地，但不在 `Store` 上，而在可选的 `CollectionStore`（5.6）。下面代码块里的 `Store.Collection` 以 5.6 为准。

```go
type Store interface {
    Specs()   SpecStore    // 定义包
    Sessions() SessionStore // 会话：定义及版本、租户、创建者、父会话、租约（持有者 + epoch）、状态、meta、使用配置、会话键
    Log()     LogStore     // 有序追加、按区间读、截断归档
    Queue()   QueueStore   // 信箱：入队（按 id 幂等）、带租约领取、确认
    Pending() PendingStore // 待回复表 session_pending：corr、所属会话、预期回复方、deadline、是否已用、原请求那一轮的权限主体（02 2.3，D3）
    Outbox()  OutboxStore  // 发件箱：一轮内产生的外发信封，由投递器搬运
    ToolResults() ToolResultStore // 工具调用记录：pending / done、参数哈希、deadline（02 2.6）
    Checkpoints() CheckpointStore // 一轮运行的检查点
    Traces()  TraceStore   // 模型请求记录（现 session_requests）与追踪，供 explain 和调试界面
    Blobs()   BlobStore    // 大内容，按 sha256 去重
    Resources() ResourceStore // 资源与订阅（订阅者、资源、匹配器），04 4.7
    Collection(owner, name string, spec CollectionSpec) (Collection, error) // owner 由框架按组件名填，组件只调 Registrar.Collection（04 4.2）
    Tx(ctx context.Context, p Partition, fn func(Tx) error) error

    // 按会话键原子地查找或新建会话；跨出单会话分区，所以单列为原语（13 13.3）
    FindOrCreateSession(ctx context.Context, k SessionKey, create func() SessionMeta) (SessionMeta, bool, error)
}

// 会话键唯一约束的四项；Key 为空时不调用 FindOrCreateSession，直接新建
type SessionKey struct {
    Tenant  string
    Agent   string // 定义全名
    Creator string
    Key     string
}

// 分区内事务句柄。内核数据和 Collection 都通过它写，只能写本分区
type Tx interface {
    Session() SessionStore
    Log() LogStore
    Queue() QueueStore
    Pending() PendingStore
    Outbox() OutboxStore
    Checkpoints() CheckpointStore
    Collection(c Collection) Collection // 把集合句柄绑定到本事务
}

// 分区 = 租户 + 分区键。内核数据的分区键是会话 id；Collection 的分区键由 CollectionSpec.Partition 决定
type Partition struct {
    Tenant string
    Key    string
}
```

所有写会话数据的接口（Log、Queue 确认、Pending、Outbox、ToolResults、Checkpoints）都带租约 epoch，存储只接受等于当前 epoch 的写入（02 2.2「租约与唤醒」）。

### 发件箱

外发信封、`corr` 签发、检查点如果分开写，崩溃后会重发或漏发。所以一轮内产生的外发信封写进本会话的发件箱，和待回复登记、检查点在同一个分区事务里提交。投递器之后把发件箱里的信封搬到目标会话的信箱，搬完标记已投递。信封 `id` 兼作幂等键，投递器重试不会重复入队（02 2.3）。

插入当前回合的信封，在本次调模型前的检查点同一事务里确认（02 2.4）。

### 跨分区的两个操作

- `FindOrCreateSession`：按（租户, 定义, 创建者, key）查或建。新会话的分区还不存在，不能放进单会话事务，所以由存储用唯一索引保证只建一个。并发时只有一个调用返回 `created = true`。
- 跨会话投递：走发件箱，不在一个事务里同时写两个会话。

每接一种数据库只实现这一个接口，所有内核功能和只用原语的组件就都能用。

### 对数据库的硬性要求

"任何数据库"并不成立。框架要求：

1. 单条记录的条件写（按版本号比较后写）：多节点抢同一会话时保证只有一个写者。
2. 有序追加：对话日志严格有序。
3. 二级索引：按 `meta` 声明的键、按 `Collection` 声明的索引查询。
4. 同一分区内的事务：写日志和改会话状态一起成功或一起失败。内核数据的分区 = 一个会话。

满足的有 SQLite、Postgres、MySQL、TiDB、MongoDB、DynamoDB。纯 Redis、纯对象存储不满足，只能承担部分职责（例如对象存储做 `BlobStore`）。`Store` 允许组合：日志放 Postgres、blob 放对象存储。

## 5.6 `Collection`（B8）

组件的数据集合，只做四件事。组件调 `Registrar.Collection(name, spec)` 拿到集合句柄（04 4.7），集合全名由框架加组件前缀。

```go
type CollectionSpec struct {
    Version    int              // 结构版本，配合迁移；0 视作 1
    Indexes    []string         // 可等值查询的字段，写入时必须在正文里
    Partition  string           // 分区字段，缺省 "tenant"；可以是用户、会话、资源 id
}

// 每个操作都带分区键；租户由框架填（当前固定 store.Tenant），组件不能指定别的租户
type Collection interface {
    Get(ctx context.Context, part, key string) (Doc, error)
    Put(ctx context.Context, part string, doc Doc, ifVersion int64) error // 条件写，0 表示必须不存在
    Delete(ctx context.Context, part, key string, ifVersion int64) error
    Query(ctx context.Context, part, index string, eq any, page Page) ([]Doc, Page, error)
}

// 从 From 版本迁到 From+1 版本。From 必须从 0 连续到 spec.Version-1，跳号拒绝启动
type CollectionMigration struct {
    Collection string
    From       int
    After      []string // 依赖的其他集合，写 "<组件>.<集合>"，它们的迁移先跑
    Run        func(ctx context.Context, c Collection) error // nil 表示该版本没有数据要改
}
// 跨记录原子操作走 Store.Tx：分区 = 租户 + 本集合 Partition 字段的值，只能在同一分区内。
// 事务里用 tx.Collection(c) 把句柄绑定到本事务
```

`Collection` 不在 `Store` 上，而在可选的 `CollectionStore`（`Open` / `CollectionVersion` / `SetCollectionVersion` / `BindCollection`）。与 2026-11-04 收窄 `Store` 的决定一致（审查 P1-53，同 `PruneStore`）：没实现它的存储照样能用，只是登记了集合的组件启动时报"存储不支持集合"。

明确不做：查询语言、关联查询、聚合，以及"列出一个分区的全部"。理由：做了就会长成半成品 ORM，每接一种数据库都要重新适配；有了全量列举的口子，调用方会靠它做序号生成，而分页会把结果截断。要全量就声明一个恒为固定值的索引字段，分段查。

例：workgroup 的任务板（[workgroup.go](<../../../modules/collab/workgroup/workgroup.go>)）登记 `Collection("tasks", CollectionSpec{Version: 1, Indexes: []string{"status", "owner"}, Partition: "team"})`，`Put(doc, ifVersion)` 就是原来的 `rev` CAS。

### 迁移

- 每个 `Collection` 有 `Version`，组件用 `Registrar.CollectionMigration(CollectionMigration{...})` 登记从某版本到下一版本的迁移函数（04 4.7）；进度记在存储的 `collection_versions` 表里，与组件自有表的 `schema_versions` 分开。
- 组件可以在 `After` 里声明依赖其他集合，框架按依赖顺序执行。
- 迁移失败，框架拒绝启动。
- 迁移函数拿不到 SQL。来源是 SQL 表的一次性搬运放在组件自己的 `Start` 里（workgroup 的旧任务板 `p_workgroup_tasks` 就是这样搬的）。

## 5.7 SQL 出口

确实需要复杂查询的组件（报表、全文检索）显式声明：

```go
func (c *Report) Requires() tenon.Requires { return tenon.Requires{SQL: true} }
```

装配时框架登记 `service:sql` 服务（`store.SQL`：`DB() *sql.DB`、`Dialect()`、`Migrate()`），组件用 `tenon.Use[store.SQL]` 取；如果当前存储不是 SQL，装配直接报错（`plugin.Requirer` 检查，出错信息说明是哪个组件、缺哪个服务）。这个限制写在明面上，应用选数据库时就知道哪些组件用不了。

标准组件一律不用 SQL 出口。**过渡期例外**：现有 `p_<名>_*` 表（workgroup 等）在 T4 `Collection` 交付前声明 `Requires{SQL: true}`，从 T1b-1b 起生效。

## 5.8 内核数据一览（目标态）

| 数据 | 由现在的什么演进 | 说明 |
|---|---|---|
| 定义包 | `definitions` 表 | 加内容哈希版本、格式版本，文件进 blob |
| 会话 | `sessions` | 加创建者、租约（持有者 + epoch）、`meta`、使用配置、会话键 `key`；`agent_version` 保留，新加 `agent_hash TEXT` 存整包内容哈希；常驻由定义决定，会话不存（D6），也不是 key 的特例；`header`、`shell_hash` 等照旧。`key` 可以为空（NULL），没给 key 的会话不受唯一约束；在 (租户, 定义, 创建者, key) 上建部分唯一索引（只覆盖 key 非空的行），`FindOrCreateSession` 据此原子地查或建（13 13.3） |
| 注入记录 | 无 | 不建表：每个状态 key 上次发出的内容从日志里的 status 条目推导，用于只发变化的 key、压缩后按 key 重新注入（12 12.5） |
| 日志 | `session_entries` / `_archive` | 照旧 |
| 信箱 | `session_inbox` | 按会话收，按 11 信封表补列：from/to/corr/trace/hop/origin/caps/budget_ref/deadline，加 `mode` 列；现有 `kind` 列取值映射到 request/reply/notify/control，原 trust 映射到 origin（D2）。现有 `input` / `note` 两种用法（[host.go:42](<../../../runtime/host/host.go#L42>)）分别映射到 mode 的 wake / notice |
| 工具结果 | `tool_results` | 照旧 |
| 待回复表 | 无 | 新表 `session_pending`：corr、所属会话、预期回复方、deadline、是否已用、原请求那一轮的权限主体（D3）。现有 `session_requests`（[schema.go:44-49](<../../../runtime/store/sqlite/schema.go#L44>)）是模型请求记录，不是待回复表，归到下面的追踪 |
| 发件箱 | 无 | 新增：一轮内产生的外发信封、是否已投递（5.5「发件箱」） |
| 请求记录、追踪 | `session_requests`、`trace_spans` 等 | 照旧，供开发调试界面使用 |
| 资源与订阅 | 无（workgroup 自建表） | 新增：资源、订阅（订阅者、资源、匹配器） |
| blob | `blobs`、`blob_refs` | 照旧 |

内核数据表现在已带 `tenant` 列（[schema.go](<../../../runtime/store/sqlite/schema.go#L14>) 起；`blobs`、`session_shells`、`schema_versions` 除外），单机恒为 `local`。但 `sessions` 主键只有 `id`，目标态要求所有按 id 的查找都带租户条件。
