# Harness 约束清单

所有会影响模型行为、工具执行或会话结果的上限、超时、截断、缺省值都登记在这里。

规则：
- 新增或修改任何约束，必须先在本清单登记（值、位置、理由、谁能改），再改代码。
- 不登记的约束视为缺陷。出现“没干完 / 被截断 / 超时”时，先查本清单。
- “用户可改”列为“否”的项，是写死在代码里的；要开放给用户，先在这里改再动代码。

本清单里的 `.tenon`、`~/.tenon`、`TENON_HOME`、`TENON_API_KEY`、`tenon trust` 等写的是框架缺省的应用身份。应用用 `tenon.SetAppID` 改程序名、数据目录名和环境变量前缀后，这些名字跟着变（如 `.mortise`、`MORTISE_HOME`、`mortise trust`）。不随应用变的：`tenon-plugin.toml`、`${TENON_PLUGIN_DIR}`、`TENON_HOOK_EVENT`、`TENON_SESSION_ID`。

## 内核与插件的分界原则（2026-10-31，用户定）

判断一项行为放内核还是插件，只看它**是否影响会话内容**，即是否改变模型看到的东西：系统提示词、工具集与工具说明、工具结果文本、注入的消息、回合的推进与结束方式。

1. **影响会话内容的，做成插件或插件配置项。**由 profile 决定开不开、配置是什么，可以随时调整，而不是每次都改内核代码。即使不开放给最终用户，也必须是系统配置项，不能写死。
2. **不影响会话内容的系统优化，可以做在内核或插件内部，但要逐项判断是否需要配置。**纯缺陷修复（并发与死锁、哈希规范化）不设开关；带取值或取舍的（缓存目录位置、超时、并发数、保留期限等）照常设计成配置项，有缺省值并登记在本清单。不能因为“不影响会话”就写死参数。
3. **内核只提供机制，不替用户做决定。**内核自己生成、会进入会话的文本（如“结果未知”“用户拒绝”“工具不存在”“结果已转存”），只限于机制必需的错误和状态说明，并统一登记在本清单的“内核生成文本”一节。
4. **默认开启的插件只保留“没有它就不能正常工作”的那些。**其余由用户开启。开启后会改写模型所见内容的插件（如脱敏），要在 `explain` 和启动横幅里明示。
5. 新增任何影响会话内容的行为之前，先在本清单登记：属于哪个插件、配置项名、缺省值。

## `[kernel]` 配置节（2026-10-31 登记，插件开关方案）

内核里会影响会话内容的参数改由 profile 的 `[kernel]` 节配置，缺省值与上表一致。分层规则同 profile（内置 < 用户 < 受信项目 < `-profile`），按键合并。

| 键 | 缺省 | 作用于 |
| --- | --- | --- |
| `max_steps` | 0（不限） | 新会话的 Policy.MaxSteps；`-max-steps` 优先 |
| `max_tool_calls_per_step` | 16 | Policy.MaxToolCallsPerStep |
| `max_result_bytes` | 1048576 | Policy.MaxResultBytes |

| `confirm_deadline` | "24h" | 确认等待期限 |

压缩的 `headroom`（16384）、`keep_ratio`（0.16）是 compact-basic 插件的配置项，不在 `[kernel]`。
